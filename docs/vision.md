# 愿景

## 一句话

nett 是一个让你的机器和 AI agent 连成一张网的自托管系统：AI 能看懂它、安全地运维它，你的 agent 们也能通过它可信地相互协作。

## 面向谁

拥有少量、分散机器的个人或小团队：几台不同厂商、不同地域的 VPS，加上家里的 NAS、Mac 或迷你主机。这些机器网络环境各异，有的在 NAT 后面，有的跨境，规格普遍不高（常见 1 vCPU / 1 GB）。

## 要解决的问题

| 问题 | 常见的现状 |
|---|---|
| **机器之间没有打通** | 家里的服务靠端口转发加 VPS 反代对外提供，回源往往是明文；NAT 后的机器从外面连不上 |
| **管理工具分散** | 监控、部署、路由、证书各用一套工具，各自部署 agent，各自占用资源 |
| **部署靠手工** | SSH 上去拉镜像、改配置、重启；回滚靠记忆 |
| **故障没人通知** | 备份失败、定时任务没跑、磁盘快满，往往是事后才发现 |
| **不清楚系统全貌** | 哪台机器跑着什么、哪些端口暴露在外，只能逐台登录排查 |
| **小机器资源紧张** | 管理工具本身就占掉可观的内存 |

## 做成什么

- **Hub**：中枢，负责期望状态、汇总、告警、对外 API 和 Web 控制台；
- **nett-node**：每台机器一个，负责组网、监控采集、部署和入口配置，模块按需开启；
- **nett-relay**：能被外部连入的节点上的低权限进程，负责中继转发和公网传输入口；
- **Edge**：入口节点上的反向代理，负责公网流量（首期使用 Caddy）；
- **Web 控制台**：主要的交互入口。

## AI Native 的含义

不是在界面上加一个聊天框，而是让系统**对 AI 来说可读、可操作、可控**：

- 所有状态都通过资源化的 API 暴露，界面能做的事 API 都能做；
- 所有变更都走同一条"预演 → 批准 → 执行 → 验证"的路径，人和 AI 没有区别；
- AI 只能从有类型的动作目录里选择操作，高风险操作必须由人签名批准；
- 组网提供的身份和连通性，可以作为 AI agent 之间通信的基础设施。

## 设计约束

| 约束 | 含义 |
|---|---|
| **资源占用极低** | node 空闲常驻 ≤ 5 MB；Hub 稳定运行 ≤ 30–50 MB |
| **性能好** | 组网加密使用 WireGuard，Linux 上由内核完成；大流量优先直连，不绕中继 |
| **适应复杂网络** | 局域网、公网、国内、跨境；没有入站 80/443 的家宽、NAT 型 VPS、UDP 被限速或识别的链路 |
| **高可用** | 路径抖动、中断或节点离线时自动切换，连接不中断；没有单点；Hub 离线不影响组网 |
| **多平台** | Linux、macOS、Synology DSM；手机通过标准 WireGuard 客户端接入 |
| **单用户** | 不做多租户 |
| **安全默认** | 管理和流量分离；高权限组件不对外；提升权限必须签名 |

## 需求优先级

**必须有**：自动选路、自动切换的组网与加密回源；声明式部署（CI 触发、版本可见、回滚、部署钩子）；告警（包括心跳缺失）；资产清单；认证与签名授权；完整的 API 和 Web 控制台。

**应该有**：暴露面审计；只读日志；入口路由联动；趋势图表。

**可以有**：MCP 适配层；运维 Agent；agent 通信；多跳寻路、QUIC 与混淆传输、打洞；移动端 App。

## 不做什么

| 不做 | 原因 |
|---|---|
| Kubernetes | 面向的是跨地域、低规格、服务绑定在固定机器上的场景，调度没有用武之地 |
| 多租户 | 单用户定位 |
| 远程 shell、任意命令执行 | 安全风险；需要时通过组网直接 SSH |
| 在服务器上构建镜像 | 交给 CI |
| 日志全文检索、APM、链路追踪 | 资源消耗与目标规模不匹配 |
| 在 node 中运行 AI 逻辑 | node 保持小巧、行为确定；AI 只经由 Hub 的 API 接入 |
