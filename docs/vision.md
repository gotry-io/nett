# 愿景

## 一句话

nett 是一个开源、自托管的基础设施，把你的机器和 AI agent 连成一张网：AI 能看懂它、安全地运维它，你的 agent 们也能通过它可信地相互访问。

## 面向谁

拥有少量、分散机器的个人或小团队：几台不同厂商、不同地域的 VPS，加上家里的 NAS、Mac 或迷你主机。这些机器网络环境各异，有的在 NAT 后面，有的跨境，规格普遍不高（常见 1 vCPU / 1 GB）。

nett 按开源项目设计：任何人都可以在自己的机器上部署；每份部署只服务一个用户。

## 要解决的问题

| 问题 | 常见的现状 |
|---|---|
| **机器之间没有打通** | 家里的服务靠端口转发加 VPS 反代对外提供，回源往往是明文；NAT 后的机器从外面连不上 |
| **管理工具分散** | 监控、部署、路由、证书各用一套工具，各自部署 agent，各自占用资源 |
| **部署靠手工** | SSH 上去拉镜像、改配置、重启；回滚靠记忆 |
| **故障没人通知** | 备份失败、定时任务没跑、磁盘快满，往往是事后才发现 |
| **不清楚系统全貌** | 哪台机器跑着什么、哪些端口暴露在外，只能逐台登录排查 |
| **小机器资源紧张** | 管理工具本身就占掉可观的内存 |
| **agent 之间无法安全互访** | 不同机器上的 AI agent 要互相调用，要么暴露到公网，要么既不知道对方是谁，也管不住谁能调用什么 |

## 做成什么

- **Hub**：中枢，负责期望状态、汇总、告警、对外 API 和 Web 控制台；
- **nett-node**：每台机器一个，直接运行在系统上（不放进容器），负责组网、监控采集、部署和入口配置，模块按需开启；
- **nett-relay**：能被外部连入的节点上的低权限进程，负责中继转发和公网传输入口；
- **数据面进程**：需要在用户态处理组网数据包的节点上运行（TLS 传输、无内核模块平台上的 WireGuard），与 nett-node 分开，node 升级或重启时组网不中断；
- **Edge**：入口节点上的反向代理，负责公网流量（首期使用 Caddy）；
- **Web 控制台**：唯一的图形界面，承担查看、管理、审批和签名。暂不提供移动端 App；手机通过标准 WireGuard 客户端接入组网，告警经 Telegram、邮件或 webhook 送达。

## 功能范围

| 领域 | 包含什么 |
|---|---|
| **组网** | 自动选路、自动切换，连接不中断；局域网直连、公网直连、经中继、多跳接力、打洞；UDP、TLS、QUIC 和混淆传输；局域网智能入口；手机双路径接入；主机名与访问控制 |
| **观测与告警** | 以替代 Beszel 这类轻量监控为准：主机 CPU、内存、磁盘、网络、温度，容器指标，NAS 的 SMART 与 RAID，节点之间的线路质量；阈值、OOM 与重启、节点离线告警；心跳检查（包括 systemd 定时器有没有按时成功）；资产清单（机器、服务、对外监听的端口）；历史图表 |
| **部署** | 构建交给 CI（例如 GitHub Actions 构建镜像）；nett **只管理容器（Compose）**：版本可见、默认在控制台手动一键部署、每个 stack 可以单独开启自动部署、部署钩子、失败自动回滚、一键回滚；只读的容器日志。直接装在系统上的原生服务只观测，不负责安装和升级 |
| **入口** | 在控制台配置路由，Edge 自动生效；证书自动申请；回源经组网加密，需要时保留访客的真实 IP |
| **认证与授权** | passkey 登录与签名授权；API token；CI 用 OIDC；提升权限、组网准入都必须由用户签名 |
| **AI 接入** | 所有能力通过 API 暴露；MCP 适配层（把 nett 自己的 API 提供给 AI 运维）；运维 Agent |
| **agent 互访** | 不同机器上的 agent 经组网互相访问：身份可验证（工作负载身份）、访问可控（网络层的访问规则、工具层的 MCP 网关）、调用可审计；服务发现 |

## 需求优先级

**必须有**：组网（包括多跳、打洞、QUIC 与混淆传输）与加密回源；观测与告警的基础能力；容器部署与只读日志；入口路由；认证与签名授权；agent 互访；完整的 API 和 Web 控制台。

**可以有**：MCP 适配层与运维 Agent；原生服务的受限部署（单个静态二进制，由 systemd 沙箱约束）；按次批准的短期 SSH 证书。

## 怎样算"能用了"

M1–M3 完成时：原来各自部署的轻量监控（如 Beszel）、容器管理面板（如 Portainer）、反向代理的管理界面、手写的隧道和家宽端口转发都可以下线；nett 的资源占用比这些工具加起来更低；日常操作不再需要 SSH 登录机器。

## AI Native 的含义

不是在界面上加一个聊天框，而是让系统**对 AI 来说可读、可操作、可控**：

- 所有状态都通过资源化的 API 暴露，界面能做的事 API 都能做；
- 所有变更都走同一条"预演 → 批准 → 执行 → 验证"的路径，人和 AI 没有区别；
- AI 只能从有类型的动作目录里选择操作，高风险操作必须由人签名批准；
- 组网提供的连通性和身份，是 agent 之间互相访问的基础；在此之上，MCP 网关负责工具级的授权和审计。

## 设计约束

| 约束 | 含义 |
|---|---|
| **资源占用极低** | 节点上每个常驻进程（node、relay、数据面）空闲 ≤ 5 MB；Hub 稳定运行 ≤ 30–50 MB |
| **性能好** | 组网加密使用 WireGuard，Linux 上由内核完成；大流量优先直连，不绕中继 |
| **适应复杂网络** | 局域网、公网、国内、跨境；没有入站 80/443 的家宽、NAT 型 VPS、UDP 被限速或识别的链路 |
| **高可用** | 路径抖动、中断或节点离线时自动切换，连接不中断；没有单点；Hub 离线不影响组网 |
| **多平台** | Linux、Synology DSM、macOS（经 Docker 中的容器内成员加入组网）、Home Assistant OS（以加载项运行）；手机通过标准 WireGuard 客户端接入。支持矩阵见 architecture.md 第 14 节 |
| **通用** | 开源项目：不依赖特定的云厂商、地区或网络环境；环境之间的差异由能力探测和测量处理，不写死 |
| **双语** | Web 界面、命令行输出、错误信息、告警通知和面向用户的文档提供中文和英文 |
| **单用户** | 每份部署只服务一个用户，不做多租户 |
| **安全默认** | 管理和流量分离；高权限组件不对外；提升权限必须签名，组网成员也凭签名准入；Hub 被攻破不能越权 |

## 不做什么

| 不做 | 原因 |
|---|---|
| Kubernetes | nett 不替代、也不集成 K8s。K8s 解决的是"大量同质机器由调度器决定容器跑在哪"；nett 面向少量、规格不一、分散各地的机器，服务固定在某台机器上，不需要调度；K8s 的控制面本身就要数百 MB。在某些机器上自行运行 k3s 的用户，仍然可以用 nett 把这些机器连起来 |
| 多租户 | 每份部署只服务一个用户 |
| 远程 shell、任意命令执行 | agent 一旦被提示词注入，shell 就意味着可以执行任意命令，并沿组网扩散，事后也难以审计和撤销。nett 只提供管道：需要时经组网 SSH，由访问规则限定谁能连哪台机器；运维操作走有类型的动作目录 |
| 移动端 App | 暂不计划。Web 控制台承担全部查看和管理；手机使用标准 WireGuard 客户端 |
| 在服务器上构建镜像 | 交给 CI |
| 安装和升级原生服务 | 部署只管理容器；原生服务只观测 |
| 日志全文检索、APM、链路追踪 | 资源消耗与目标规模不匹配 |
| 遥测 | 默认不收集、不上报任何使用数据 |
| 在 node 中运行 AI 逻辑 | node 保持小巧、行为确定；AI 只经由 Hub 的 API 接入 |
| 计费与用量核算 | nett 是基础设施：只提供容量上限、测量和自动选路这些机制。机器按什么方式计费、上层业务怎样使用带宽，由用户自己决定，nett 不做判断 |
