# 架构

本文描述整体架构和长期稳定的设计原则。各阶段的详细设计见 [design/](design/README.md)，关键决策的理由见 [adr/](adr/README.md)。

## 1. 总览

```
┌──────────────────────────── 浏览器 ─────────────────────────────┐
│ Web 控制台：React SPA，WebAuthn（passkey 登录与签名）             │
└───────────────┬────────────────────────────────────────────────┘
                │ HTTPS：REST/JSON + SSE
┌───────────────▼──────────── Hub 主机（同时是入口节点）────────────┐
│ Edge：反向代理（TLS 终止）                                        │
│ nett-hub：对外 API · 认证 · 期望状态 · 变更集 · 告警 · 审计          │
│           SQLite · node 网关 · 内嵌 Web 前端                          │
│ nett-relay：中继与公网传输入口（低权限）                              │
│ nett-node                                                       │
└───────────────┬────────────────────────────────────────────────┘
                │ 控制：WebSocket over TLS + Protobuf（node 主动连接）
                │ 数据：nett 组网（WireGuard 会话 + nett 路径层）
        ┌───────┼────────────┬─────────────────┐
     VPS 节点   VPS 节点     家里的智能入口      家里的其他主机
     nett-node（+ nett-relay）                 （经智能入口接入，无需安装）

外部：CI ─OIDC─► Hub　　手机 ─标准 WireGuard─► 家里入口 / 移动网关
```

## 2. 角色与能力边界

| 角色 | 负责 | 不负责 | 权限 | 监听公网 |
|---|---|---|---|---|
| **Hub** | 保存期望状态；汇总状态和指标；告警；对外 API；分发组网拓扑；转发签过名的策略 | 直接操作机器；自行提升任何节点的权限；处于数据通路上 | 普通 | 经 Edge 暴露 |
| **nett-node** | 在本机执行：采集、部署、生成 Edge 配置；把组网配置交给组网进程并启停各进程；上报状态 | 监听公网端口；执行任意命令；运行 AI 逻辑；自行决定权限 | 高 | 否 |
| **组网进程** | WireGuard 配置、路径层（测量、选路、切换）、DNS、访问规则与地址转换、准入材料验证；独立于 node 运行（ADR 0013） | 连接 Hub；访问 Docker；执行外部命令 | `CAP_NET_ADMIN`；用户态平台上需要 TUN 权限 | 只有 WireGuard 端口，与内核实现一样不响应未认证的数据包 |
| **传输适配进程** | TLS 传输适配，只经手密文（ADR 0013） | 持有任何密钥；任何管理功能 | 低 | 否（主动连出） |
| **nett-relay** | 中继转发加密数据包；接收 TCP/TLS 等传输；探测应答；按连接转发（CONNECT） | 解密组网流量；任何管理功能 | 低 | 是 |
| **Edge** | TLS 终止；按域名把请求转发到组网内的服务 | 任何管理功能 | 低 | 是 |
| **用户的 passkey** | 签名批准提升权限的变更 | — | 持有签名私钥 | — |

**三条原则**

1. **管理和流量分离**：Hub 和 node 都停止时，网站和组网照常工作，只是暂时无法变更和观测。
2. **有权限的不对外，对外的没权限**：nett-node 和组网进程都不监听公网地址（组网进程只在组网地址上提供 DNS 和探测应答；局域网地址上的探测应答只在存在局域网直连候选时开启，且不响应未认证的探测）；所有公网监听都交给独立的低权限进程（Edge、nett-relay，以后的 MCP 网关）。WireGuard 的 UDP 端口由内核或组网进程监听，对未认证的数据包不作任何响应。
3. **决定和执行分离，提升权限必须签名**：Hub 被攻破也无法越权，前提是用户没有在被攻破的控制台上完成签名（控制台页面由 Hub 提供，见 design/auth.md 第 2 节）。组网成员、宣告网段和访问规则同样由签名产物构成（ADR 0014），部署能使用的特权由签名的部署档位限定，带机密的 stack 定义也要签名。

## 3. nett-node

单进程，tokio 单线程运行时，**直接运行在系统上，不放进容器**：它要读取宿主上的全部进程、systemd 服务与定时器、SMART 与 RAID、温度、系统日志，管理宿主上的 Docker；组网进程还要通过 netlink 配置内核 WireGuard 和 nftables。放进容器就得开特权、共享宿主网络和进程空间、挂载大量宿主目录，实际上等于原生运行，而且更脆弱。macOS 的容器内成员只负责组网，是例外（ADR 0016）；Home Assistant OS 不允许直接安装程序，nett 以加载项运行、能力相应受限，是另一个例外（ADR 0017）。

nett-node 由以下部分组成：

- **Transport**：主动连接 Hub，认证，断线重连，多端点选优；
- **Supervisor**：计算模块是否生效，管理模块生命周期，崩溃后带退避地重启；
- **四个模块**：每个都是调和器（期望状态 → 实际状态 → 差异 → 执行），可重复执行，相互隔离；
- **State Store**：本地保存身份密钥、上一次生效的配置和部署版本（组网拓扑、准入材料和撤销记录由组网进程自己保存，ADR 0013）。**启动时先应用本地缓存，再连接 Hub**，避免组网和 Hub 相互依赖。

| 模块 | 负责 | 典型启用位置 |
|---|---|---|
| **metrics** | 主机和容器指标；平台特有指标（如 NAS 的 RAID、SMART、卷使用率）；服务与端口发现；原生服务的观测（进程、systemd 服务与定时器，定时器没有按时成功即可告警）；节点间线路质量（M1 由节点主动测量） | 所有节点 |
| **deploy** | **只管理容器（Compose）**：按 stack 定义拉镜像、启动、回滚，执行部署钩子；不超出签名的部署档位。原生服务只观测，不安装、不升级 | 运行容器的节点 |
| **mesh** | 把 `trust`、`mesh` 分区交给组网进程，启停组网进程、传输适配进程和 nett-relay，转发链路状态与指标。组网工作本身（第 6 节）在组网进程中完成，node 不在时照常进行（ADR 0013） | 直接加入组网的节点 |
| **ingress** | 把 Hub 的路由翻译成 Edge 配置并推送；向组网进程提交 Edge 专用地址的地址转换意图；检查回源健康和证书 | 入口节点 |

### 模块开关

**生效 = 本地未禁止 ∩ 节点能力 ∩ 签名策略**

| 层 | 由谁决定 | 作用 |
|---|---|---|
| 本地硬性禁止 | 节点管理员 | 可选的绝对上限，签名策略也无法突破 |
| 节点能力 | node 自动探测 | 缺少内核模块、Docker、root 权限等时，对应模块不可用或改用替代实现 |
| 签名策略 | Hub 下发 | 降低权限可直接下发；**提升权限必须带用户签名**；版本号只增不减 |

### 零配置

节点本地只保存**身份和权限**，其余来自 Hub 下发或本地探测：Hub 端点列表（入网时只需一个公网地址，其余由 Hub 推送，node 并发探测并选择最优）、网络可达性（`public` / `dial-only`）、局域网地址、组网地址、Docker socket 位置、平台特有采集项等。组网私钥在本机生成，永不离开节点。

```bash
curl -fsSL https://hub.example.com/install.sh | sudo sh -s -- enroll <token>
```

## 4. Hub

- **对外 API**：REST + JSON，资源化；从代码生成 OpenAPI 3.1；Web、脚本、以后的 MCP 和移动端都使用同一套 API；
- **实时数据**：SSE；
- **node 网关**：WebSocket + Protobuf；
- **组网控制**：分配地址、分发公钥和候选路径、维护中继名单和线路质量矩阵；
- **存储**：SQLite（WAL）；指标分层降采样，最多保留 30 天；
- **告警**：阈值、OOM 与重启、节点离线、心跳缺失（包括 systemd 定时器没有按时成功）。

**资源保护**：所有队列、缓存和通道设置上限；查询图表时服务端降采样（每条曲线约 1000 个点）；限制 SSE 连接数；数据和审计有保留策略；上线前做 24 小时浸泡测试。前端运行在浏览器中，对 Hub 只增加约 1 MB 二进制体积。

## 5. 认证与授权

| 身份 | 认证方式 |
|---|---|
| 用户 | passkey（WebAuthn）+ 恢复密钥；短期会话 Cookie |
| API token | 带权限范围、有过期时间、可吊销；固定前缀；服务端只存哈希 |
| node | 一次性入网 token → X25519 身份密钥；入网私钥由浏览器生成，节点用它签署准入证明（ADR 0014）；连接时在 WebSocket 内层用 Noise 协议双向认证并端到端加密 |
| CI | OIDC（如 GitHub Actions），不保存长期密钥 |
| 手机设备 | 设备凭据（WireGuard 密钥，或 CONNECT 凭据） |

```
请求 → 识别身份 → 检查权限范围 → 检查策略 → 执行 → 写入审计
```

**token 只能提议高风险变更，不能批准。**批准由用户用 passkey 签名：把变更内容的哈希作为 WebAuthn 挑战，浏览器里即可完成。

## 6. 组网

### 6.1 目标

像导航软件一样工作：节点之间有多条候选路径和多种传输方式，持续测量，自动选择最优路径；路径抖动、中断，或某个节点离线时，在几秒内自动切换，**正在进行的连接不中断**；没有单点。

### 6.2 分层

```
┌─ 会话层：WireGuard（负责加密）────────────────────────────────┐
│ 每对节点一个加密会话；更换路径时会话不变                           │
│ Linux 使用内核 WireGuard；无内核模块的平台使用 Rust 用户态实现       │
├─ 传输层：可插拔（负责把加密包送达）──────────────────────────────┤
│ UDP（默认）· TCP/TLS 443 · QUIC 443（后期）· 混淆包装（后期）       │
├─ 路径层：组网进程（负责选路，ADR 0013）──────────────────────────┤
│ 候选路径：局域网直连 · 公网直连 · 经中继 · 多跳接力                   │
│ 持续测量 → 打分 → 选择最优（带防抖）→ 变差时快速切换                  │
└──────────────────────────────────────────────────────────────┘
控制面：Hub（地址、公钥、候选路径、中继名单、线路质量矩阵）
```

- **会话层只用 WireGuard**：代码精简，经过形式化验证，Linux 内核原生支持，所有平台都有标准客户端。WireGuard 支持对端更换地址（为漫游设计），因此切换路径只需更新会话的对端地址，上层连接不受影响。WireGuard 的配置、路径层和无内核模块平台上的用户态实现，都在独立的组网进程中（ADR 0013）；macOS 以容器内成员加入组网（ADR 0016）。
- **传输层可插拔**：WireGuard 只支持 UDP，特征也明显。UDP 受限时，把加密后的数据包放进 TCP/TLS 或 QUIC 传输，外部看到的是普通的 HTTPS 或 HTTP/3 流量。
- **路径层是 nett 的核心**：它决定每对节点之间走哪条路径、用哪种传输。

### 6.3 候选路径与选路

| 候选路径 | 条件 |
|---|---|
| 局域网直连 | 两个节点在同一局域网（由 Hub 下发双方的局域网地址，组网进程探测确认） |
| 公网直连 | 至少一端可从外部连入（`public`） |
| 经中继 | 经某个 `public` 节点的 nett-relay 转发 |
| 多跳接力 | 经两个或更多中继（如跨境时经优质线路） |
| 打洞直连（后期） | 两端都在 NAT 后；由 Hub 交换双方地址后同时发包 |

选路：

- 对每条候选路径持续测量延迟、丢包和抖动；
- 按得分选择当前路径；新路径需要**明显更好并持续一段时间**才切换，避免来回跳动；
- 当前路径连续丢包时**立即**切换到次优路径，不等待评分周期；
- 节点按本地缓存的拓扑自主切换，**不依赖 Hub 在线**；
- 支持策略覆盖，例如指定某类流量优先直连，或强制经某个中继。

### 6.4 中继

- **所有 `public` 节点都具备中继能力**（`dial-only` 节点和手机不能为其他节点中转）。Hub 根据位置、实测质量、流量配额和资源余量决定实际使用哪些中继。
- **中继只转发加密后的数据包，看不到内容**，端到端加密不受影响。
- 中继由独立的低权限进程 nett-relay 承担，只在转发流量时消耗资源。
- 每个中继只使用一个 UDP 端口。在入口节点上与网站共用 443：WebSocket 传输由 Edge 按域名转交，HTTP/2 CONNECT 由 Edge 按 TLS 的 SNI 转交（ADR 0011）。

### 6.5 网络可达性

| 类型 | 含义 | 连接规则 |
|---|---|---|
| `public` | 可从外部连入（公网地址，或映射了端口） | 可以接受连接，可以做中继 |
| `dial-only` | 只能主动连出 | 主动连接 `public` 节点；**至少连接两个**，避免单点 |

可达性由 node 与 Hub 共同探测，网络变化后自动更新。云厂商的安全组需要用户手动放行，各角色所需的端口见 design/mesh.md 第 5.5 节。

### 6.6 局域网接入

一个局域网只需要一台主机运行 nett-node，作为**智能入口**（subnet router）：把整个局域网段接入组网，并具备完整的选路和切换能力。局域网内的其他主机无需安装任何组网软件。智能入口对转发进来的流量做源地址转换，避免局域网主机的回包被本机的其他 VPN 或代理截走；来自 Edge 专用地址的流量转换为单独的"入口地址"，需要真实 IP 的服务只信任它（ADR 0015）。宣告的局域网段默认只对用户的设备开放。网关设备自带的 WireGuard 可以作为备用路径。

### 6.7 按连接转发（CONNECT）

除了数据包级别的组网，nett-relay 还提供 **HTTPS CONNECT 代理**（HTTP/2 over TLS）：

- 适合"由应用自己发起 TCP 连接"的场景：支持 HTTPS 代理的程序在 UDP 受限的网络中访问内网服务（Edge 所在主机本身是组网成员，回源直接走组网，不用 CONNECT）；
- 入口节点的 443 上只支持 HTTP/2 CONNECT（实测标准 Caddy 不能转发 HTTP/1.1 CONNECT 隧道），其他节点上的 nett-relay 两种都支持；
- 不需要专用客户端，任何支持 HTTPS 代理的程序都能使用；
- 只支持 TCP；中继能看到目的地址，非加密流量的内容也可见。中继都运行在用户自己的机器上，且中继之间每一跳都使用 TLS。

两种方式互补：组网承载任意协议；CONNECT 适合不便运行组网的客户端和应用层代理。

### 6.8 后备方案

tailscale（Headscale + derper + tailscaled）作为可选后备：在自研组网尚未覆盖的场景下使用，由 Hub 统一管理，对上层隐藏。上层只看到 nett 自己的概念（节点、地址、主机名、访问规则、链路状态）。后备方案未排期；只在用户显式启用的节点上运行，不受节点内存预算约束；Headscale 的地址池必须排除 nett 的组网网段。

## 7. 手机接入

手机端兼容**任意标准 WireGuard 客户端**：nett 仅导出标准配置（配置文件与二维码），不限定客户端。配置包含**两条路径**：

```
手机 ─┬─ 直连家里的智能入口（标准 WireGuard）→ 家里的服务，大流量（如视频）不绕路
      └─ 移动网关（标准 WireGuard）→ 其他节点；直连不可用时兜底
```

- 两个对端按网段分流，标准客户端即支持；
- 同一时间一台设备只归属一个移动网关，由它代为宣告设备地址；配置中列出两个 DNS 服务器（移动网关和智能入口）；
- 移动网关是 Hub 主机（或其他 `public` 节点）上的 WireGuard 接口，网关之后的路径由 nett 路径层负责；
- 一台设备可以有多份凭据（例如两个不同的客户端程序各一份），各自独立吊销，权限按设备授予；
- UDP 受限时，支持 HTTPS 代理的客户端可以经 nett-relay 的 CONNECT 代理访问内网服务；
- 移动端 App 暂不计划。标准客户端不会在路径之间自动切换，因此同时导出一份"全部经网关"的备用配置，供直连受阻时手动切换。

## 8. 入口路由

```
Hub 路由（域名 → 服务 → 节点:端口）→ ingress 模块 → Edge 配置
```

Hub 只保存与实现无关的路由模型；Edge 可以从 Caddy 换成其他反向代理，只需新增一个翻译后端。Edge 回源经过组网，路径由路径层选择；Edge 配置中写组网地址而不是主机名（Edge 常运行在容器中，解析不了组网后缀）。

**回源身份**（ADR 0015）：需要访客真实 IP 的服务，最后一跳必须来自一个只有 Edge 能使用的地址，服务只信任这个地址发来的 `X-Forwarded-For`。

| 服务所在位置 | 服务看到的转发者 |
|---|---|
| 组网成员上（Linux） | 入口节点的 Edge 专用组网地址 |
| 智能入口后面的局域网主机 | 智能入口的入口地址（只用于转换来自 Edge 专用地址的流量） |
| macOS 上的 Docker 容器 | 容器内成员在该容器网络中的地址（ADR 0016） |

路由同时决定了 Edge 能访问什么：每条路由生成一条"Edge 专用地址 → 目标主机:端口"的访问规则。新增或改变回源目标，等于把一个内网端口暴露到公网，属于高风险变更。

## 9. AI 接入

| 阶段 | 内容 |
|---|---|
| 现在 | 把基础打好：资源模型、API 优先、变更集（plan → approve → apply → verify）、动作目录（带风险等级）、身份模型、审计事件 |
| M4 | **MCP 适配层**：把 nett 自己的 API 包装成 MCP 工具，供 AI 运维 nett；**运维 Agent**：告警 → 诊断 → 提案 → 审批 → 执行 → 验证，作为 Hub 侧的独立服务 |
| M5 | **agent 互访**：不同机器上的 agent 经组网互相访问。工作负载身份（细化到每个 agent 或容器）；服务发现；**MCP 网关**，即挡在用户各个 MCP 服务前面的代理，负责统一入口、认证、按工具授权和调用审计 |

两层的分工：组网负责连通和网络层的身份与访问规则（M2 起，凭 `whois` 可以查到调用方是哪台机器）；MCP 网关负责工具层的授权和审计（M5）。

AI 不能执行 shell；它的输出只是提案，必须经过策略引擎和签名。nett 本身不提供远程 shell：agent 需要在远程机器上执行命令时，经组网 SSH，由访问规则限定能连哪些机器，命令本身由 agent 自己的运行环境把关。

## 11. 代码组织

```
nett/
├── proto/              # node ↔ Hub 的 Protobuf 定义
├── crates/             # node、mesh、transport、relay、cli 链接为同一个 nett 可执行文件
│   ├── nett-proto/
│   ├── nett-core/      # 共享领域模型
│   ├── nett-trust/     # 签名载荷、信任锚、准入材料与撤销记录的验证（node 与组网进程共用）
│   ├── nett-hub/
│   ├── nett-node/
│   ├── nett-mesh/      # 组网进程：WireGuard 配置、路径层、DNS、过滤与地址转换
│   ├── nett-transport/ # 传输适配进程
│   ├── nett-relay/
│   └── nett-cli/       # nett 命令
├── web/                # React SPA；src/api 由 OpenAPI 生成
└── docs/
```

生成链路：`proto → prost → Rust`；`Hub 代码 → utoipa → openapi.json → TypeScript 客户端`。CI 检查生成文件是否最新。

## 12. 故障与可用性

### 12.1 Hub 与 node 的关系

Hub 是控制面，node 是执行者：

- node 主动连接 Hub，Hub 从不主动连接 node；
- node 只执行 Hub 下发的、签过名的期望状态，不自行决定权限；
- **node 和组网进程各自在本地保存上一次生效的配置**（组网拓扑、准入材料和撤销记录由组网进程保存），重启时先应用本地配置，再连接 Hub；
- **Hub 不在数据通路上**：节点之间的组网流量、访客访问服务的流量都不经过 Hub；路径切换由节点自主完成。

### 12.2 故障场景

| 场景 | 继续工作 | 暂停 | 应对 |
|---|---|---|---|
| **Hub 进程停止**（崩溃、升级、重启） | 节点间组网与自动切换、Edge 回源、手机接入、已部署的服务 | 告警、部署与配置变更、新节点入网 | node 本地缓存指标（有上限），Hub 恢复后补传 |
| **nett-node 停止**（崩溃、升级、被 OOM 杀掉） | 组网与自动切换、DNS、Edge 回源、已部署的服务 | 指标上报、部署、配置变更 | 服务管理器自动重启；组网进程独立运行（ADR 0013） |
| **Hub 主机宕机** | 不经过该主机的路径和服务 | 上述全部，以及该主机上的 Edge、中继、移动网关 | 路径层自动绕开；见 12.3 |
| **某个节点宕机** | 其余节点；以它为中继的路径自动绕开 | 该节点上的服务 | Hub 发出节点离线告警 |
| **某条路径变差或中断** | — | — | 路径层在几秒内切换，连接不中断 |

### 12.3 消除单点

1. **多点连接**：`dial-only` 节点至少连接两个 `public` 节点。
2. **至少两个可用中继**，且位于不同主机。这是冗余下限，不限制中继数量。
3. **组网不依赖控制面在线**：拓扑和密钥持久化在各节点本地，没有过期问题；Hub 不在时，节点照常选路和切换。
4. **移动网关可以部署多个**；手机同时保留直连家里的路径。
5. **外部死信开关**：Hub 定期向外部发送心跳，心跳中断即报警，解决"Hub 自己挂了谁来告警"的问题。实现方式可以是另一台节点上的 metrics 模块（检查 Hub 的心跳是否按时到达），或外部的心跳检测服务。
6. **备份与重建**：Hub 的数据库连同 Hub 身份私钥和主密钥，用备份公钥加密后，由其他节点定时拉取（Hub 从不主动连接节点），拉取是否按时完成本身是一项心跳检查；提供在另一台主机上重建 Hub 的操作手册。node 的端点列表包含备用入口，Hub 迁移后节点自动连上新的 Hub。备份总是落后于节点的状态，恢复时由节点回传已生效的签名产物（protocol.md 第 6.4 节）。

## 13. 打包、安装与运行

### 13.1 发布物

| 发布物 | 包含 | 安装位置 |
|---|---|---|
| **`nett`** | 一个可执行文件，按子命令运行为不同角色：命令行、`nett node`、`nett mesh`、`nett transport`、`nett relay` | 所有节点 |
| **`nett-hub`** | Hub 与内嵌的 Web 前端 | 只在 Hub 主机 |
| **HA 加载项** | `nett` 的容器镜像与加载项仓库（ADR 0017） | 运行 Home Assistant OS 的设备 |

代码层面 node、mesh、transport、relay、cli 仍是独立的 crate，最终链接成同一个可执行文件。这样安装和升级只有一次、版本不会错配；多个进程映射同一个文件，代码页由系统共享，总内存更低。安全隔离依靠运行用户和权限，与是否同一个文件无关。

### 13.2 运行方式

| 服务 | 运行身份 | 何时运行 |
|---|---|---|
| `nett-node` | root，或具备 `CAP_NET_ADMIN` 和 docker 组权限的用户；直接运行在系统上，不放进容器（第 3 节） | 所有节点 |
| `nett-mesh` | Linux 上为具备 `CAP_NET_ADMIN`（DNS 需要时加 `CAP_NET_BIND_SERVICE`）的专用用户；用户态平台上为能创建 TUN 的身份；持有组网私钥 | 开启 mesh 模块的节点；先于 nett-node 启动，单独的内存上限和更低的 OOM 优先级 |
| `nett-transport` | 专用的低权限用户，不持有任何密钥 | 存在 TLS 传输候选时由 nett-node 启用 |
| `nett-relay` | 专用的低权限用户；不持有组网私钥 | 由 Hub 按节点可达性和签名策略决定启用，nett-node 负责启用或停用；`dial-only` 节点不运行 |
| `nett-hub` | 专用的低权限用户；也可以用容器运行（Hub 不需要访问宿主） | Hub 主机 |

每个服务崩溃后由服务管理器自动重启，不依赖 nett-node。服务管理：Linux 使用 systemd（设置内存上限），macOS 使用 launchd，Synology DSM 使用开机任务（以后提供套件包），Home Assistant OS 使用加载项（ADR 0017）。

### 13.3 安装

**Hub（一次）**

```bash
curl -fsSL https://<项目主页>/install.sh | sudo sh -s -- hub --domain hub.example.com
```

脚本下载并校验发布签名，安装服务，然后在终端打印**一次性初始化链接**；在浏览器中打开它注册 passkey，并离线保存恢复密钥和备份密钥。初始化链接只能使用一次，防止他人抢先完成注册。Hub 也提供容器镜像。

**节点**：在控制台"添加节点"并勾选模块，复制生成的命令：

```bash
curl -fsSL https://hub.example.com/install.sh | sudo sh -s -- enroll <一次性 token>
```

- **安装脚本和二进制都由用户自己的 Hub 提供**：脚本中预置 Hub 的公钥；可执行文件用项目的发布签名验证（公钥编译在 `nett` 中，首次安装时可对照项目主页公布的指纹核对）；Hub 缓存经过签名的发布包，节点无需访问公共代码托管平台（在网络受限的地区更可靠）；
- token 一次性有效且很快过期；
- 不使用 `curl | sh` 时，可手动下载、校验签名后执行 `sudo nett enroll <token>`；
- macOS 也可以通过 Homebrew 安装后执行 `sudo nett enroll <token>`。

**手机**：无需安装 nett。控制台"添加设备"（passkey 确认）后导出标准 WireGuard 配置，用任意 WireGuard 客户端导入。

### 13.4 日常命令

| 命令 | 作用 |
|---|---|
| `nett status` | 本机状态：模块、Hub 连接、组网当前路径 |
| `nett doctor` | 自动诊断，给出通俗的说明和处理建议 |
| `nett upgrade` | 手动升级；默认由 Hub 经 `release` 分区推送，校验发布签名、拒绝降级后替换，失败自动回滚 |
| `nett leave` | 退出组网并卸载，通知 Hub 把本节点标记为已移除（降低权限，不需要签名） |
| `nett deny <模块>` | 设置本地硬性禁止（第 3 节），签名策略也无法突破 |
| `nett trust reset` | 恢复密钥也丢失时，重置本机的信任锚（需要 root） |
| `nett trust log` | 列出本机接受过的签名产物和撤销记录，不经过 Hub（design/auth.md 第 2 节） |
| `nett whois <地址>` | 按本机已验证的准入材料，查询一个组网地址属于哪个节点、设备或 Edge |
