## M1：组网

按顺序推进：先过原型关卡，再接入 Hub，最后铺开平台和功能。

- **原型关卡**（第一步，只在 Linux 上，用静态配置代替 Hub）：签名准入、UDP 中继与切换到新中继、双方都是 `dial-only` 时的切换与时间片汇合、漫游纠正、中继重启、MTU（大包 TCP）、TLS 回退、打洞（成功率与失败时的停顿时间），以及所选 WireGuard 实现的实际行为（索引冲突重试、删除再添加对端后的握手时间）；**性能基准**：在同一组机器上与原生 WireGuard、Tailscale 对比吞吐、延迟和 CPU 占用。切换时间和性能达到下面的验收标准后，再做其他平台、CONNECT 和智能入口（mesh.md 第 18 节）
- **组网离不开的基础**：
  - Hub 与 nett-node（原生运行）：入网、能力探测（WireGuard、TUN、包过滤、能否被外部连入）；node 经公网 HTTPS 连接 Hub，不依赖组网；node 把 `trust` 和 `mesh` 分区转交组网进程
  - 认证：passkey 登录、恢复密钥与备份密钥、API token、node 密钥与准入证明、信任锚；变更集最小版本与浏览器内 passkey 签名
  - 安装：Hub 安装脚本与一次性初始化，生成 Hub 前的反向代理配置（默认 Caddy，包括按 SNI 转交 nett-relay 的一段）；节点一键入网（安装脚本与签名发布包由 Hub 分发）；Homebrew（macOS）；Home Assistant 加载项仓库；发布工作流（CI 构建，单独的签名任务自动签名）与发布公钥作为构建参数；自动升级与回滚（项目发布签名、防降级）
  - 可用性：node 和组网进程在本地保存配置；Hub 备份（含身份私钥，加密后由其他节点拉取）与重建手册
- 组网进程独立于 nett-node 运行，TLS 传输适配单独以低权限运行（ADR 0013）；核心逻辑与平台无关，数据面按平台分后端，为 M3 的客户端预留（ADR 0018）
- 会话层：Linux 内核 WireGuard；DSM 和旧内核使用 Rust 用户态实现，运行在组网进程中；macOS 原生加入（用户态 WireGuard + utun；铺开前先实测与代理类 VPN 应用共存），需要访客真实 IP 的容器服务另用容器内成员；Home Assistant OS 加载项可做智能入口；成员准入验证（签名的成员表、网段、访问规则）
- 路径层：局域网直连、公网直连（IPv4、IPv6）、经单个中继；两端都在锥形 NAT 后或都有全局 IPv6 地址时打洞直连，失败回落到中继；持续测量、打分、防抖、快速切换；节点离线时自主切换
- 传输：UDP；TCP/TLS 443 兜底（由传输适配进程适配）
- nett-relay：单端口转发加密数据包、接收 TCP/TLS 传输、探测应答、HTTPS CONNECT 代理（入口节点上仅 HTTP/2）
- 局域网智能入口（subnet router + 按来源分类的源地址转换）；Edge 专用地址（`edge` 角色，Edge 是用户自己的反向代理）；宣告网段默认拒绝
- 节点身份与身份查询接口（`whois`）、节点主机名与别名（`hostnames`）、主机名解析、访问控制
- 手机：移动网关 + 直连家里的双路径；设备与凭据模型；导出标准 WireGuard 配置（配置文件和二维码），以及 Surge、mihomo、sing-box 的配置（两条出站放进自动回落的策略组）
- Web 控制台（原型关卡之后，与 Hub 一起开始）：
  - 先做签名和生成私钥的页面：初始化（注册 passkey，离线保存恢复密钥和备份密钥）、添加节点（浏览器生成入网密钥）、添加设备（浏览器生成设备私钥，导出配置和二维码）、变更的审批与签名
  - 再做查看与管理：节点、成员与设备、访问规则；每对节点的当前路径、传输方式、延迟、丢包，先用表格呈现，拓扑图放在 M1 后段、组网稳定之后
  - 中英双语
- OpenAPI（覆盖本阶段的资源）；`nett status`、`nett doctor`、`nett leave`、`nett whois`，命令行输出中英双语；排障手册（中英双语）
- 首批平台：Linux、Synology DSM、macOS（原生成员；容器内成员可选）、Home Assistant OS（加载项）
- 可用性：至少两个可用中继（位于不同主机）；`dial-only` 节点至少连接两个 `public` 节点

**验收**：

- 性能：千兆及以下的路径上，直连吞吐不低于同机原生 WireGuard 的 95%，延迟没有可测出的差异；直连和经中继两种路径上，吞吐不低于 Tailscale 的 95%；记录各自的 CPU 占用，以及 1 vCPU 中继的最大转发吞吐；
- Edge 回源全部经过组网（Edge 的配置由用户自己维护），需要真实 IP 的服务能识别访客地址；手机在外可直连家里观看视频，也可经移动网关访问其他节点；切换到"全部经网关"的备用配置后，仍能访问家里的服务；使用代理客户端配置时，直连家里不通会自动改走网关；
- Mac 笔记本换网络、休眠唤醒后自动恢复连接，能主动访问其他成员；与代理类 VPN 应用的增强模式同时开启时组网正常（或按说明配置后正常）；
- 人为制造丢包或断开当前路径：几秒内切换到其他路径，**进行中的 TCP 连接不中断**；切换到此前没有经手这条连接的中继，以及中继重启后，同样满足；大包传输不受影响；
- 两端都在锥形 NAT 后，或都有全局 IPv6 地址、只隔着路由器防火墙：打洞直连成功；失败时自动回落到中继，上层 TCP 连接不断；
- 停掉任一中继或节点：依赖它的路径自动绕开；
- 屏蔽 UDP：自动改用 TCP/TLS 443；
- 停止 Hub：组网、自动切换和手机接入照常工作；
- 停止 nett-node：组网照常测量和切换，DNS 照常应答；
- 用备用钥匙签发的版本替换主钥匙：节点装上之后拒绝旧主钥匙签的包；开发钥匙签的包，官方构建拒绝安装；
- Hub 下发一个没有准入材料的对端：所有成员都拒绝配置它；移除一个成员后，Hub 重发它原来的准入材料：所有成员都拒绝；一个很久以前入网的成员，新加入的成员能正常验证它；
- 按手册在另一台主机上从备份重建 Hub，所有 node 自动重新连接。使用的备份要落后于节点的状态（备份之后又批准过变更），恢复后不需要用户重新批准（protocol.md 第 6.4 节）；
- 在 1 vCPU / 1 GB 的机器上空闲 24 小时：nett-node、组网进程、传输适配进程、nett-relay 的内存各自满足资源预算；Hub ≤ 30–50 MB 且内存不上涨。

## M2：组网增强

- 多跳接力与自动寻路
- QUIC 传输、混淆包装、CONNECT 的 UDP 支持
- 对称型 NAT 的打洞；在 WireGuard 端口上探测，使尝试打洞不影响当前连接

**验收**（方向）：人为劣化单跳中继时，两段接力明显更优就自动改走多跳，连接不中断；只放行 UDP 443 的网络中自动改用 QUIC；按 WireGuard 特征丢包的环境中，混淆传输仍能连通；一端在对称型 NAT 后（另一端为锥形）时打洞直连成功；常驻进程仍满足资源预算。

## M3：客户端

- iOS、Android App：完整成员，在 Network Extension（iOS）、VpnService（Android）中运行用户态 WireGuard 和路径层
- Windows 成员：wireguard-nt 内核驱动，过滤使用 Windows 防火墙（WFP）
- 复用 M1 起与平台无关的组网核心，只新增各平台的数据面后端和 App 外壳（ADR 0018）；iOS 需要 Apple 开发者账号（付费）
