# 本地签名部署

- 状态：草案
- 阶段：M1，原型关卡之后、接入 Hub 之前（roadmap M1，ADR 0022）

## 1. 目标

用 nett 替换用户手工配置的 WireGuard 隧道，不等 Hub、nett-node 和控制台。典型的例子：VPS 上的 Edge 经隧道回源到家里 Mac 上的容器服务（ADR 0015、0016）。

签名、验证和组网的行为与接入 Hub 之后相同：用户签名，节点独立验证。Hub 本来只是签名产物的转发者（auth.md 第 2 节）；这里由用户自己的电脑上的签名工具生成产物，用户把文件拷到节点上。

## 2. 范围

| 包含 | 不包含 |
|---|---|
| 签名工具 `nett site`，运行在用户自己的电脑上：生成恢复密钥和信任锚清单，分配地址，签名节点策略、宣告网段和访问规则集，为每个节点生成期望状态文件 | Hub、nett-node、控制台、passkey、自动升级 |
| 正式构建的 `nett mesh --config`：读本地的期望状态文件，`SIGHUP` 时重新加载 | 设备凭据、移动网关、主机名与 DNS、CONNECT |
| 节点上生成密钥的 `nett mesh keys` | 原生 macOS 成员、DSM、Home Assistant OS |
| 访问控制（mesh.md 第 12 节）、Edge 专用地址（ADR 0015）、容器内成员作为它所在容器网络的智能入口（mesh.md 第 10 节、ADR 0016） | |
| 运行方式：Linux 上的 systemd 单元（`packaging/systemd/nett-mesh.service`）；容器内成员的容器镜像与 Compose 示例（`packaging/container/`） | |

候选路径、中继和传输与原型相同（mesh.md 第 5–9 节）。

## 3. 信任与密钥

| 密钥 | 在哪里生成 | 保存 |
|---|---|---|
| 恢复密钥（ECDSA P-256），唯一的信任锚 | `nett site init`，用户自己的电脑 | 站点目录中的私钥文件，权限 `0600`，只在签名时读取；另存一份离线备份 |
| 节点的组网私钥（X25519）与身份私钥（X25519） | `nett mesh keys`，节点本机 | 节点本机，权限 `0600`，不离开节点（硬性规则 10）；只把公钥交给签名工具 |
| 入网密钥（Ed25519，auth.md 第 8 节） | `nett site build`，每个节点一把 | 不保存：签出准入证明后即丢弃 |

- 信任锚清单（auth.md 第 11.1 节）只含恢复密钥，没有 passkey。控制台地址（`origin`）可以在 `nett site init --origin` 时写上；还不知道时为 `https://nett.invalid`，接入 Hub 时由恢复密钥签一次信任锚更新改成控制台的地址（auth.md 第 11.2 节）；
- 恢复密钥等同于控制台的恢复密钥：泄露等于交出全部控制权；丢失后不能再签发新的授权，只能重建信任锚、所有节点重新入网。建议站点目录放在加密卷上，私钥文件另存一份离线备份；
- 准入证明由入网私钥对节点 ID、身份公钥、组网公钥签名，节点策略写入入网公钥并由恢复密钥签名。产物格式与经 Hub 入网时相同，其他成员按同一条链验证（mesh.md 第 4.1 节）。

## 4. 站点描述与状态

用户维护一份站点描述（TOML），写节点、宣告的网段、候选路径和访问规则：

```toml
[mesh]
ipv4 = "100.88.0.0/16"

[[node]]
name = "edge-vps"
reachability = "public"
ipv4 = "203.0.113.10"
keys = "…"                        # 节点上 `nett mesh keys` 输出的一行公钥
roles = ["edge"]
edge = { containers = ["172.17.0.2/32"] }   # 怎样识别 Edge 发出的流量：Edge 容器的地址（ADR 0015）

[[node]]
name = "mac-app"
reachability = "dial-only"
keys = "…"
routes = ["172.30.0.10/32"]        # 容器网络的智能入口（ADR 0016）：宣告服务在容器网络中的固定地址

[[link]]
peers = ["edge-vps", "mac-app"]
candidates = ["direct"]

[[allow]]
from = ["edge-vps.edge"]           # 该节点的 Edge 专用地址
to = ["mac-app.routes"]            # 该节点宣告的网段
ports = ["8686/tcp"]
```

- 候选路径目前支持 `direct`（对端的公网 IPv4）、`direct6`（对端的公网 IPv6）和 `punch`（mesh.md 第 6.1 节）；经中继和 TLS 的候选在需要时再加；
- WireGuard 端口取 `[mesh]` 中的 `listen_port`（默认 `41820`）；节点上写 `listen_port` 时用它自己的端口，连向它的直连候选也用这个端口。同一台主机上有两个成员时各用一个端口，例如原生成员与容器内的成员：容器的 UDP 经端口转发出去时可能保留原端口，占用主机上的同一个端口；
- 签名工具在站点目录中保存状态：信任锚清单、已分配的组网地址和 Edge 专用地址（不回收，mesh.md 第 3 节），以及每份产物当前的版本与哈希；
- 内容变化时，产物的版本加一并重新签名；内容不变时沿用原来的签名，节点视为幂等（auth.md 第 10.2 节）；
- 选择器写节点名（它的组网地址）、`<节点>.edge`（它的 Edge 专用地址）或 `<节点>.routes`（它宣告的网段），在签名工具中展开，签名产物写的是展开后的地址和端口（mesh.md 第 12 节）；
- 有 `routes` 的节点在节点策略中带 `subnet_router` 角色，宣告的网段另签一份带版本号的产物（auth.md 第 10.5 节）；网段不能与组网网段或其他节点宣告的网段重叠；
- 移除节点、删除允许规则属于降低权限：工具生成撤销记录（auth.md 第 10.4 节），不需要签名，同样写进各节点的期望状态。

## 5. 分发与更新

- `nett site build` 为每个节点生成一份期望状态文件，格式与接入 Hub 后 nett-node 交给组网进程的 `mesh` 分区相同（protocol.md 第 6 节）。文件不含私钥，可以经不受信任的通道传递；
- 用户把文件拷到节点上，替换后向组网进程发 `SIGHUP`；
- 签名载荷的过期时间是生成后 30 天：节点首次接受自己的节点策略时检查它（auth.md 第 10.2 节），因此生成后 30 天内拷到节点上。生成时已签的节点策略离过期不到 7 天的，换一个新版本重签；
- 组网进程照常验证签名、版本和撤销记录。验证失败的部分不应用，已生效的状态保持不变，并记录事件（硬性规则 3–6）。

## 6. 访问控制、Edge 与容器内成员

按 mesh.md 第 12 节与 ADR 0015、0016 实现。本阶段的做法：

- **过滤**：Linux 上用 nftables，挂在 `prerouting`，优先级在 Docker 的目的地址转换之前，匹配从 `nett0` 进入的流量。先安装规则，再添加对端；规则更新失败时保持拒绝；
- **Edge**：`edge` 角色写明 Edge 所在容器的网段。从这些来源发往组网的流量，源地址换成 Edge 专用地址，这条转换在 Docker 的源地址伪装之前生效。本机输出和容器转发两个方向上，丢弃源地址为 Edge 专用地址、但不是来自 Edge 的数据包。这个网段里的每个容器都会被当作 Edge，因此只写 Edge 容器自己的地址，或只有 Edge 使用的容器网络；
- **宣告的网段**：其他成员把它加进这个节点对端的 `AllowedIPs`，并在组网接口上加路由；
- **容器内成员**：是它所在容器网络的智能入口（ADR 0016）。容器在网络中使用固定地址，在自己的网络命名空间中开启转发（Compose 的 `sysctls`），宣告服务的固定地址。只转发来自 Edge 专用地址、访问规则放行的连接，来源换成自己在出接口上的地址，也就是它在容器网络中的固定地址；需要真实 IP 的服务把这个地址配置为可信代理。其他来源的转发丢弃（智能入口为其他来源准备的"普通地址"，ADR 0015，留到接入局域网时实现）。容器以 `NET_ADMIN`、`NET_RAW` 运行；服务保留自己的网络，容器内成员重启不影响服务。

## 7. 替换已有的隧道

- **并行准备**：新的组网使用自己的端口和网段（`41820`、`100.88.0.0/16`），与旧隧道互不影响；先确认两端连通、访问规则生效，再切换；
- **切换**：服务固定在容器网络中的地址，可信代理改为容器内成员的地址，Edge 的上游改为服务的地址；
- **回滚**：Edge 的上游改回旧地址。旧隧道的配置一直保留到验证通过；
- 在用户的机器上执行之前，先列出命令和回滚方法，经用户确认（CLAUDE.md "隐私与操作边界"）。

## 8. 验证

实验 A 的场景 `nett-lab run access`（`crates/nett-lab/topologies/access.toml`，每次推送都在 CI 中运行）：一个运行 Edge 的成员（背后有一个"容器"，成员像 Docker 一样对它做源地址伪装）、一个在锥形 NAT 之后的容器内成员（背后有一个服务，宣告它的地址）、一个普通成员，访问规则只放行 Edge 访问这个服务的一个端口。通过标准：

- Edge 访问服务放行的端口能连上，服务看到的来源是容器内成员的地址；
- Edge 访问其他端口、Edge 所在成员自己和普通成员访问这个服务，都被拒绝；
- 一个成员伪造路由和 `AllowedIPs`、把包发往容器内成员背后没有宣告的地址，被容器内成员丢弃（模拟这个成员被攻破）；
- 没有规则放行的成员之间互相连不上，规则放行的能连上；隧道内探测不受访问规则影响；
- 在 Edge 所在的成员上以 Edge 专用地址为源发出的包，不出现在其他成员的组网接口上；
- 各成员的规则集都已生效，没有数据面失败。

## 9. 接入 Hub 时

接入 Hub 时，可以沿用这把恢复密钥、信任锚版本、已分配的地址和产物版本，让节点不必重新入网；也可以让节点重新入网。到时在 Hub 的设计中决定。本阶段保证地址不回收、版本只增不减，两种做法都可行。

## 10. 待定问题

| 问题 | 说明 |
|---|---|
| 恢复密钥的保护 | 文件权限之外，是否加口令加密，或放进硬件密钥（auth.md 第 14 节） |
| 宣告的网段与本机网络重叠 | 成员在组网接口上加路由之前，是否检查它与本机直连的网络是否重叠（重叠时本机发往那个网络的流量会被引进组网）；目前由签名工具只检查与组网网段、其他节点网段的重叠 |
