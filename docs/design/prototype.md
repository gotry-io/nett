# Prototype Gate

- Status: draft
- Phase: M1 step 1
- Related: [mesh.md](mesh.md) (sections 4-8, 18), [auth.md](auth.md) (sections 8, 10, 11), [roadmap](../roadmap.md) M1; ADR [0007](../adr/0007-own-mesh-wireguard-session-path-layer.md), [0011](../adr/0011-nett-relay.md), [0013](../adr/0013-mesh-and-transport-processes.md), [0014](../adr/0014-signed-mesh-membership.md), [0021](../adr/0021-tailscale-parity.md)

## 1. Goal

M1 first validates the riskiest parts of the mesh design on Linux; only after that does it connect the Hub and extend to other platforms and features. The gate answers these questions with measurements:

1. When connections drop, fluctuate, fall back and recover, is the experience no worse than Tailscale (ADR 0021);
2. When a path is switched by changing only a peer's endpoint, do in-progress TCP connections survive;
3. Does single-port relay forwarding by `mac1` and session index work with the actual behavior of kernel WireGuard: re-handshake, cookie, index collisions, old indexes after key rotation;
4. When both sides are `dial-only`, can the in-tunnel proposal and confirmation and the time-slot rendezvous restore the connection;
5. Can roaming correction suppress late and out-of-order packets;
6. Is probing on the WireGuard port reliable, does it affect throughput, and can hole punching avoid interrupting the current connection;
7. With the `nett0` MTU fixed at 1280, is it usable when the outer path MTU is smaller;
8. Throughput, latency and CPU usage compared with native WireGuard and Tailscale;
9. Admission verification: only peers with a complete signature chain are configured.

Each question gets a measured conclusion. Items that fail get a design change first (mesh.md etc.) before continuing.

## 2. Scope

**Included**

| Component | Part implemented in the gate |
|---|---|
| `nett-trust` | Signed payloads (RFC 8785 canonical JSON), trust anchor list; verification of recovery key signatures (ECDSA P-256) and WebAuthn assertions (ES256, EdDSA); admission proofs (Ed25519); identity revocations; versions only increase |
| `nett-mesh` | Platform-independent core: candidate paths, in-tunnel and out-of-tunnel measurement, extra probing on suspected failure, scoring, switching rules (mesh.md section 8.2), decider and endpoint correction, re-handshake when switching to a relay, proposal and confirmation and time-slot rotation when both sides are `dial-only`, mapped address and NAT type, hole punching. Linux kernel backend: configures the WireGuard interface, peers, addresses and routes through netlink; sends and receives probes on the WireGuard port (sending uses a raw socket, receiving copies only probe packets through nftables, mesh.md section 7.1) |
| `nett-relay` | Single-port UDP forwarding (mesh.md section 5.1), address binding rules (section 5.2), authenticated probe replies and mapped address echo, TLS (WebSocket) transport entry |
| `nett-transport` | Conversion between local loopback UDP and WebSocket/TLS (mesh.md section 5.3), including the standby connection kept with the TLS relay |
| `nett-lab` (new) | Lab tool used only for development and testing, not in the release package: generates lab keys and signed artifacts, generates each node's static configuration, builds lab topologies, deploys Tailscale in the same topology for comparison, injects faults, collects measurements |

**Not included**: Hub, nett-node, control protocol and Web; DNS; access rules and filtering; smart gateway and source-based address translation; Edge address; CONNECT; mobile gateway and devices; userspace WireGuard and platforms other than Linux; QUIC, multi-hop, hole punching when both ends are behind symmetric NAT; switch proposals relayed through the Hub (`PathSwitch`).

## 3. Which code is kept

What is written in the gate is the first version of the production code: `nett-trust`, `nett-mesh`, `nett-relay` and `nett-transport` continue to be used after the Hub is connected. Only two parts are written specifically for the gate:

- **Static configuration**: the mesh process's configuration source is abstracted as one interface. In the gate it is read from local files; after the Hub is connected, nett-node provides it through the local interface. Reading local files is provided only in builds with the `lab` feature enabled, and official builds do not contain it;
- **`nett-lab`**: it calls external commands such as `ip`, `tc`, `nft` and `iperf3` to build the lab network and run the comparison targets. It is not in the release package, and the rule that the mesh process does not execute external commands does not apply to it.

The static file's content is the same as the `trust` and `mesh` partitions of the desired state: trust anchor list, signed artifacts, admission proofs, revocations, candidate paths and relay assignments. The mesh process and nett-relay verify each item as usual and skip no check because the source is a local file.

The gate's test scenarios are kept as regression tests (section 7).

## 4. Static configuration

`nett-lab` reads a topology description and generates a configuration file for each node:

1. A lab recovery key (P-256) as the trust anchor. The trust anchor list contains only this recovery key, with `origin` set to `https://hub.example.com`;
2. Each node's node ID, mesh key pair and enrollment key pair (Ed25519). In the lab environment these keys are generated centrally by `nett-lab` and used only for experiments;
3. Each node's signed node policy (address, role, enrollment public key), signed by the lab recovery key in the signed payload format (auth.md sections 10.1, 10.3); the admission proof is signed by the enrollment private key (auth.md section 8);
4. Candidate paths and relay assignments, equivalent to the Hub's computed results, written directly in the topology description;
5. Counterexamples for admission tests: wrong signature, unknown trust anchor, missing admission proof, admission proof that does not match the mesh public key, revoked node ID, version lower than the one in effect.

An illustration of the topology description:

```toml
[[node]]
name = "a"
reachability = "dial-only"
behind = "nat-a"                 # the router it sits behind

[[node]]
name = "r1"
reachability = "public"
roles = ["relay"]

[[router]]
name = "nat-a"
nat = "cone"                     # cone | symmetric | ipv6-firewall

[[link]]
peers = ["a", "b"]
candidates = ["direct", "relay:r1", "relay:r2", "tls:r1"]
```

## 5. Lab environments

### 5.1 Lab A: single-machine network namespaces

- Each member, relay and router gets its own network namespace, connected with veth; the "public network" is a bridge;
- NAT is implemented with nftables in the router's namespace: cone (`masquerade`, port preserving, mapping independent of destination address), symmetric (`masquerade fully-random`), and IPv6 stateful firewall (inbound allows only established connections; IPv4 is symmetric NAT). Like a home router, the router's external interface drops connections newly initiated from outside and addressed to the router itself: dropped packets leave no record in the connection tracking table, otherwise the record left by the peer's earlier hole-punch packet conflicts with this side's subsequent address translation and the router has to switch to another port (measured: nett and Tailscale both fail to connect in that case);
- Link quality uses `tc netem` to set delay, loss, reordering and rate limits. Fault injection methods: 100% packet loss on a link, blocking UDP, lowering a router interface's MTU, restarting processes;
- **Comparison target Tailscale**: in the same topology, each member's namespace runs `tailscaled`, and another namespace attached to the "public network" runs Headscale and its built-in DERP server (the self-signed certificate is given only to `tailscaled`, with no connection to external services). Versions are fixed at Tailscale 1.104.5 (the version ADR 0021 is based on) and Headscale 0.29.7. nett and Tailscale run separately and do not occupy the network at the same time; the same faults are injected by `nett-lab` on the underlying network. Tailscale is compared in its default configuration; when the version used supports UDP relay (peer relay), another group is run with it enabled. Versions and configuration are recorded with the results;
- Run in CI: GitHub Actions Ubuntu runners support sudo and network namespaces and can load the `wireguard` kernel module; on development machines it runs in a Linux virtual machine;
- Record the kernel version (≥ 5.6).

### 5.2 Lab B: real machines

- **Performance**: two Linux hosts on the same LAN with a link of at least 1 Gbps;
- **Across the public internet**: at least two VPSes in different regions, one of them with 1 vCPU, used to measure the relay's maximum forwarding throughput;
- **Hole punching**: real home-broadband NAT, NAT-type VPS, networks with IPv6; the more combinations the better;
- **Comparison targets**: native WireGuard (same kernel, configured by hand with `wg`); Tailscale (self-hosted Headscale and DERP, no dependence on external accounts);
- Before running on the user's own machines, list the software to install, the commands and the rollback method, and run only after the user confirms (CLAUDE.md "Privacy and operational boundaries"). Arrangements for specific machines are not written in this document.

## 6. Scenarios and pass criteria

### 6.1 Measurement method

- **In-tunnel probe stream**: one sequence-numbered UDP packet every 100 ms. The **interruption time** is the longest period in which no packet is received;
- **Long-lived connection**: a TCP connection that keeps transferring data; check whether it is reset and record throughput;
- **Current path**: determined from the traffic on each link of the underlying network (read each link's received byte count every 20 ms). nett and Tailscale use the same method and do not depend on their own logs;
- **Recovery time**: from the moment the fault is removed until traffic returns to a better type of path (for example from relay back to direct): the link of the worse path stays idle for at least 200 ms from that moment;
- For interruption and recovery scenarios (items 1-3 and 8), nett and Tailscale are each repeated 20 times; for fluctuation scenarios (items 4-6 and 24), each runs for 5 minutes and is repeated 3 times (each run is itself a 5-minute long-term average).

**"No worse than Tailscale"** means: the p95 and maximum of interruption time and recovery time do not exceed Tailscale's, and a recovery time not exceeding 0.2 s also counts (during recovery, traffic keeps flowing over the worse path and only latency differs; during a disconnection Tailscale sends every packet over the direct path at the same time, and its fast runs are within 0.03 s); in time comparisons a difference of less than 10 ms counts as equal (jitter of the receiver's timestamps; a probe stream that loses one packet gains 100 ms, so this does not mask real differences); no flapping during fluctuation: leave the impaired path at most once and do not go back and forth between paths (ADR 0021: switch away more aggressively than Tailscale when packet loss is too high, with hysteresis between paths of the same type); throughput not below 95% of Tailscale's; median round-trip time not higher than Tailscale's, or the difference not exceeding the variation between repeated measurements of the same configuration. When two Tailscale configurations are compared, the better one is the reference. **In no scenario may nett's long-lived connection be reset.**

### 6.2 Scenarios compared with Tailscale

| # | Scenario | Method |
|---|---|---|
| 1 | Disconnection: direct path fails | A (`dial-only`) and B (`public`) are directly connected, with candidates through relays as well; 100% packet loss on the direct path |
| 2 | Disconnection: relay fails | While going through a relay, 100% packet loss on that relay's link; nett switches to another relay that has not yet handled this connection (re-handshake) |
| 3 | Disconnection: relay process restarts | Restart nett-relay on the current relay while traffic flows; the Tailscale group restarts DERP |
| 4 | Fluctuation: sustained packet loss | Add 5%, 15% and 30% random packet loss to the current path, each for 5 minutes |
| 5 | Fluctuation: delay jitter | Add ±20 ms and ±80 ms jitter to the current path; plus another group: the delays of two paths alternately improve, each for 5 minutes, with the delay added in the data direction (the segment from the sender to the relay or DERP it currently uses, so that both round-trip times increase by the delay only once); the pass criterion for the alternating group is following to the better path within 1 minute of each half |
| 6 | Fluctuation: intermittent disconnection | The current path is down for 2 s and up for 8 s, for 5 minutes |
| 7 | Fallback: all UDP blocked | Block all of A's UDP upstream of A (the NAT router it sits behind or the bridge port it attaches to). Not blocked on A itself: with a local block, sending fails immediately and some implementations reroute right away based on that, which does not capture the real situation of an upstream firewall silently dropping packets |
| 8 | Recovery: direct path recovers | Remove the fault after item 1 |
| 9 | Recovery: UDP recovers | Remove the block after item 7 |
| 10 | Hole punching: cone NAT at both ends | A and B each behind a cone NAT, currently going through a relay |
| 11 | Hole punching: IPv6 stateful firewall | A and B both have global IPv6 addresses, each behind a stateful firewall |
| 12 | Hole punching: one cone, one symmetric | A behind a cone NAT, B behind a symmetric NAT |
| 13 | Symmetric NAT at both ends | A and B both behind symmetric NAT |
| 24 | Fluctuation: congestion | B's uplink is limited to 2 Mbit/s with a queue of about 5 seconds (a rate-limited VPS, home broadband with very deep upload buffers); B continuously sends a long-lived connection and a probe stream to A through the tunnel for 5 minutes; one group through a relay and one direct, each repeated 3 times |

Pass criteria: every item is "no worse than Tailscale" (section 6.1). In addition: for items 10 and 11 nett connects in all 20 runs and the current connection is not interrupted during hole punching (the probe stream loses no packets: the longest gap is less than two normal intervals, that is 190 ms); the success rate of item 12 is not below Tailscale's; for item 13 nett does not attempt hole punching and the connection is unaffected; for item 24 nett does not switch or re-handshake (the path is not broken, it is only queuing).

## 7. Measurement and running

- `nett-lab` outputs one JSON per run: the moments faults are injected and removed, the traffic on each underlying link, the send and receive time of every packet of the in-tunnel probe stream, the transfer progress of the long-lived connection, and the derived metrics such as interruption time, recovery time and number of switches; for nett runs it also attaches the path switch events reported by the mesh process;
- On every push, CI runs the short scenarios (items 1-3, 7-11, 13, 14, 16-20, and the 60-second version of item 24) once each with nett as regression tests; the Tailscale comparison, the full repeat counts, the fluctuation scenarios (items 4-6 and 24 at 5 minutes each) and item 21 are run at gate acceptance by a manually triggered workflow (`.github/workflows/lab-baseline.yml`), with one parallel job per scenario;
- Raw data and information about specific machines stay outside the repository. Conclusions are written in section 9 of this document, and environments are described only generically, such as machine specifications, kernel version and network type.
