## 1. 目标

M1 先在 Linux 上验证组网设计中风险最大的部分，通过之后再接入 Hub、铺开其他平台和功能。关卡要用实测回答这些问题：

1. 断开、波动、回退、恢复时，体验是否不比 Tailscale 差（ADR 0021）；
2. 只修改对端的 endpoint 来切换路径时，进行中的 TCP 连接是否不断；
3. 单端口中继按 `mac1` 和会话索引转发，能否与内核 WireGuard 的实际行为配合：重新握手、cookie、索引冲突、密钥轮换后的旧索引；
4. 双方都是 `dial-only` 时，经隧道的提议与确认、按时间片汇合，能否恢复连接；
5. 漫游纠正能否压住迟到和乱序的包；
6. 在 WireGuard 端口上探测是否可靠、是否影响吞吐，打洞能否做到不中断当前连接；
7. `nett0` 的 MTU 固定为 1280，外层路径 MTU 较小时是否可用；
8. 与原生 WireGuard、Tailscale 相比的吞吐、延迟和 CPU 占用；
9. 准入验证：只配置签名链条完整的对端。

每个问题得到实测结论。不通过的项先修改设计（mesh.md 等），再继续。

## 2. 范围

**包含**

| 组件 | 关卡中实现的部分 |
|---|---|
| `nett-trust` | 签名载荷（RFC 8785 规范化 JSON）、信任锚清单；恢复密钥签名（ECDSA P-256）与 WebAuthn 断言（ES256、EdDSA）的验证；准入证明（Ed25519）；身份撤销记录；版本号只增不减 |
| `nett-mesh` | 与平台无关的核心：候选路径、隧道内与隧道外测量、疑似故障时的加探、评分、切换规则（mesh.md 第 8.2 节）、决定方与 endpoint 纠正、切换到中继时的重新握手、双方 `dial-only` 时的提议与确认和时间片轮换、映射地址与 NAT 类型、打洞。Linux 内核后端：经 netlink 配置 WireGuard 接口、对端、地址和路由；在 WireGuard 端口上收发探测（发送用原始套接字，接收经 nftables 只拷贝探测包，mesh.md 第 7.1 节） |

| `nett-transport` | 本机回环 UDP 与 WebSocket/TLS 之间的转换（mesh.md 第 5.3 节），包括与首选 TLS 中继保持的备用连接 |
| `nett-lab`（新增） | 实验工具，只用于开发和测试，不进发布包：生成实验用的钥匙和签名产物、生成各节点的静态配置、搭建实验拓扑、在同一拓扑中部署 Tailscale 作为对比、注入故障、采集测量结果 |

## 3. 哪些代码保留

关卡中写的是正式代码的第一版：`nett-trust`、`nett-mesh`、`nett-relay`、`nett-transport` 在接入 Hub 之后继续使用。只有两部分专为关卡而写：

- **静态配置**：组网进程的配置来源抽象为一个接口。关卡中从本地文件读取；接入 Hub 之后，由 nett-node 经本机接口提供。读取本地文件只在启用 `lab` 特性的构建中提供，官方构建不含；
- **`nett-lab`**：它会调用 `ip`、`tc`、`nft`、`iperf3` 等外部命令搭建实验网络、运行对比对象。它不进发布包，与组网进程"不执行外部命令"的规则无关。

静态文件的内容与期望状态的 `trust`、`mesh` 分区相同：信任锚清单、签名产物、准入证明、撤销记录、候选路径和中继分配。组网进程和 nett-relay 照常逐项验证，不因为来源是本地文件而跳过任何检查。

关卡中的测试场景保留为回归测试（第 7 节）。

## 4. 静态配置

`nett-lab` 读取一份拓扑描述，为每个节点生成一份配置文件：

1. 一把实验用的恢复密钥（P-256）作为信任锚。信任锚清单中只有这把恢复密钥，`origin` 为 `https://hub.example.com`；
2. 每个节点的节点 ID、组网密钥对、入网密钥对（Ed25519）。实验环境中这些钥匙由 `nett-lab` 集中生成，只用于实验；
3. 每个节点的签名节点策略（地址、角色、入网公钥），以签名载荷的格式由实验恢复密钥签名（auth.md 第 10.1、10.3 节）；准入证明由入网私钥签名（auth.md 第 8 节）；
4. 候选路径和中继分配，相当于 Hub 的计算结果，直接写在拓扑描述中；
5. 用于准入测试的反例：签名错误、信任锚不认识、缺少准入证明、准入证明与组网公钥不符、节点 ID 已被撤销、版本低于已生效的版本。

拓扑描述的示意：

```toml
[[node]]
name = "a"
reachability = "dial-only"
behind = "nat-a"                 # 所在的路由器

[[node]]
name = "r1"
reachability = "public"
roles = ["relay"]

[[router]]
name = "nat-a"
nat = "cone"                     # cone | symmetric | ipv6-firewall

[[link]]
peers = ["a", "b"]
candidates = ["direct", "relay:r1", "relay:r2", "tls:r1"]
```

## 5. 实验环境

### 5.1 实验 A：单机网络命名空间

- 每个成员、中继和路由器各占一个网络命名空间，用 veth 相连；"公网"是一个网桥；
- NAT 在路由器的命名空间中用 nftables 实现：锥形（`masquerade`，端口保持，映射与目的地址无关）、对称型（`masquerade random-fully`）、IPv6 有状态防火墙（入方向只放行已建立的连接）；
- 链路质量用 `tc netem` 设置延迟、丢包、乱序和限速。故障注入方式：链路 100% 丢包、拦截 UDP、降低路由器接口的 MTU、重启进程；
- **对比对象 Tailscale**：在同一拓扑中，每个成员的命名空间运行 `tailscaled`，另一个接在"公网"上的命名空间运行 Headscale 和它内置的 DERP 服务器（自签证书只交给 `tailscaled`，不连接外部服务）。版本固定为 Tailscale 1.104.5（ADR 0021 依据的版本）和 Headscale 0.29.7。nett 和 Tailscale 分开运行，不同时占用网络，同样的故障由 `nett-lab` 在底层网络上注入。Tailscale 对比其默认配置；所用版本支持 UDP 中继（peer relay）时，开启它再跑一组。版本和配置随结果一起记录；
- 在 CI 中运行：GitHub Actions 的 Ubuntu 运行器支持 sudo 和网络命名空间，能加载 `wireguard` 内核模块；在开发机上用 Linux 虚拟机运行；
- 记录内核版本（≥ 5.6）。

### 5.2 实验 B：真实机器

- **性能**：两台位于同一局域网、链路不低于 1 Gbps 的 Linux 主机；
- **跨公网**：至少两台位于不同地域的 VPS，其中一台为 1 vCPU，用来测中继的最大转发吞吐；
- **打洞**：真实的家宽 NAT、NAT 型 VPS、有 IPv6 的网络，组合越多越好；
- **对比对象**：原生 WireGuard（同一内核，用 `wg` 手工配置）；Tailscale（自建 Headscale 和 DERP，不依赖外部账号）；
- 在用户自己的机器上运行之前，先列出要安装的软件、命令和回滚方法，经用户确认后再执行（CLAUDE.md "隐私与操作边界"）。具体机器的安排不写进本文。

## 6. 场景与通过标准

### 6.1 测量方法

- **隧道内探测流**：每 100 毫秒一个、带序号的 UDP 包。**中断时间**是其中最长的一段没有收到包的时间；
- **长连接**：一条持续传输数据的 TCP 连接，检查它是否被重置，并记录吞吐；
- **当前路径**：从底层网络上各条链路的流量判断当前走哪条路径（每 20 毫秒读一次各链路的接收字节数）。nett 和 Tailscale 用同一种方法，不依赖各自的日志；
- **恢复时间**：从故障解除，到流量回到更优类型的路径上（例如从中继回到直连）：较差路径的链路从这一刻起持续空闲至少 200 毫秒；
- 中断与恢复类的场景（第 1–3、8 项）nett 和 Tailscale 各重复 20 次；波动类（第 4–6 项）每种持续 5 分钟，各重复 3 次（每次本身就是 5 分钟的长时间平均）。

**"不比 Tailscale 差"** 指：中断时间和恢复时间的 p95 与最大值不超过 Tailscale，恢复时间不超过 0.2 秒也算（恢复期间流量照常经较差的路径，差别只是延迟；Tailscale 断开期间每个包同时经直连发送，快的那些次在 0.03 秒以内）；波动期间不来回切换：离开受损的路径至多一次，不在路径之间往返（ADR 0021：丢包过高时比 Tailscale 更积极地切走，同类路径之间防抖）；吞吐不低于 Tailscale 的 95%；往返时间的中位数不高于 Tailscale，或差距不超过同一配置重复测量之间的波动。对比了两组 Tailscale 配置时，以较好的一组为准。**任何场景中 nett 的长连接都不能被重置。**

### 6.2 与 Tailscale 对比的场景

| # | 场景 | 方法 |
|---|---|---|
| 1 | 断开：直连失效 | A（`dial-only`）与 B（`public`）直连，另有经中继的候选；直连 100% 丢包 |
| 2 | 断开：中继失效 | 经中继时让这个中继的链路 100% 丢包，nett 切到尚未经手这条连接的另一个中继（重新握手） |
| 3 | 断开：中继进程重启 | 有流量时重启当前中继上的 nett-relay；Tailscale 一组重启 DERP |
| 4 | 波动：持续丢包 | 当前路径分别加 5%、15%、30% 的随机丢包，各持续 5 分钟 |
| 5 | 波动：延迟抖动 | 当前路径加 ±20 毫秒、±80 毫秒的抖动；另做一组：两条路径的延迟交替变好，各持续 5 分钟，延迟加在数据方向上（发送方到它当前所用的中继或 DERP 那一段，两者的往返时间都只增加一次延迟）；交替一组的通过标准是每个半程 1 分钟内跟随到更优的路径 |
| 6 | 波动：间歇断开 | 当前路径断 2 秒、通 8 秒，持续 5 分钟 |
| 7 | 回退：UDP 全部被拦 | 拦截 A 的全部出站 UDP |
| 8 | 恢复：直连恢复 | 第 1 项之后解除故障 |
| 9 | 恢复：UDP 恢复 | 第 7 项之后解除拦截 |
| 10 | 打洞：两端锥形 NAT | A、B 分别在锥形 NAT 后，当前经中继 |
| 11 | 打洞：IPv6 有状态防火墙 | A、B 都有全局 IPv6 地址，各在一个有状态防火墙后 |
| 12 | 打洞：一端锥形、一端对称型 | A 在锥形 NAT 后，B 在对称型 NAT 后 |
| 13 | 两端对称型 NAT | A、B 都在对称型 NAT 后 |

通过标准：每一项都"不比 Tailscale 差"（第 6.1 节）。另外：第 10、11 项 nett 20 次全部打通，打洞期间当前连接的中断时间不超过探测流的正常间隔（即不中断）；第 12 项的成功率不低于 Tailscale；第 13 项 nett 不尝试打洞，连接不受影响。

### 6.3 只对 nett 的场景

这些场景 Tailscale 没有对应的做法，设明确的标准。

| # | 场景 | 方法 | 通过标准 |
|---|---|---|---|
| 14 | 准入验证 | 配置中同时有合法的对端和第 4 节的每一种反例 | 合法的对端被配置；每一种反例都不被配置，并记录事件 |
| 15 | 漫游纠正 | 切换到中继之后，旧的直连路径每分钟送来一串延迟 3 秒、乱序的包（实际网络中，切换时在途的包只会迟到一次），持续 10 分钟 | 决定方的 endpoint 每次被改回旧路径后，1.5 秒内纠正；长连接不断；偏离的总时长记录，不设门槛（内核 WireGuard 每收到一个迟到的包都会改走 endpoint，总时长约等于一串迟到包的分布时长，不由纠正速度决定） |
| 16 | 双方 `dial-only`，当前路径可用 | A、B 都是 `dial-only`，经 R1；让 R2 更优，经隧道提议与确认后两端一起切 | 中断 ≤ 1 秒；长连接不断 |
| 17 | 双方 `dial-only`，当前路径断开、没有 Hub | 经 R1 时让 R1 失效，靠时间片汇合；Tailscale 一组同时停掉 Headscale 和当前 DERP，结果只记录 | 双方时钟误差 ≤ 2 秒时，20 次中至少 18 次在 45 秒（三个时间片）内恢复；误差 > 2 秒时改用随机间隔重试，记录恢复时间的分布 |
| 18 | 在 WireGuard 端口上探测 | IPv4、IPv6 各一组；主机上另有连接跟踪和 NAT 规则（例如 Docker）时再跑一组；同时向 WireGuard 端口发送未认证的探测 | 探测收发正常；WireGuard 流量的吞吐与不开探测时相比没有可测出的差异；未认证的探测得不到任何响应 |
| 19 | MTU | 长连接传输 1 GiB 并校验内容；外层路径 MTU 分别为 1500、1360、1300，IPv4 与 IPv6 各一组 | 1500 和 1360：传输完整，外层没有分片；IPv4 的 1300：靠分片传输完整；IPv6 的 1300：记录结果，不通时在 mesh.md 第 4 节写明限制和处理办法 |
| 20 | WireGuard 的实际行为 | (a) 删除再添加对端后，从第一个包到握手完成的时间；(b) 中继在测试模式下按索引冲突丢弃一次握手，测 WireGuard 的重试时间；(c) 向节点灌入大量握手发起，使它进入负载状态，确认经中继的 cookie 应答送达、握手最终完成；(d) 经中继连续运行 30 分钟，跨过多次密钥轮换 | (c)(d) 通过：握手完成，中继索引表的大小保持稳定，流量不断；(a)(b) 记录数据，用来修正 mesh.md 中的估计 |
| 21 | 资源占用 | 每个场景结束后静置 10 分钟，测组网进程、传输适配进程、nett-relay 的 RSS 和 PSS | 记录。超过 5 MB 时，进入下一阶段之前查明原因并给出处理办法 |

## 7. 测量与运行

- `nett-lab` 为每次运行输出一份 JSON：故障注入和解除的时刻、底层各链路的流量、隧道内探测流每个包的收发时间、长连接的传输进度，以及据此算出的中断时间、恢复时间、切换次数等指标；nett 一组还附上组网进程报告的路径切换事件；
- CI 中每次推送都把短场景（第 1–3、7–14、16、18–20 项）各跑一次 nett，作为回归测试；Tailscale 对比、完整的重复次数、波动类场景和第 21 项，在关卡验收时由手动触发的工作流（`.github/workflows/lab-baseline.yml`）运行，每个场景一个并行任务；
- 原始数据和具体机器的信息放在 `private/`，不进仓库。结论写进本文第 9 节，环境只写机器规格、内核版本和网络类型这类通用描述。
