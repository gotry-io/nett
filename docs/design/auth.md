## 2. 信任模型

```
用户的 passkey（及恢复密钥）  ← 最高信任锚，私钥只在用户设备上
   │ 签名
   ▼
信任锚清单（passkey 公钥 + 恢复密钥公钥）──► 写入每个节点
   │                                         │
   │ 签名                                     │ 节点用它独立验证
   ▼                                         ▼
变更批准、节点策略、组网准入材料 ── Hub 转发 ──► 节点

项目的发布签名密钥 ──► 公钥编译进 nett ──► 节点验证发布包（第 12.3 节）
```

| 主体 | 持有的密钥 | 被谁信任 | 被攻破的后果 |
|---|---|---|---|
| 用户 | passkey 私钥（设备内）、恢复密钥与备份私钥（离线保存） | Hub、所有节点 | 全部控制权 |
| Hub | Hub 身份密钥（X25519，用于 Noise）、Hub 主密钥 | 节点（入网时固定其公钥） | 能观测，能执行低风险操作和经过确认的中风险操作（部署受部署档位限制）；**不能**提升任何节点的权限，不能加入组网成员或放宽访问，读不到机密 |
| 节点 | 节点身份密钥（X25519，用于 Noise）、组网私钥 | Hub、其他节点（凭准入材料） | 影响该节点本身；具有 `gateway` 角色的节点还能以经它接入的设备的地址发出流量 |
| nett-relay | 不持有组网私钥和身份密钥 | — | 只能转发或丢弃密文；CONNECT 代理能看到经它访问的目标和未加密的内容 |
| 项目 | 发布签名密钥 | 所有节点 | 能发布恶意的新版本；不能让节点降级 |

原则：**Hub 是中间人，而不是信任根**。所有提升权限的操作，最终都要由节点用用户的公钥验证。

**控制台页面的信任边界**：控制台页面由 Hub 提供（ADR 0005）。签名载荷由页面计算，再交给 passkey 签名，而 passkey 无法向用户显示它签的是什么。被攻破的 Hub 可以让页面显示一项操作，实际请求签名另一项。浏览器生成入网私钥、设备私钥，以及加密机密时使用的节点公钥，也都依赖这份页面。因此，"Hub 被攻破不能越权"的准确含义是：**在用户没有在被攻破的控制台上完成签名之前**，Hub 不能越权。缓解措施：

- 节点保存它接受过的每一份签名产物，`nett trust log` 在本机列出（时间、种类、内容摘要），不经过 Hub，用户可以事后核对；
- 浏览器加密机密前，按准入材料验证目标节点的公钥，防止只篡改了数据库的情况；
- 独立于 Hub 的批准工具（在用户自己的电脑上显示载荷、用硬件密钥签名）列为以后的增强（第 15 节）。

## 3. 身份与凭据

| 身份 | 凭据 | 用途 | 记录到 `events` 的 `actor.kind` |
|---|---|---|---|
| 用户 | passkey；恢复密钥 | 控制台登录、批准与签名 | `owner` |
| 会话 | 会话 Cookie | 浏览器访问 API | `owner` |
| API token | Bearer token | 脚本、AI、静态集成 | `api_token` / `ai`（按 token 类型） |
| node | X25519 身份密钥 | node ↔ Hub 通信 | `node` |
| 入网 | 一次性的入网签名密钥（Ed25519，浏览器生成） | 证明节点获得了用户授权（第 8 节） | `node` |
| CI | OIDC 短期令牌 | 触发部署 | `ci` |
| 设备 | 设备凭据：WireGuard 密钥，或 CONNECT 凭据 | 组网接入、CONNECT 代理 | — |
| 心跳 | URL 中的独立密钥 | 上报心跳 | `system` |
| Hub 自身 | — | 自动执行、回滚、告警 | `system` |

## 4. 初始化与恢复

### 4.1 初始化

1. 安装 Hub 后，终端打印一次性**初始化链接**：包含 256 位随机密钥，1 小时内有效，只能使用一次；
2. 打开链接，注册第一个 passkey；
3. 浏览器生成**恢复密钥**（一对 P-256 签名密钥）和**备份密钥**（一对 X25519 密钥，用于加密 Hub 备份，见第 13 节），将两个私钥以文本形式显示一次，并提供下载，提示离线保存；Hub 只保存两个公钥；
4. 建议立即注册第二个 passkey（例如另一台设备或硬件密钥）；
5. 初始化完成后，初始化链接失效，再次初始化需要在 Hub 主机上执行命令重置。

### 4.2 恢复

| 情形 | 处理 |
|---|---|
| 丢失一个 passkey，仍有其他 passkey | 用其他 passkey 登录，删除丢失的 passkey（信任锚更新，需签名） |
| 丢失全部 passkey | 用恢复密钥登录控制台，注册新的 passkey；信任锚更新由恢复密钥签名 |
| 恢复密钥也丢失 | 无法在线恢复；需要在 Hub 主机上重置信任锚，并在每个节点上执行 `nett trust reset`（需要节点 root 权限） |

恢复密钥既能登录，也能签名信任锚更新，权限等同于 passkey，必须离线保存。**使用恢复密钥时，签名在浏览器本地完成，私钥不发送给 Hub**：登录时浏览器对 Hub 给出的挑战签名，签名信任锚更新时对签名载荷的哈希签名。

**呈现形式**：私钥以 `nett-recovery-` 开头，后接 Bech32m 编码的数据部分，按 4 个字符一组、以连字符分隔显示，例如 `nett-recovery-qpzr-y9x8-gf2t-…`。校验和按 Bech32m 规则、以 `nett-recovery` 作为前缀计算；显示时省略 Bech32 规定的分隔符 `1`，解析时自动补回。输入时忽略连字符、空格和大小写，校验和可以发现绝大多数抄写错误。备份私钥使用相同的格式，前缀为 `nett-backup-`。

## 5. 登录与会话

- **控制台只使用一个地址**：passkey 绑定注册时的域名（RP ID），在其他域名下无法使用；Hub 的备用入口只用于 node 连接（node 依靠 Hub 公钥认证，不涉及 passkey），不提供控制台；
- 登录：WebAuthn 认证，要求用户验证（UV）；
- 会话 Cookie：`__Host-nett_session`，`HttpOnly`、`Secure`、`SameSite=Strict`；空闲 12 小时过期，最长 7 天；
- **二次验证**：创建带写权限的 API token、修改通知渠道凭据等，要求 5 分钟内完成过一次 passkey 验证；
- CSRF：`SameSite=Strict` 之外，所有写请求校验 `Origin` 头；
- 会话可以在控制台查看和吊销。

## 6. API token

### 6.1 格式

```
nett_tok_<26 位 ID>_<43 位随机密钥>
```

- 固定前缀便于代码托管平台的密钥扫描识别；
- 随机密钥为 256 位；服务端只保存其 SHA-256 哈希，比较使用常量时间算法；
- 明文只在创建时显示一次。

### 6.2 属性

| 属性 | 说明 |
|---|---|
| `kind` | `script` / `ai`：决定活动记录中的操作方类型。**`ai` 类型 token 的一切写入**（包括低风险的直接修改）**都经过变更集，由用户批准** |
| `scopes` | 权限范围（第 7 节） |
| `expires_at` | 必填，最长 1 年 |
| `allowed_sources` | 可选，允许的来源地址范围（来源的判断方式见第 13 节） |

创建带写权限的 token 需要二次验证。

## 7. 权限范围

格式：`<资源>:<操作>[:<目标名称>]`。

| 权限范围 | 允许 |
|---|---|
| `read` | 读取所有资源（不含敏感字段） |
| `<资源>:read` | 读取某类资源，例如 `nodes:read`、`events:read`、`metrics:read` |
| `<资源>:write` | 低风险的直接修改，例如 `alerts:write`（确认、静默告警）、`nodes:write`（改名称、标签） |
| `<资源>:propose` | 提议该类资源的中、高风险变更，例如 `routes:propose`、`links:propose`、`access-rules:propose`、`devices:propose`、`nodes:propose` |
| `changes:propose` | 创建变更集；同时需要对应动作要求的权限范围 |
| `stacks:deploy[:<stack>]` | 提议部署（可限定某个 stack） |
| `services:operate[:<service>]` | 提议重启、停止、启动服务 |
| `heartbeat-checks:ping` | 仅用于心跳（通常直接使用 ping URL） |

每个动作类型所需的权限范围列在动作目录中（changes.md 第 9 节）。

规则：

- **token 不能批准变更集**；批准只能由用户在会话中完成，高风险时必须携带 passkey 签名；
- 中风险变更可以由自动执行策略放行（见 `changes.md` 第 5 节），而不是由 token 自己批准；`ai` 类型的 token 不适用自动执行策略；
- 用户会话拥有全部权限范围，但高风险操作仍需签名；
- 涉及身份与信任的操作（passkey、恢复密钥、API token 管理、自动执行策略、CI 信任规则）只能通过用户会话完成。

## 8. node 入网与连接

### 8.1 入网 token

```
nett_enr_<编码内容>
```

创建 token 时，Hub 先分配节点 ID 和组网地址（以及开启 ingress 模块时的 Edge 专用地址），**浏览器**生成一对一次性的入网签名密钥（Ed25519）。编码内容包含：

| 字段 | 作用 |
|---|---|
| Hub 地址 | 入网时连接的地址 |
| 节点 ID | 创建 token 时分配，写入初始节点策略和准入证明 |
| Hub 身份公钥（32 字节） | Noise IK 握手需要完整公钥；同时防止连接到冒充的 Hub |
| 信任锚清单指纹（128 位） | 防止 Hub 在入网时下发伪造的信任锚 |
| 入网私钥 | 证明持有者获得了用户授权；Hub 从未见过它 |

- token 由用户在控制台创建，默认 30 分钟内有效（创建时可调整，最长 24 小时），只能使用一次；
- 创建时勾选的初始模块，连同节点 ID、组网地址和入网公钥，形成一份**初始节点策略**。模块的风险等级：metrics 为低，mesh、deploy、ingress 为高；包含高风险模块时，初始策略需要 passkey 签名。不需要签名时，入网公钥由 Hub 保存。

### 8.2 入网流程

```
node                                              Hub
 │ 生成节点身份密钥（X25519）和组网密钥，私钥只存本机
 │ ── Noise IK 握手（使用 token 中的 Hub 公钥）──────►│
 │ ── Hello：节点 ID + 准入证明 + 能力信息 ──────────►│ 用入网公钥验证准入证明；
 │    准入证明 = 入网私钥对                            │ 检查 token 未使用、未过期
 │    { 节点 ID, 身份公钥, 组网公钥 } 的签名          │
 │ ◄── 信任锚清单 + 初始节点策略（含签名）────────────│
 │ 校验信任锚清单的指纹与 token 中一致
 │ 用信任锚验证初始节点策略的签名，核对其中的节点 ID
 │ 丢弃入网私钥；保存身份、Hub 公钥、信任锚、策略 → 应用 → 上报
```

签名策略加上准入证明，就是该节点的**准入材料**：Hub 把它分发给其他成员，成员据此独立验证这个节点的组网公钥（ADR 0014、mesh.md 第 4.1 节）。

### 8.3 日常连接

- node 主动建立 WebSocket 连接；
- **在 WebSocket 内层使用 Noise 协议（IK 模式）完成双向认证并建立端到端加密通道**：node 和 Hub 各自用身份密钥证明身份（细节见 [protocol.md](protocol.md)）。这样即使 TLS 由 Edge 终止，Edge 也无法读取或篡改 node 与 Hub 之间的消息；
- Hub 公钥在入网时固定；Hub 身份密钥更换时，新公钥通过以旧密钥建立的已认证通道下发，节点确认后切换。更换后立即生成一次备份：更早的备份中是旧密钥，用它恢复的 Hub 无法与节点握手（protocol.md 第 6.4 节）；
- 吊销节点：Hub 拒绝该节点的连接，并从组网拓扑中移除其公钥；
- **节点自行退出**（`nett leave`）：节点发送 `Leave` 消息并删除本地身份，Hub 把节点标记为 `removed`。这属于降低权限，不需要签名。

## 9. CI 认证

- 使用 OIDC：Hub 验证 CI 平台签发的短期 JWT（如 GitHub Actions），通过 JWKS 获取公钥并缓存；
- 用户配置信任规则（`ci-trust-rules` 资源）：签发者、受众、仓库、分支或环境 → 映射到权限范围（例如某仓库 `main` 分支 → `stacks:deploy:web` + `changes:propose`）；
- 不保存任何长期密钥；活动记录包含仓库和运行编号。

## 10. 设备凭据

| 类型 | 内容 | 用途 |
|---|---|---|
| `wireguard` | WireGuard 密钥对 | 标准 WireGuard 客户端接入组网 |
| `connect` | CONNECT 代理的 token | UDP 受限时经 nett-relay 的 CONNECT 代理访问内网服务 |

- WireGuard 私钥**只在浏览器中生成**（WebCrypto X25519；浏览器不支持时使用页面内置的实现），Hub 只保存公钥，从不经手私钥；
- **完整配置（含私钥）只在创建时生成一次**：浏览器生成配置文件和二维码，供下载或扫码，之后无法再次导出。配置丢失时新建一份凭据，并吊销旧的；
- 新增设备（`device.add`）和给已有设备新增凭据（`device_credential.create`）都是高风险操作，需要签名；签名产物绑定凭据的公钥（或 token 哈希）和组网地址，由网关、智能入口和 nett-relay 独立验证；
- 创建凭据记录到活动事件；吊销后立即从移动网关、直连入口和 nett-relay 移除。

## 11. 签名格式

### 11.1 签名载荷

签名的对象是一份规范化的 JSON（RFC 8785），称为**签名载荷**：

```json
{
  "v": 1,
  "kind": "change_approval",
  "change_id": "chg_…",
  "plan_hash": "sha256:…",
  "artifacts": [
    {
      "kind": "node_policy",
      "node_id": "node_…",
      "policy_version": 5,
      "modules": ["metrics", "mesh", "deploy"]
    }
  ],
  "expires_at": "…"
}
```

`kind` 的取值：`change_approval`（变更批准）、`enrollment_policy`（入网 token 的初始策略）、`trust_update`（信任锚更新）。

`artifacts` 是需要下发给节点、由节点独立验证的产物：

| 产物 `kind` | 内容 | 验证方 |
|---|---|---|
| `node_policy` | 节点 ID、版本、模块、角色（relay、gateway、智能入口）、组网地址与 Edge 专用地址、入网公钥 | 该节点；组网成员（准入） |
| `device_credential` | 设备 ID、凭据 ID、凭据类型、公钥或 token 哈希、组网地址 | 移动网关、智能入口、nett-relay |
| `advertised_routes` | 节点 ID、网段列表、版本 | 组网成员 |
| `access_rule_set` | 整份访问规则，写的是**选择器展开后的结果**（成员 ID、地址、端口），不是标签；版本 | 组网成员、nett-relay（CONNECT） |
| `deploy_profile` | 节点 ID、允许的部署特权、版本（changes.md 第 7.1 节） | 该节点 |
| `stack_spec` | 节点 ID、stack ID、除各服务镜像版本外的完整 Compose 定义、机密密文的哈希、版本（第 13 节） | 该节点 |
| `release_override` | 节点 ID、允许安装的指定版本（用于降级） | 该节点 |

变更集签名覆盖的内容就是这份载荷，`plan_hash` 已经包含了各步骤，changes.md 引用本节，不另行定义。

### 11.2 与 WebAuthn 的结合

- 浏览器以 `challenge = SHA-256(签名载荷)` 发起 WebAuthn 认证；
- 得到的认证结果（`authenticatorData`、`clientDataJSON`、`signature`）与签名载荷一起保存和下发；
- 验证方（Hub 和节点）检查：
  1. `clientDataJSON.type` 为 `webauthn.get`；
  2. `clientDataJSON.challenge` 等于签名载荷的哈希；
  3. `origin` 与信任锚清单中记录的控制台地址一致；
  4. `authenticatorData` 中的 RP ID 哈希一致，且用户在场（UP）、用户验证（UV）标志均已设置；
  5. 签名能用信任锚中的某个公钥验证；
  6. **过期时间约束的是批准**：Hub 只在载荷过期前执行变更集；直接改变某个节点自身权限的产物（该节点自己的 `node_policy`、`deploy_profile`、`stack_spec`、`release_override`），该节点首次接受时检查载荷未过期。描述组网成员和访问范围的产物（其他成员的准入材料、`device_credential`、`advertised_routes`、`access_rule_set`）会在批准很久之后才分发给新加入的成员、新的网关或重装的节点，验证方不检查过期时间；
  7. 带版本号的产物，版本号大于当前已生效的版本，也大于撤销记录中的版本（第 11.4 节）。与当前已生效版本完全相同的产物（例如重连后 Hub 重发的完整快照）视为幂等，直接确认，不改变已经生效的收窄。
- 允许的算法：ES256、EdDSA；
- 同步型 passkey 的签名计数器不可靠，不作为校验条件。

### 11.3 恢复密钥签名

恢复密钥直接对签名载荷的哈希做 ECDSA P-256 签名，不经过 WebAuthn，签名在浏览器本地完成。节点按相同的载荷格式验证。

### 11.4 撤销与首次同步

- 移除成员、吊销设备凭据、撤销网段、收窄访问规则、降低部署档位都不需要签名。Hub 下发时附带**撤销记录**：对象（节点、凭据、网段宣告、规则集、部署档位）和被撤销时的版本；
- 节点永久保存撤销记录（每条几十字节），此后只接受版本更高的签名产物。收窄后的状态作为本地覆盖保存：重发同一版本的签名产物不会解除它，只有版本更高的签名产物才会取代它；
- 新成员入网时，Hub 下发完整的撤销记录和当前的签名产物，作为首次同步的基准；
- 局限：撤销只在收到撤销记录的成员上生效，离线的成员重新连接后才收到。被攻破的 Hub 可以对从未收到某条撤销记录的成员隐瞒它。

## 12. 信任锚

### 12.1 信任锚清单

```json
{
  "v": 1,
  "version": 3,
  "rp_id": "hub.example.com",
  "origin": "https://hub.example.com",
  "passkeys": [ { "id": "pk_…", "alg": "ES256", "public_key": "…" } ],
  "recovery_key": { "alg": "ES256", "public_key": "…" }
}
```

### 12.2 更新

- 新增或删除 passkey、更换恢复密钥，都是信任锚更新：生成新版本的清单，以 `trust_update` 签名载荷，由**当前清单中**的某个 passkey 或恢复密钥签名；
- 节点只接受版本更高、且由当前信任锚签名的更新；
- 不允许删除最后一个 passkey；
- 控制台地址（`origin`）变化也是信任锚更新；由于 passkey 绑定域名，迁移到新域名后需要重新注册 passkey，因此该更新由恢复密钥签名，新 passkey 在新地址注册后再加入信任锚。

### 12.3 发布签名

发布包的信任锚独立于用户的信任锚，也独立于 Hub（ADR 0012）：

- 发布签名密钥属于项目，公钥编译进 `nett` 可执行文件；节点用它验证每一个发布包；
- 安装脚本由 Hub 提供，不能充当独立的信任锚；首次安装时，用户可以对照项目主页公布的指纹核对可执行文件；
- 节点只自动接受版本号更高的发布包；回滚只能回到本机上一次安装过的版本；安装其他更低的版本，需要 `release_override` 产物（passkey 签名）；
- 升级只有一条通路：期望状态的 `release` 分区（protocol.md 第 6 节）。满足上面规则的升级属于低风险，可以由 Hub 自动推送。

## 13. 防护措施

| 项 | 措施 |
|---|---|
| 暴力尝试 | 登录、入网、心跳、token 认证接口按来源限流；连续失败后临时锁定 |
| 真实来源 | Hub 位于 Edge 之后，只信任 Edge 地址（本机或 Edge 容器的地址）发来的 `X-Forwarded-For`，用于限流和 `allowed_sources`（ADR 0015） |
| 密钥存储 | Hub 身份私钥和 Hub 主密钥存放在 Hub 数据目录，文件权限 `0600`；恢复密钥和备份密钥的公钥存入数据库；通知渠道凭据用 Hub 主密钥加密后存入数据库 |
| 机密 | stack 的敏感环境变量、签发证书用的 DNS 凭据：用户在浏览器中输入，直接用目标节点的公钥加密（sealed box），Hub 只保存密文。**机密绑定到签名的 stack 定义**（`stack_spec`）：节点只把机密交给与签名定义一致的容器；带机密的 stack，除镜像版本（标签或摘要，镜像仓库不变）以外的任何改动都是高风险操作（changes.md 第 9 节），否则 Hub 可以换掉镜像或启动命令来取走机密。DNS 凭据只交给 Edge。节点重新入网后需要重新录入 |
| 签名审计 | 节点保存接受过的签名产物和撤销记录，`nett trust log` 在本机列出，不经过 Hub（第 2 节） |
| 备份 | 备份包含数据库、Hub 身份私钥和 Hub 主密钥，整体用备份公钥加密；只有持有离线备份私钥的用户能解开 |
| 内存中的密钥 | 使用 `zeroize`；不写入日志和错误信息 |
| token 泄露 | 固定前缀便于扫描；`last_used_at` 和来源可在控制台查看；一键吊销 |
| 时间 | 过期判断依赖时钟；节点与 Hub 时间偏差超过阈值时告警 |
