# Authentication and Authorization

- Status: draft
- Phase: P0 design; M1 implementation (see section 13)
- Related: ADR [0006](../adr/0006-auth-and-passkey-signing.md), [0012](../adr/0012-single-binary-packaging.md), [0014](../adr/0014-signed-mesh-membership.md), [0019](../adr/0019-mesh-only.md); [api-resources.md](api-resources.md), [changes.md](changes.md)

## 1. Scope

This document defines: the trust model, each kind of identity and its credentials, initialization and recovery, login and sessions, API tokens, permission scopes, node enrollment and connection authentication, device credentials, the signature format, distribution and update of trust anchors, release signatures, and safeguards.

## 2. Trust model

```
The user's recovery key (passkeys added later) <- highest trust anchor; the private key stays only on the user's computer
   │ signs
   ▼
Trust anchor list (recovery key public key, passkey public keys added later) ──► written to every node
   │                                         │
   │ signs                                    │ nodes verify with it independently
   ▼                                         ▼
Change approvals, node policies, mesh admission material ── relayed by the Hub ──► nodes

The project's release signing keys (primary and backup) ──► public keys embedded in nett at build time ──► nodes verify release packages (section 11.3)
```

| Principal | Keys held | Trusted by | Consequence of compromise |
|---|---|---|---|
| User | Recovery key (in the site directory, with an offline copy) and backup private key; passkey private keys (in the device) added later | Hub, all nodes | Full control |
| Hub | Hub identity key (X25519, used for Noise) | Nodes (pin its public key at enrollment) | Can see all state stored by the Hub and reported by nodes, and can perform low-risk operations and confirmed medium-risk operations; **cannot** raise any node's privileges, add mesh members, or widen mesh access |
| Node | Node identity key (X25519, used for Noise), mesh private key | Hub, other nodes (by admission material) | Affects that node itself; a node with the `gateway` role can also send traffic from the addresses of devices connected through it |
| nett-relay | Holds no mesh private key or identity key | — | Can only forward or drop ciphertext; a CONNECT proxy can see the targets accessed through it and unencrypted content, and when compromised can also reach every target the CONNECT policy allows from the shared CONNECT egress address |
| Project | Release signing keys (the primary key is in CI's encrypted secrets, with an offline copy; the backup key is stored offline only) | All nodes | Primary key stolen: can publish malicious new versions until a new version signed by the backup key replaces it; cannot make nodes downgrade (ADR 0020) |

Principle: **the Hub is a middleman, not a root of trust**. Every operation that raises privileges is ultimately verified by the node against the user's public key.

**Where the signed content is computed and displayed**: the signing tool on the user's computer computes the signed payload from the local site state and lists it locally before signing (ADR 0024, site.md section 7); enrollment private keys and device private keys are also generated by the signing tool and never pass through the Hub (hub.md section 6). The Hub only relays signed artifacts and cannot substitute the content being signed; a node's enrollment command is likewise generated by the signing tool and states the hash of the release package, and installation does not run code supplied by the Hub (hub.md section 3.3). A compromised Hub therefore cannot exceed its authority, and the user does not need to avoid anything it provides. Mitigations:

- A node stores every signed artifact it has accepted, and `nett trust log` lists them locally (time, kind, content digest) without going through the Hub, so the user can check afterwards which authorizations a node has accepted. If a malicious signature has already handed control of the node over, this record can no longer be trusted either;
- Once the Web console is added (ADR 0005, 0024), the console page is served by the Hub: the page computes the signed payload and hands it to the passkey to sign, but a passkey cannot show the user what it is signing, so a compromised Hub can make the page display one operation while requesting a signature for another. When signing on the console, the premise gains one more condition: the user has not signed, entered secrets, or generated device configuration on a compromised console.

## 3. Identities and credentials

| Identity | Credential | Purpose | `actor.kind` recorded in `events` |
|---|---|---|---|
| User | Recovery key (signing tool); passkey added later | Approval and signing; login to the Web console once it is added | `owner` |
| Signing tool | `owner` API token (section 6) | Pushing signed artifacts, maintaining the site (hub.md section 4) | `owner` |
| Session | Session cookie (added with the Web console) | Browser access to the API | `owner` |
| API token | `script` API token | External programs such as scripts and static integrations (including AI) | `api_token` |
| node | X25519 identity key | node ↔ Hub communication | `node` |
| Enrollment | One-time enrollment signing key (Ed25519, generated by the signing tool) | Proves the node obtained the user's authorization (section 8) | `node` |
| Device | Device credentials: a WireGuard key, or a CONNECT credential | Mesh access, CONNECT proxy | — |
| Hub itself | — | Automatic execution after approval, upgrade pushes | `system` |

## 4. Initialization and recovery

### 4.1 Initialization

1. On the user's computer, `nett site init` generates the **recovery key** (a P-256 signing key pair) and the trust anchor list, saves them in the site directory, and prompts the user to keep an offline copy (site.md section 8);
2. After the Hub is installed, `nett-hub init` prints a one-time **link code** in the terminal: it contains the Hub address, the Hub identity public key, and a 256-bit random secret, is valid for 1 hour, and can be used only once;
3. On the user's computer, `nett site link <link code>` verifies the Hub's TLS certificate, proves itself with the random secret, hands the trust anchor list to the Hub, and receives the site's `owner` token in return (hub.md section 3.1);
4. After linking completes, the link code is invalidated; linking again requires running a command on the Hub host to reset it.

The **backup key** (an X25519 key pair used to encrypt Hub backups, see section 12) is generated by the signing tool together with the Hub's backup (H5 in hub.md section 9); the Hub stores only the public key. Passkey registration is added with the Web console (ADR 0024).

### 4.2 Recovery

| Situation | Handling |
|---|---|
| The computer holding the site directory is damaged or lost | Restore from the offline copy of the recovery key and the backup of the site directory (site.md section 8) |
| One passkey is lost and other passkeys remain (after the Web console is added) | Log in with another passkey and delete the lost passkey (a trust anchor update, which requires a signature) |
| All passkeys are lost (after the Web console is added) | Log in to the console with the recovery key and register a new passkey; the trust anchor update is signed by the recovery key |
| The recovery key is also lost | Online recovery is impossible: artifacts signed by the old trust anchors can no longer be verified, and the mesh can only be rebuilt. Reset on the Hub host, run `nett leave` as root on every node (section 8.3), and join the new mesh |

The recovery key can sign all authorizations, so a leak hands over full control: it is kept in the site directory (`0600`), with an offline copy. **Signing is done on the user's computer by the signing tool, and the private key is never sent to the Hub.** Once the Web console is added, the recovery key can also log in to the console: the browser signs a challenge issued by the Hub, again without sending the private key.

**Presentation**: a private key begins with `nett-recovery-`, followed by a Bech32m-encoded data part, displayed in groups of 4 characters separated by hyphens, for example `nett-recovery-qpzr-y9x8-gf2t-…`. The checksum follows the Bech32m rules, computed with `nett-recovery` as the prefix; the separator `1` specified by Bech32 is omitted when displaying and added back automatically when parsing. Input ignores hyphens, spaces, and case, and the checksum catches the vast majority of transcription errors. The backup private key uses the same format with the prefix `nett-backup-`.

## 5. Login and sessions

This section is added with the Web console (ADR 0024).

- **The console uses a single address**: a passkey is bound to the domain it was registered on (the RP ID) and cannot be used on other domains; the Hub's alternate entry points are used only for node connections (nodes authenticate by the Hub public key, which does not involve passkeys) and do not serve the console;
- Login: WebAuthn authentication, requiring user verification (UV);
- Session cookie: `__Host-nett_session`, `HttpOnly`, `Secure`, `SameSite=Strict`; expires after 12 hours idle, 7 days at most;
- **Step-up verification**: creating an API token with write permission and similar operations require a passkey verification completed within the last 5 minutes;
- CSRF: in addition to `SameSite=Strict`, all write requests check the `Origin` header;
- Sessions can be viewed and revoked in the console.

## 6. API tokens

### 6.1 Format

```
nett_tok_<26-character ID>_<43-character random secret>
```

- The fixed prefix makes the tokens easy for secret scanners on code hosting platforms to recognize;
- The random secret is 256 bits; the server stores only its SHA-256 hash and compares in constant time;
- The plaintext is shown only once, at creation.

### 6.2 Attributes

| Attribute | Description |
|---|---|
| `kind` | `owner`: issued to the signing tool when the site is linked (hub.md section 4), allows all site operations, and the artifacts it pushes must still pass signature verification; `script`: external programs such as scripts |
| `scopes` | Permission scopes (section 7) |
| `expires_at` | Required, at most 1 year |
| `allowed_sources` | Optional, the allowed source address ranges (how the source is determined is described in section 12) |

An `owner` token is issued only at linking. A `script` token is created in the Web console, and one with write permission requires step-up verification (section 5).

## 7. Permission scopes

Format: `<resource>:<operation>[:<target name>]`.

| Scope | Allows |
|---|---|
| `read` | Read all resources (excluding sensitive fields) |
| `<resource>:read` | Read one kind of resource, for example `nodes:read`, `events:read` |
| `<resource>:write` | Low-risk direct modification, for example `nodes:write` (change name, labels) |
| `<resource>:propose` | Propose medium- and high-risk changes to that kind of resource, for example `links:propose`, `access-rules:propose`, `devices:propose`, `nodes:propose` |
| `changes:propose` | Create change sets; the scopes required by the corresponding actions are also needed |

The scopes required by each action type are listed in the action catalog (changes.md section 8).

Rules:

- **Tokens cannot approve**: an artifact that raises privileges must carry a signature verifiable against the trust anchors, and this holds for artifacts pushed with an `owner` token too (hard rule 3). Change sets and their approval are added with the Web console (changes.md);
- A user session has all permission scopes, but high-risk operations still require a signature;
- Operations involving identity and trust (passkeys, the recovery key, API token management) can be done only by the signing tool or a user session.

## 8. Node enrollment and connection

### 8.1 Enrollment token

```
nett_enr_<encoded content>
```

When a token is created, the **signing tool** assigns the node ID and mesh address and generates a one-time enrollment signing key pair (Ed25519, hub.md section 6). The encoded content contains:

| Field | Purpose |
|---|---|
| Hub address | The address to connect to at enrollment |
| Node ID | Assigned when the token is created; written into the initial node policy and the admission proof |
| Hub identity public key (32 bytes) | The Noise IK handshake needs the full public key; also prevents connecting to an impostor Hub |
| Trust anchor list fingerprint (128 bits) | Prevents the Hub from delivering forged trust anchors at enrollment |
| Enrollment private key | The 32-byte Ed25519 seed; proves the holder obtained the user's authorization; the Hub never sees it |
| Expiry time | 30 minutes after creation; the Hub checks it at enrollment |
| Hub certificate fingerprint | Only when the Hub uses a self-signed certificate: TLS verifies against it (hard rule 11) |

- The token is created by the signing tool (`nett site add`, `nett site invite`), is valid for 30 minutes, and can be used only once: after enrollment the Hub recognizes the machine by its identity public key, and another machine using it is rejected (hub.md section 6);
- The node's initial modules and roles, together with the node ID, mesh address, and enrollment public key, form an **initial node policy**, signed by the signing tool with the recovery key (the mesh and relay modules both have risk level high).

### 8.2 Enrollment flow

```
node                                              Hub
 │ Generate the node identity key (X25519) and mesh key; private keys stay on this machine only
 │ ── Noise IK handshake (using the Hub public key from the token) ──►│
 │ ── Hello: node ID + admission proof + capabilities ───────────────►│ Verify the admission proof with the enrollment public key in the policy;
 │    admission proof = signature by the enrollment private key over  │ the identity public key in the proof = the handshake identity public key;
 │    { node ID, identity public key, mesh public key }               │ check the token is unused and unexpired
 │ ◄── Welcome ─────────────────────────────────────│
 │ ◄── Desired state (trust anchor list, admission material including this node) ─│
 │ Verify the trust anchor list fingerprint matches the token; check the node ID
 │ Discard the enrollment private key; save the desired state and Hub configuration → the mesh process verifies with the trust anchors and applies → report
```

The signed policy plus the admission proof is the node's **admission material**: the Hub distributes it to the other members, and they use it to independently verify this node's mesh public key (ADR 0014, mesh.md section 4.1).

### 8.3 Regular connection

- The node initiates a WebSocket connection;
- **A Noise protocol (IK pattern) inside the WebSocket provides mutual authentication and establishes an end-to-end encrypted channel**: the node and the Hub each prove their identity with their identity keys (details in [protocol.md](protocol.md)). Even if TLS is terminated by a reverse proxy in between, the reverse proxy cannot read or tamper with messages between the node and the Hub;
- The Hub public key is pinned at enrollment; when the Hub identity key is replaced, the new public key is delivered over an authenticated channel established with the old key, and the node switches after confirming. A backup is generated immediately after the replacement: earlier backups contain the old key, and a Hub restored from them cannot handshake with nodes (protocol.md section 6.4);
- Revoking a node: the Hub refuses the node's connection and removes its public key from the mesh topology;
- **A node leaving on its own** (`nett leave`, run as root on the node):
  - Sends `Leave` to the Hub, which marks the node `removed`; this lowers privileges and needs no signature; if the Hub is unreachable, the remaining steps proceed anyway. For a site without a Hub, use `nett site remove` to remove the node, which generates a revocation (site.md section 4);
  - Tears down the local mesh interface, filter rules, and routes. The mesh process deliberately leaves the interface in place when it normally exits (connections stay up across a restart, mesh.md section 4), so stopping the process is not enough;
  - Deletes the local identity key, mesh private key, trust anchors, accepted signed artifacts and revocations, desired state, and Hub configuration, and stops and removes the nett-node and mesh process services. Afterwards the machine can join any mesh, generating all keys anew at enrollment, so the two meshes cannot link it across them;
- **Remote removal does not reset trust anchors**: a revocation delivered by the Hub or the site tool only makes the other members stop accepting this node, and the node keeps its original trust anchors. A compromised Hub therefore cannot first remove a node and then pull it into another mesh; resetting the trust anchors is possible only by running `nett leave` as root on the node.

## 9. Device credentials

| Type | Content | Purpose |
|---|---|---|
| `wireguard` | WireGuard key pair | A standard WireGuard client or proxy client (Surge, mihomo, sing-box) joins the mesh |
| `connect` | CONNECT proxy token | Access internal services through the CONNECT proxy of nett-relay when UDP is restricted |

- WireGuard private keys are **generated only on the user's computer by the signing tool**; the Hub stores only the public key and never handles the private key;
- **The full configuration (including the private key) is generated only once, at creation**: the signing tool generates the configuration file and QR code (or the proxy client's configuration) for saving or scanning, and it cannot be exported again afterwards. If the configuration is lost, create a new credential and revoke the old one. The "everything through the gateway" fallback configuration uses a separate credential created together with the main configuration (mesh.md section 13);
- Adding a device (`device.add`) and adding a credential to an existing device (`device_credential.create`) are both high-risk operations and require a signature; the signed artifact binds the credential's public key (or token hash) and the mesh address, and is verified independently by the gateway, the smart gateway, and nett-relay;
- Credential creation is recorded as an activity event; once revoked, the credential is removed immediately from the mobile gateway, the direct entry point, and nett-relay.

## 10. Signature format

### 10.1 Signed payload

The object being signed is a canonicalized JSON document (RFC 8785), called the **signed payload**:

```json
{
  "v": 1,
  "kind": "change_approval",
  "change_id": "chg_…",
  "plan_hash": "sha256:…",
  "artifacts": [
    {
      "kind": "node_policy",
      "node_id": "node_…",
      "policy_version": 5,
      "modules": ["mesh", "relay"]
    }
  ],
  "expires_at": "…"
}
```

Values of `kind`: `change_approval` (change approval), `enrollment_policy` (the initial policy of an enrollment token), `trust_update` (trust anchor update).

`artifacts` are the products to be delivered to nodes and verified independently by them:

| Artifact `kind` | Content | Verified by |
|---|---|---|
| `node_policy` | Node ID, version, modules, roles (relay, gateway, smart gateway, edge; the `edge` role states how to recognize traffic sent by Edge), mesh address and Edge address, enrollment public key | That node; mesh members (admission) |
| `device_credential` | Device ID, credential ID, credential type, public key or token hash, mesh address | Mobile gateway, smart gateway, nett-relay |
| `advertised_routes` | Node ID, prefix list, version | Mesh members |
| `access_rule_set` | The whole access rule set, written as the **result after selector expansion** (member IDs, addresses, ports), not as labels; version | Mesh members, nett-relay (CONNECT) |
| `release_override` | Node ID, the specific version allowed to be installed (for downgrade) | That node |

The change set signature covers exactly this payload, and `plan_hash` already includes the steps of the change; changes.md refers to this section and does not define it separately.

### 10.2 Combination with WebAuthn

Passkey signing is added with the Web console (ADR 0024). Items 1-5 below apply only to passkey signatures; items 6 and 7 (expiry time and version number) apply to all signatures, including recovery key signatures (section 10.3).

- The browser starts WebAuthn authentication with `challenge = SHA-256(signed payload)`;
- The resulting authentication result (`authenticatorData`, `clientDataJSON`, `signature`) is stored and delivered together with the signed payload;
- The verifier (Hub and node) checks:
  1. `clientDataJSON.type` is `webauthn.get`;
  2. `clientDataJSON.challenge` equals the hash of the signed payload;
  3. `origin` matches the console address recorded in the trust anchor list, and `crossOrigin` is not `true`;
  4. The RP ID hash in `authenticatorData` matches, and both the user present (UP) and user verified (UV) flags are set;
  5. The signature verifies with one of the public keys in the trust anchors;
  6. **The expiry time constrains approval**: the Hub executes a change set only before the payload expires; for artifacts that directly change a node's own privileges (that node's own `node_policy` and `release_override`), the node checks that the payload has not expired when it first accepts it. Artifacts describing mesh members and access scope (other members' admission material, `device_credential`, `advertised_routes`, `access_rule_set`) are distributed long after approval to newly joined members, new gateways, or reinstalled nodes, so verifiers do not check their expiry time. When an approval is canceled or expires unexecuted, the Hub delivers a revocation that voids the approval (section 10.4);
  7. For versioned artifacts, the version is greater than the version currently in effect and also greater than the version in the revocation (section 10.4). An artifact identical to the version currently in effect (for example the full snapshot the Hub resends after reconnecting) is treated as idempotent and acknowledged directly, without changing any narrowing already in effect.
- Allowed algorithms: ES256, EdDSA;
- The signature counter of synced passkeys is unreliable and is not used as a verification condition.

### 10.3 Recovery key signature

The recovery key signs the hash of the signed payload directly with ECDSA P-256, without going through WebAuthn, and signing is done on the user's computer by the signing tool (site.md). Nodes verify using the same payload format.

### 10.4 Revocation and initial sync

Lowering privileges never requires a signature. When the Hub delivers such a change it attaches a **revocation**, in three kinds by object:

| Type | Object | Effect |
|---|---|---|
| Identity revocation | Removing a node, revoking a device credential | Takes effect **permanently** by node ID or credential ID; no signed artifact of any version can restore it; a re-enrolled node and a newly created credential use new IDs |
| Privilege narrowing | Revoking a prefix, narrowing access rules | Records the object and the version at which it was narrowed. The narrowed state is saved as a local override: resending a signed artifact of the same version does not lift it, and only a signed artifact with a higher version replaces it |
| Approval voiding | An approval that was canceled or expired unexecuted | Voids the approval by approval ID and artifact hash, without affecting older versions that are still valid |

- Nodes keep revocations permanently (a few dozen bytes each); when connecting to the Hub, a node syncs revocations first and then applies new authorizations;
- A member removes a peer only because of a revocation: a member missing from a full snapshot is not treated as revoked;
- When a new member enrolls, the Hub delivers the complete revocations and the current signed artifacts as the baseline for the initial sync;
- Limitation: a revocation takes effect only on members that have received it, and offline members receive it only after reconnecting. A compromised Hub can withhold a revocation from members that never received it (for example members that were offline at the time and joined afterwards).

### 10.5 Encoding

The byte-level format of signed payloads, admission proofs, and trust anchor lists. The signing tool generates them in this format, and all verifiers (Hub, nett-node, mesh process, nett-relay) share the same implementation in `nett-trust`.

- **Canonical JSON**: a subset of RFC 8785; numbers are only integers from 0 to 2⁵³−1, with no floating point. The verifier first confirms that the received bytes are exactly the canonical form of the parse result (duplicate keys, extra whitespace, and non-canonical escapes all fail), then verifies the signature; verification and storage both use only the received bytes, without re-serializing.
- **Unrecognized content is rejected as a whole**: if a payload contains an unrecognized field, `kind`, or artifact kind, the entire payload is not accepted. Nodes of an older version accept artifacts of a new kind only after upgrading.
- **Field formats**: public keys and signatures use unpadded base64url; hashes are written as `sha256:` followed by 64 lowercase hexadecimal characters; times are written as `YYYY-MM-DDTHH:MM:SSZ` (UTC, second precision).
- **Public keys**: ES256 uses an uncompressed SEC1 point (65 bytes); EdDSA uses an Ed25519 public key (32 bytes); mesh public keys and identity public keys are X25519 public keys (32 bytes).
- **Signatures**:

  | Signer | Signed content | Signature format |
  |---|---|---|
  | passkey | `authenticatorData ‖ SHA-256(clientDataJSON)` (section 10.2) | ASN.1 DER for ES256; 64 bytes for EdDSA |
  | recovery key | The bytes of the signed payload, ECDSA P-256 with SHA-256 (section 10.3) | 64-byte `r ‖ s` (WebCrypto output format) |
  | enrollment private key | The bytes of the admission proof payload, Ed25519 | 64 bytes |

- **Transport form of a signed artifact**: the bytes of the signed payload plus one signature. A passkey signature carries the ID of that passkey in the trust anchors, plus `authenticatorData`, `clientDataJSON`, and the signature; a recovery key signature is just the signature itself.
- **Node policy artifact**, with fields matching the `node-policies` resource (api-resources.md section 5.2):

  ```json
  {
    "kind": "node_policy",
    "node_id": "node_…",
    "policy_version": 1,
    "modules": ["mesh"],
    "roles": ["relay"],
    "addresses": { "mesh": { "ipv4": "100.88.0.2", "ipv6": "fd…::2" } },
    "enrollment_public_key": "…"
  }
  ```

  With the `edge` role there are two more items: `edge` states how to recognize traffic sent by Edge (`containers`: the prefixes of the containers Edge runs in), and `addresses.edge` is the Edge address; without that role neither item appears.

  ```json
  {
    "roles": ["edge"],
    "edge": { "containers": ["172.17.0.0/16"] },
    "addresses": { "mesh": { "ipv4": "…", "ipv6": "…" }, "edge": { "ipv4": "…", "ipv6": "…" } }
  }
  ```

- **Access rule set artifact**: the whole rule set, with rules matched in array order (earlier rules take precedence), written as the prefixes and ports after selector expansion (mesh.md section 12). An empty `ports` means all protocols and ports:

  ```json
  {
    "kind": "access_rule_set",
    "version": 3,
    "rules": [
      { "action": "allow", "from": ["100.88.0.9/32", "fd…::9/128"], "to": ["100.88.0.2/32", "fd…::2/128"],
        "ports": [{ "protocol": "tcp", "first": 8686, "last": 8686 }] }
    ]
  }
  ```

- **Advertised routes artifact**: the prefixes advertised by a smart gateway (mesh.md section 10), one per node, with a version number. Only the advertisement of a node whose node policy has the `subnet_router` role is accepted:

  ```json
  { "kind": "advertised_routes", "node_id": "node_…", "version": 1, "routes": ["192.0.2.10/32"] }
  ```

- **Admission proof**: the signature by the enrollment private key over the following payload, distributed together with the payload bytes:

  ```json
  {
    "v": 1,
    "kind": "admission_proof",
    "node_id": "node_…",
    "identity_public_key": "…",
    "mesh_public_key": "…"
  }
  ```

- **Artifact hash** (approval voiding and the keep-valid list refer to artifacts by it): the SHA-256 of the artifact object's canonical form;
- **Trust anchor list fingerprint** (the 128 bits in the enrollment token): the first 16 bytes of the SHA-256 of the list's canonical form.

## 11. Trust anchors

### 11.1 Trust anchor list

```json
{
  "v": 1,
  "version": 3,
  "rp_id": "hub.example.com",
  "origin": "https://hub.example.com",
  "passkeys": [ { "id": "pk_…", "alg": "ES256", "public_key": "…" } ],
  "recovery_key": { "alg": "ES256", "public_key": "…" }
}
```

### 11.2 Updates

- Adding or removing a passkey and replacing the recovery key are all trust anchor updates: generate a new version of the list, as a `trust_update` signed payload, signed by a passkey or the recovery key **in the current list**;
- A node accepts only updates with a higher version that are signed by the current trust anchors;
- Deleting the last passkey is not allowed;
- **Deleting a passkey carries a keep-valid list**: the artifacts signed by the deleted passkey that are currently in effect and not revoked have their exact hashes listed in this `trust_update` payload and are signed together with the trust anchor update. Members that join afterwards accept these artifacts by the list; the deleted passkey can no longer issue any new authorization. Historical trust anchors are not looked up by "issue time", because a lost passkey can forge issue times;
- A change of the console address (`origin`) is also a trust anchor update; since passkeys are bound to the domain, passkeys must be registered again after migrating to a new domain, so this update is signed by the recovery key, and the new passkeys are added to the trust anchors after registering at the new address.

### 11.3 Release signatures

The trust anchors for release packages are independent of the user's trust anchors and also independent of the Hub (ADR 0012, 0020):

- The release signing keys belong to the project and are held by the maintainers, and the release workflow signs automatically in CI; Ed25519, minisign format. Every build embeds two public keys, primary and backup (a build parameter: official builds use the project's, and people compiling themselves use their own); a node accepts a package signed by either key and uses it to verify every release package;
- When the primary key is leaked or lost, the backup key signs a version embedding new primary and backup public keys; once a node has installed it, the node no longer accepts signatures from the old primary key;
- At first installation, the release package is checked against the hash stated in the enrollment command; the hash is written by the signing tool after it verifies the release signature with the embedded release public key (hub.md section 3.3). The user can also check the executable against the fingerprint published on the project homepage;
- A node automatically accepts only release packages with a higher version number; rollback is possible only to the version last installed on this machine; installing any other lower version requires a `release_override` artifact (signed by the user);
- Upgrades have a single path: the `release` partition of the desired state (protocol.md section 6). An upgrade that satisfies the rules above is low risk and can be pushed automatically by the Hub.

## 12. Safeguards

| Item | Measure |
|---|---|
| Brute force | Login, enrollment, and token authentication endpoints are rate-limited by source; temporary lockout after consecutive failures |
| Real source | The Hub sits behind its own reverse proxy (Caddy by default, hub.md section 8) and trusts `X-Forwarded-For` only from that reverse proxy's address (the local machine or its container address), used for rate limiting and `allowed_sources` (ADR 0015, 0019) |
| Key storage | The Hub identity private key is stored in the Hub data directory with file permissions `0600`; the public keys of the recovery key and backup key are stored in the database |
| Signature audit | Nodes keep the signed artifacts and revocations they have accepted, and `nett trust log` lists them locally without going through the Hub (section 2) |
| Backup | A backup contains the database and the Hub identity private key, encrypted as a whole with the backup public key; only a user holding the offline backup private key can open it |
| Keys in memory | Use `zeroize`; never written to logs or error messages |
| Token leak | Fixed prefix for scanning; `last_used_at` and source are visible via the API; one-click revocation |
| Time | Expiry decisions depend on the clock; an event is reported when the time offset between a node and the Hub exceeds a threshold |
