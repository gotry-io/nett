## 2. 信任模型

```
用户的恢复密钥（以后加上 passkey） ← 最高信任锚，私钥只在用户自己的电脑上
   │ 签名
   ▼
信任锚清单（恢复密钥公钥，以后加上 passkey 公钥）──► 写入每个节点
   │                                         │
   │ 签名                                     │ 节点用它独立验证
   ▼                                         ▼
变更批准、节点策略、组网准入材料 ── Hub 转发 ──► 节点

项目的发布签名密钥（主备两把）──► 公钥在构建时嵌入 nett ──► 节点验证发布包（第 11.3 节）
```

| 主体 | 持有的密钥 | 被谁信任 | 被攻破的后果 |
|---|---|---|---|
| 用户 | 恢复密钥（站点目录中，另有离线备份）与备份私钥；以后加上 passkey 私钥（设备内） | Hub、所有节点 | 全部控制权 |
| Hub | Hub 身份密钥（X25519，用于 Noise） | 节点（入网时固定其公钥） | 能看到 Hub 保存和节点上报的全部状态，能执行低风险操作和经过确认的中风险操作；**不能**提升任何节点的权限，不能加入组网成员或放宽组网访问 |
| 节点 | 节点身份密钥（X25519，用于 Noise）、组网私钥 | Hub、其他节点（凭准入材料） | 影响该节点本身；具有 `gateway` 角色的节点还能以经它接入的设备的地址发出流量 |
| nett-relay | 不持有组网私钥和身份密钥 | — | 只能转发或丢弃密文；CONNECT 代理能看到经它访问的目标和未加密的内容，被攻破时还能以共享的 CONNECT 出口地址访问 CONNECT 允许的全部目标 |
| 项目 | 发布签名密钥（主钥匙在 CI 的加密密钥中，另有离线备份；备用钥匙只离线保存） | 所有节点 | 主钥匙被盗：能发布恶意的新版本，直到备用钥匙签发的新版本换掉它；不能让节点降级（ADR 0020） |

原则：**Hub 是中间人，而不是信任根**。所有提升权限的操作，最终都要由节点用用户的公钥验证。

**签名的内容在哪里计算和显示**：签名载荷由用户电脑上的签名工具从本地的站点状态计算，签名之前在本机列出（ADR 0024，site.md 第 7 节）；入网私钥和设备私钥也由签名工具生成，不经过 Hub（hub.md 第 6 节）。Hub 只转发签名产物，替换不了要签的内容；节点的入网命令同样由签名工具生成，写明发布包的哈希，安装不运行 Hub 提供的代码（hub.md 第 3.3 节）。因此 Hub 被攻破时不能越权，不需要用户避开它提供的任何东西。缓解措施：

- 节点保存它接受过的每一份签名产物，`nett trust log` 在本机列出（时间、种类、内容摘要），不经过 Hub，用户可以事后核对节点接受过哪些授权。某份恶意签名如果已经把节点的控制权交了出去，这份记录也不再可信；
- Web 控制台加入之后（ADR 0005、0024），控制台页面由 Hub 提供：签名载荷由页面计算，再交给 passkey 签名，而 passkey 无法向用户显示它签的是什么，被攻破的 Hub 可以让页面显示一项操作、实际请求签名另一项。在控制台上签名时，前提还要加上：用户没有在被攻破的控制台上签名、输入机密或生成设备配置。

## 3. 身份与凭据

| 身份 | 凭据 | 用途 | 记录到 `events` 的 `actor.kind` |
|---|---|---|---|
| 用户 | 恢复密钥（签名工具）；以后加上 passkey | 批准与签名；Web 控制台加入后登录 | `owner` |
| 签名工具 | `owner` API token（第 6 节） | 推送签名产物、维护站点（hub.md 第 4 节） | `owner` |
| 会话 | 会话 Cookie（随 Web 控制台加入） | 浏览器访问 API | `owner` |
| API token | `script` API token | 脚本、静态集成等外部程序（包括 AI） | `api_token` |
| node | X25519 身份密钥 | node ↔ Hub 通信 | `node` |
| 入网 | 一次性的入网签名密钥（Ed25519，签名工具生成） | 证明节点获得了用户授权（第 8 节） | `node` |
| 设备 | 设备凭据：WireGuard 密钥，或 CONNECT 凭据 | 组网接入、CONNECT 代理 | — |
| Hub 自身 | — | 批准后的自动执行、升级推送 | `system` |

## 4. 初始化与恢复

### 4.1 初始化

1. 用户的电脑上 `nett site init` 生成**恢复密钥**（一对 P-256 签名密钥）与信任锚清单，保存在站点目录中，提示另存一份离线备份（site.md 第 8 节）；
2. 安装 Hub 后，`nett-hub init` 在终端打印一次性**关联码**：包含 Hub 地址、Hub 身份公钥和 256 位随机密钥，1 小时内有效，只能使用一次；
3. 用户的电脑上 `nett site link <关联码>`：校验 Hub 的 TLS 证书，用随机密钥证明自己，把信任锚清单交给 Hub，换回站点的 `owner` token（hub.md 第 3.1 节）；
4. 关联完成后关联码失效，再次关联需要在 Hub 主机上执行命令重置。

**备份密钥**（一对 X25519 密钥，用于加密 Hub 备份，见第 12 节）随 Hub 的备份由签名工具生成（hub.md 第 9 节的 H5）；Hub 只保存公钥。passkey 的注册随 Web 控制台加入（ADR 0024）。

### 4.2 恢复

| 情形 | 处理 |
|---|---|
| 站点目录所在的电脑损坏或丢失 | 用离线备份的恢复密钥和站点目录的备份恢复（site.md 第 8 节） |
| 丢失一个 passkey，仍有其他 passkey（Web 控制台加入之后） | 用其他 passkey 登录，删除丢失的 passkey（信任锚更新，需签名） |
| 丢失全部 passkey（Web 控制台加入之后） | 用恢复密钥登录控制台，注册新的 passkey；信任锚更新由恢复密钥签名 |
| 恢复密钥也丢失 | 无法在线恢复：旧的信任锚签过的产物都无法再验证，只能重建这张网。在 Hub 主机上重置，每个节点上以 root 执行 `nett leave`（第 8.3 节），再加入新的网 |

恢复密钥能签名所有授权，泄露等于交出全部控制权：保存在站点目录中（`0600`），另存一份离线备份。**签名在用户的电脑上由签名工具完成，私钥不发送给 Hub**。Web 控制台加入之后，恢复密钥也能登录控制台：浏览器对 Hub 给出的挑战签名，同样不发送私钥。

**呈现形式**：私钥以 `nett-recovery-` 开头，后接 Bech32m 编码的数据部分，按 4 个字符一组、以连字符分隔显示，例如 `nett-recovery-qpzr-y9x8-gf2t-…`。校验和按 Bech32m 规则、以 `nett-recovery` 作为前缀计算；显示时省略 Bech32 规定的分隔符 `1`，解析时自动补回。输入时忽略连字符、空格和大小写，校验和可以发现绝大多数抄写错误。备份私钥使用相同的格式，前缀为 `nett-backup-`。

## 5. 登录与会话

本节随 Web 控制台加入（ADR 0024）。

- **控制台只使用一个地址**：passkey 绑定注册时的域名（RP ID），在其他域名下无法使用；Hub 的备用入口只用于 node 连接（node 依靠 Hub 公钥认证，不涉及 passkey），不提供控制台；
- 登录：WebAuthn 认证，要求用户验证（UV）；
- 会话 Cookie：`__Host-nett_session`，`HttpOnly`、`Secure`、`SameSite=Strict`；空闲 12 小时过期，最长 7 天；
- **二次验证**：创建带写权限的 API token 等，要求 5 分钟内完成过一次 passkey 验证；
- CSRF：`SameSite=Strict` 之外，所有写请求校验 `Origin` 头；
- 会话可以在控制台查看和吊销。

## 6. API token

### 6.1 格式

```
nett_tok_<26 位 ID>_<43 位随机密钥>
```

- 固定前缀便于代码托管平台的密钥扫描识别；
- 随机密钥为 256 位；服务端只保存其 SHA-256 哈希，比较使用常量时间算法；
- 明文只在创建时显示一次。

### 6.2 属性

| 属性 | 说明 |
|---|---|
| `kind` | `owner`：关联站点时发给签名工具（hub.md 第 4 节），拥有站点的全部操作，推送的产物照样要通过签名验证；`script`：脚本等外部程序 |
| `scopes` | 权限范围（第 7 节） |
| `expires_at` | 必填，最长 1 年 |
| `allowed_sources` | 可选，允许的来源地址范围（来源的判断方式见第 12 节） |

`owner` token 只在关联时发放。`script` token 在 Web 控制台中创建，带写权限的需要二次验证（第 5 节）。

## 7. 权限范围

格式：`<资源>:<操作>[:<目标名称>]`。

| 权限范围 | 允许 |
|---|---|
| `read` | 读取所有资源（不含敏感字段） |
| `<资源>:read` | 读取某类资源，例如 `nodes:read`、`events:read` |
| `<资源>:write` | 低风险的直接修改，例如 `nodes:write`（改名称、标签） |
| `<资源>:propose` | 提议该类资源的中、高风险变更，例如 `links:propose`、`access-rules:propose`、`devices:propose`、`nodes:propose` |
| `changes:propose` | 创建变更集；同时需要对应动作要求的权限范围 |

每个动作类型所需的权限范围列在动作目录中（changes.md 第 8 节）。

规则：

- **token 不能批准**：提升权限的产物必须带有能用信任锚验证的签名，`owner` token 推送的产物同样如此（硬性规则 3）。变更集及其批准随 Web 控制台加入（changes.md）；
- 用户会话拥有全部权限范围，但高风险操作仍需签名；
- 涉及身份与信任的操作（passkey、恢复密钥、API token 管理）只能由签名工具或用户会话完成。

## 8. node 入网与连接

### 8.1 入网 token

```
nett_enr_<编码内容>
```

创建 token 时，**签名工具**分配节点 ID 和组网地址，生成一对一次性的入网签名密钥（Ed25519，hub.md 第 6 节）。编码内容包含：

| 字段 | 作用 |
|---|---|
| Hub 地址 | 入网时连接的地址 |
| 节点 ID | 创建 token 时分配，写入初始节点策略和准入证明 |
| Hub 身份公钥（32 字节） | Noise IK 握手需要完整公钥；同时防止连接到冒充的 Hub |
| 信任锚清单指纹（128 位） | 防止 Hub 在入网时下发伪造的信任锚 |
| 入网私钥 | 证明持有者获得了用户授权；Hub 从未见过它 |

- token 由签名工具创建（`nett site add`、`nett site invite`），默认 30 分钟内有效（最长 24 小时），只能使用一次；
- 节点的初始模块与角色，连同节点 ID、组网地址和入网公钥，形成一份**初始节点策略**，由签名工具用恢复密钥签名（mesh、relay 模块的风险等级均为高）。

### 8.2 入网流程

```
node                                              Hub
 │ 生成节点身份密钥（X25519）和组网密钥，私钥只存本机
 │ ── Noise IK 握手（使用 token 中的 Hub 公钥）──────►│
 │ ── Hello：节点 ID + 准入证明 + 能力信息 ──────────►│ 用入网公钥验证准入证明；
 │    准入证明 = 入网私钥对                            │ 检查 token 未使用、未过期
 │    { 节点 ID, 身份公钥, 组网公钥 } 的签名          │
 │ ◄── 信任锚清单 + 初始节点策略（含签名）────────────│
 │ 校验信任锚清单的指纹与 token 中一致
 │ 用信任锚验证初始节点策略的签名，核对其中的节点 ID
 │ 丢弃入网私钥；保存身份、Hub 公钥、信任锚、策略 → 应用 → 上报
```

签名策略加上准入证明，就是该节点的**准入材料**：Hub 把它分发给其他成员，成员据此独立验证这个节点的组网公钥（ADR 0014、mesh.md 第 4.1 节）。

### 8.3 日常连接

- node 主动建立 WebSocket 连接；
- **在 WebSocket 内层使用 Noise 协议（IK 模式）完成双向认证并建立端到端加密通道**：node 和 Hub 各自用身份密钥证明身份（细节见 [protocol.md](protocol.md)）。这样即使 TLS 由中间的反向代理终止，反向代理也无法读取或篡改 node 与 Hub 之间的消息；
- Hub 公钥在入网时固定；Hub 身份密钥更换时，新公钥通过以旧密钥建立的已认证通道下发，节点确认后切换。更换后立即生成一次备份：更早的备份中是旧密钥，用它恢复的 Hub 无法与节点握手（protocol.md 第 6.4 节）；
- 吊销节点：Hub 拒绝该节点的连接，并从组网拓扑中移除其公钥；
- **节点自行退出**（`nett leave`，在节点上以 root 运行）：
  - 向 Hub 发送 `Leave`，Hub 把节点标记为 `removed`，属于降低权限，不需要签名；连不上 Hub 时照常往下做。不接 Hub 的站点，用 `nett site remove` 移除这个节点，生成撤销记录（site.md 第 4 节）；
  - 拆掉本机的组网接口、过滤规则和路由。组网进程平时退出时故意保留接口（重启期间连接不断，mesh.md 第 4 节），所以只停掉进程不够；
  - 删除本机的身份密钥、组网私钥、信任锚、已接受的签名产物与撤销记录、期望状态和 Hub 的配置，停止并删除 nett-node 与组网进程的服务。之后这台机器可以加入任何一张网，入网时重新生成全部密钥，在两张网中不会被关联起来；
- **远程移除不重置信任锚**：Hub 或站点工具下发的撤销记录只让其他成员不再接受这个节点，节点自己保留原来的信任锚。被攻破的 Hub 因此不能先移除一个节点、再把它拉进别的网；重置信任锚只能在节点上以 root 执行 `nett leave`。

## 9. 设备凭据

| 类型 | 内容 | 用途 |
|---|---|---|
| `wireguard` | WireGuard 密钥对 | 标准 WireGuard 客户端或代理客户端（Surge、mihomo、sing-box）接入组网 |
| `connect` | CONNECT 代理的 token | UDP 受限时经 nett-relay 的 CONNECT 代理访问内网服务 |

- WireGuard 私钥**只在用户的电脑上由签名工具生成**，Hub 只保存公钥，从不经手私钥；
- **完整配置（含私钥）只在创建时生成一次**：签名工具生成配置文件和二维码（或代理客户端的配置），供保存或扫码，之后无法再次导出。配置丢失时新建一份凭据，并吊销旧的。"全部经网关"的备用配置使用另外一份凭据，与主配置同时创建（mesh.md 第 13 节）；
- 新增设备（`device.add`）和给已有设备新增凭据（`device_credential.create`）都是高风险操作，需要签名；签名产物绑定凭据的公钥（或 token 哈希）和组网地址，由网关、智能入口和 nett-relay 独立验证；
- 创建凭据记录到活动事件；吊销后立即从移动网关、直连入口和 nett-relay 移除。

## 10. 签名格式

### 10.1 签名载荷

签名的对象是一份规范化的 JSON（RFC 8785），称为**签名载荷**：

```json
{
  "v": 1,
  "kind": "change_approval",
  "change_id": "chg_…",
  "plan_hash": "sha256:…",
  "artifacts": [
    {
      "kind": "node_policy",
      "node_id": "node_…",
      "policy_version": 5,
      "modules": ["mesh", "relay"]
    }
  ],
  "expires_at": "…"
}
```

`kind` 的取值：`change_approval`（变更批准）、`enrollment_policy`（入网 token 的初始策略）、`trust_update`（信任锚更新）。

`artifacts` 是需要下发给节点、由节点独立验证的产物：

| 产物 `kind` | 内容 | 验证方 |
|---|---|---|
| `node_policy` | 节点 ID、版本、模块、角色（relay、gateway、智能入口、edge；`edge` 角色写明怎样识别 Edge 发出的流量）、组网地址与 Edge 专用地址、入网公钥 | 该节点；组网成员（准入） |
| `device_credential` | 设备 ID、凭据 ID、凭据类型、公钥或 token 哈希、组网地址 | 移动网关、智能入口、nett-relay |
| `advertised_routes` | 节点 ID、网段列表、版本 | 组网成员 |
| `access_rule_set` | 整份访问规则，写的是**选择器展开后的结果**（成员 ID、地址、端口），不是标签；版本 | 组网成员、nett-relay（CONNECT） |
| `release_override` | 节点 ID、允许安装的指定版本（用于降级） | 该节点 |

变更集签名覆盖的内容就是这份载荷，`plan_hash` 已经包含了变更的步骤，changes.md 引用本节，不另行定义。

### 10.2 与 WebAuthn 的结合

passkey 签名随 Web 控制台加入（ADR 0024）。下面第 1–5 项只用于 passkey 签名；第 6、7 项（过期时间与版本号）适用于所有签名，包括恢复密钥签名（第 10.3 节）。

- 浏览器以 `challenge = SHA-256(签名载荷)` 发起 WebAuthn 认证；
- 得到的认证结果（`authenticatorData`、`clientDataJSON`、`signature`）与签名载荷一起保存和下发；
- 验证方（Hub 和节点）检查：
  1. `clientDataJSON.type` 为 `webauthn.get`；
  2. `clientDataJSON.challenge` 等于签名载荷的哈希；
  3. `origin` 与信任锚清单中记录的控制台地址一致，`crossOrigin` 不为 `true`；
  4. `authenticatorData` 中的 RP ID 哈希一致，且用户在场（UP）、用户验证（UV）标志均已设置；
  5. 签名能用信任锚中的某个公钥验证；
  6. **过期时间约束的是批准**：Hub 只在载荷过期前执行变更集；直接改变某个节点自身权限的产物（该节点自己的 `node_policy`、`release_override`），该节点首次接受时检查载荷未过期。描述组网成员和访问范围的产物（其他成员的准入材料、`device_credential`、`advertised_routes`、`access_rule_set`）会在批准很久之后才分发给新加入的成员、新的网关或重装的节点，验证方不检查过期时间。批准被取消或过期未执行时，Hub 下发撤销记录作废这份批准（第 10.4 节）；
  7. 带版本号的产物，版本号大于当前已生效的版本，也大于撤销记录中的版本（第 10.4 节）。与当前已生效版本完全相同的产物（例如重连后 Hub 重发的完整快照）视为幂等，直接确认，不改变已经生效的收窄。
- 允许的算法：ES256、EdDSA；
- 同步型 passkey 的签名计数器不可靠，不作为校验条件。

### 10.3 恢复密钥签名

恢复密钥直接对签名载荷的哈希做 ECDSA P-256 签名，不经过 WebAuthn，签名在用户的电脑上由签名工具完成（site.md）。节点按相同的载荷格式验证。

### 10.4 撤销与首次同步

降低权限都不需要签名。Hub 下发时附带**撤销记录**，按对象分三类：

| 类型 | 对象 | 效果 |
|---|---|---|
| 身份撤销 | 移除节点、吊销设备凭据 | 按节点 ID 或凭据 ID **永久生效**，任何版本的签名产物都不能恢复；重新入网的节点、新建的凭据使用新的 ID |
| 权限收窄 | 撤销网段、收窄访问规则 | 记录对象和被收窄时的版本。收窄后的状态作为本地覆盖保存：重发同一版本的签名产物不会解除它，只有版本更高的签名产物才会取代它 |
| 批准作废 | 被取消或过期未执行的批准 | 按批准 ID 和产物哈希作废这份批准，不影响当前仍然有效的旧版本 |

- 节点永久保存撤销记录（每条几十字节）；连接 Hub 时先同步撤销记录，再应用新的授权；
- 成员只因撤销记录删除对端：完整快照中缺少某个成员，不视为撤销；
- 新成员入网时，Hub 下发完整的撤销记录和当前的签名产物，作为首次同步的基准；
- 局限：撤销只在收到撤销记录的成员上生效，离线的成员重新连接后才收到。被攻破的 Hub 可以对从未收到某条撤销记录的成员（例如当时离线、之后才加入的成员）隐瞒它。

### 10.5 编码

签名载荷、准入证明和信任锚清单在字节层面的格式。签名工具按它生成，所有验证方（Hub、nett-node、组网进程、nett-relay）共用 `nett-trust` 中的同一份实现。

- **规范化 JSON**：RFC 8785 的子集，数值只允许 0 到 2⁵³−1 的整数，没有浮点数。验证方先确认收到的字节恰好是解析结果的规范形式（重复的键、多余的空白、非规范的转义都不能通过），再验证签名；验证和保存都只用收到的这份字节，不重新序列化。
- **不认识的内容整份拒绝**：载荷中出现不认识的字段、`kind` 或产物种类，整份载荷不被接受。版本较旧的节点升级之后才接受新种类的产物。
- **字段格式**：公钥和签名用不带填充的 base64url；哈希写作 `sha256:` 加 64 位小写十六进制；时间写作 `YYYY-MM-DDTHH:MM:SSZ`（UTC，精确到秒）。
- **公钥**：ES256 为未压缩的 SEC1 点（65 字节）；EdDSA 为 Ed25519 公钥（32 字节）；组网公钥和身份公钥为 X25519 公钥（32 字节）。
- **签名**：

  | 签名方 | 签名的内容 | 签名格式 |
  |---|---|---|
  | passkey | `authenticatorData ‖ SHA-256(clientDataJSON)`（第 10.2 节） | ES256 为 ASN.1 DER；EdDSA 为 64 字节 |
  | 恢复密钥 | 签名载荷的字节，ECDSA P-256 与 SHA-256（第 10.3 节） | 64 字节的 `r ‖ s`（WebCrypto 的输出格式） |
  | 入网私钥 | 准入证明载荷的字节，Ed25519 | 64 字节 |

- **签名产物的传输形式**：签名载荷的字节，加上一个签名。passkey 签名带信任锚中这把 passkey 的 ID，以及 `authenticatorData`、`clientDataJSON` 和签名；恢复密钥签名只有签名本身。
- **节点策略产物**，字段与 `node-policies` 资源一致（api-resources.md 第 5.2 节）：

  ```json
  {
    "kind": "node_policy",
    "node_id": "node_…",
    "policy_version": 1,
    "modules": ["mesh"],
    "roles": ["relay"],
    "addresses": { "mesh": { "ipv4": "100.88.0.2", "ipv6": "fd…::2" } },
    "enrollment_public_key": "…"
  }
  ```

  有 `edge` 角色时还有两项：`edge` 写明怎样识别 Edge 发出的流量（`containers`：Edge 所在容器的网段），`addresses.edge` 是 Edge 专用地址；没有这个角色时两项都不出现。

  ```json
  {
    "roles": ["edge"],
    "edge": { "containers": ["172.17.0.0/16"] },
    "addresses": { "mesh": { "ipv4": "…", "ipv6": "…" }, "edge": { "ipv4": "…", "ipv6": "…" } }
  }
  ```

- **访问规则集产物**：整份规则集，规则按数组顺序匹配（排在前面的优先），写的是选择器展开后的网段和端口（mesh.md 第 12 节）。`ports` 为空表示所有协议和端口：

  ```json
  {
    "kind": "access_rule_set",
    "version": 3,
    "rules": [
      { "action": "allow", "from": ["100.88.0.9/32", "fd…::9/128"], "to": ["100.88.0.2/32", "fd…::2/128"],
        "ports": [{ "protocol": "tcp", "first": 8686, "last": 8686 }] }
    ]
  }
  ```

- **宣告网段产物**：智能入口宣告的网段（mesh.md 第 10 节），每个节点一份，带版本号。只有节点策略中有 `subnet_router` 角色的节点，它的宣告才被接受：

  ```json
  { "kind": "advertised_routes", "node_id": "node_…", "version": 1, "routes": ["192.0.2.10/32"] }
  ```

- **准入证明**：入网私钥对下面这份载荷的签名，与载荷的字节一起分发：

  ```json
  {
    "v": 1,
    "kind": "admission_proof",
    "node_id": "node_…",
    "identity_public_key": "…",
    "mesh_public_key": "…"
  }
  ```

- **产物哈希**（批准作废和继续有效清单按它引用产物）：产物对象规范形式的 SHA-256；
- **信任锚清单指纹**（入网 token 中的 128 位）：清单规范形式的 SHA-256 的前 16 字节。

## 11. 信任锚

### 11.1 信任锚清单

```json
{
  "v": 1,
  "version": 3,
  "rp_id": "hub.example.com",
  "origin": "https://hub.example.com",
  "passkeys": [ { "id": "pk_…", "alg": "ES256", "public_key": "…" } ],
  "recovery_key": { "alg": "ES256", "public_key": "…" }
}
```

### 11.2 更新

- 新增或删除 passkey、更换恢复密钥，都是信任锚更新：生成新版本的清单，以 `trust_update` 签名载荷，由**当前清单中**的某个 passkey 或恢复密钥签名；
- 节点只接受版本更高、且由当前信任锚签名的更新；
- 不允许删除最后一个 passkey；
- **删除 passkey 时附带继续有效清单**：由被删除的 passkey 签署、目前仍然生效且未被撤销的产物，把它们的精确哈希列进这次 `trust_update` 载荷，随信任锚更新一起签名。之后新加入的成员凭清单接受这些产物；被删除的 passkey 不能再签发任何新的授权。不按"签发时间"查历史信任锚，因为丢失的 passkey 可以伪造签发时间；
- 控制台地址（`origin`）变化也是信任锚更新；由于 passkey 绑定域名，迁移到新域名后需要重新注册 passkey，因此该更新由恢复密钥签名，新 passkey 在新地址注册后再加入信任锚。

### 11.3 发布签名

发布包的信任锚独立于用户的信任锚，也独立于 Hub（ADR 0012、0020）：

- 发布签名密钥属于项目，由维护者掌握，发布工作流在 CI 中自动签名；Ed25519，minisign 格式。每个构建嵌入主、备两把公钥（构建参数：官方构建用项目的，自己编译的人用自己的），节点接受任一把签名的包，用它验证每一个发布包；
- 主钥匙泄露或丢失时，用备用钥匙签发一个嵌入新的主、备公钥的版本；节点装上之后，不再接受旧主钥匙的签名；
- 首次安装时，发布包按入网命令中写明的哈希核对；哈希由签名工具用嵌入的发布公钥核对发布签名之后写入（hub.md 第 3.3 节）。用户也可以对照项目主页公布的指纹核对可执行文件；
- 节点只自动接受版本号更高的发布包；回滚只能回到本机上一次安装过的版本；安装其他更低的版本，需要 `release_override` 产物（用户签名）；
- 升级只有一条通路：期望状态的 `release` 分区（protocol.md 第 6 节）。满足上面规则的升级属于低风险，可以由 Hub 自动推送。

## 12. 防护措施

| 项 | 措施 |
|---|---|
| 暴力尝试 | 登录、入网、token 认证接口按来源限流；连续失败后临时锁定 |
| 真实来源 | Hub 位于它自己的反向代理之后（默认 Caddy，hub.md 第 8 节），只信任这台反向代理的地址（本机或其容器的地址）发来的 `X-Forwarded-For`，用于限流和 `allowed_sources`（ADR 0015、0019） |
| 密钥存储 | Hub 身份私钥存放在 Hub 数据目录，文件权限 `0600`；恢复密钥和备份密钥的公钥存入数据库 |
| 签名审计 | 节点保存接受过的签名产物和撤销记录，`nett trust log` 在本机列出，不经过 Hub（第 2 节） |
| 备份 | 备份包含数据库和 Hub 身份私钥，整体用备份公钥加密；只有持有离线备份私钥的用户能解开 |
| 内存中的密钥 | 使用 `zeroize`；不写入日志和错误信息 |
| token 泄露 | 固定前缀便于扫描；`last_used_at` 和来源可经 API 查看；一键吊销 |
| 时间 | 过期判断依赖时钟；节点与 Hub 时间偏差超过阈值时上报事件 |
