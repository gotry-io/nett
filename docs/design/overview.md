## 2. 三个平面

| 平面 | 承载什么 | 组件 | 不依赖什么 |
|---|---|---|---|
| 控制面 | 期望状态、状态与指标、任务 | Hub ⇄ nett-node（WebSocket + Noise，见 protocol.md） | 组网：Hub 端点列表中至少保留一个不经组网的端点（5.2） |
| 组网数据面 | 成员之间的 IP 流量 | 组网进程（WireGuard、路径层、DNS、过滤）+ 传输适配进程 + nett-relay（见 mesh.md） | Hub 在线；nett-node 在线（ADR 0013） |
| 入口面 | 公网访客到服务的流量 | Edge → 组网 → 服务（第 6 节） | Hub、nett-node 在线 |

入口面依赖组网数据面。控制面可以借道组网（例如经另一个入口节点连接 Hub），但不能只靠组网，否则一次错误的组网配置会让节点再也收不到修正。

## 3. 部署形态

### 3.1 节点形态

| 形态 | 典型机器 | 运行的进程 | 组网 | 备注 |
|---|---|---|---|---|
| Hub 主机 | 能使用控制台域名的公网 VPS | nett-hub、Edge、nett-node、组网进程、nett-relay | 内核 WireGuard，`public` | 控制台只有这一个地址（auth.md 第 5 节） |
| 公网节点 | 普通 VPS | nett-node、组网进程、nett-relay，可选 Edge | 内核 WireGuard，`public` | 都具备中继能力 |
| NAT 节点 | NAT 型 VPS | nett-node、组网进程、传输适配进程 | 内核 WireGuard，`dial-only` | 至少连接两个 `public` 节点 |
| 智能入口 | 家里常开的 NAS 或小主机 | nett-node、组网进程、可选 nett-relay | 内核或用户态（在组网进程中） | 宣告局域网段；路由器映射端口后为 `public` |
| 局域网主机 | 家里的其他机器 | 可选 nett-node（metrics、deploy，不开 mesh） | 经智能入口 | 无需安装组网软件 |
| macOS 主机 | Mac | 原生 nett-node（metrics、deploy）+ 容器内成员（mesh） | 容器内成员，内核 WireGuard（ADR 0016） | 同一台主机对应两个节点身份 |
| HAOS 设备 | 运行 Home Assistant OS 的设备 | 加载项内的 nett-node 与组网进程，可选 nett-relay | 内核 WireGuard（ADR 0017） | 可做智能入口；deploy、ingress 不可用 |
| 设备 | 手机 | 标准 WireGuard 客户端 | 双路径（ADR 0008） | 不运行 nett |

### 3.2 进程、权限与密钥

| 进程 | 运行身份 | 持有的密钥 | 监听 | 停止后 |
|---|---|---|---|---|
| nett-hub | 专用低权限用户 | Hub 身份密钥、Hub 主密钥 | 本机（经 Edge 暴露） | 不能变更和观测，其余照常 |
| nett-node | root，或 `CAP_NET_ADMIN` + docker 组 | 节点身份密钥 | 不监听 | 不能采集上报、部署、变更；组网照常 |
| 组网进程 | Linux：`CAP_NET_ADMIN`；用户态平台：能创建 TUN 的身份 | 组网私钥 | 组网地址（DNS、探测应答）；用户态平台上的 WireGuard 端口 | 内核 WireGuard 保持当前路径但不再切换；服务管理器重启它 |
| 传输适配进程 | 专用低权限用户 | 无 | 不监听（主动连出） | 经 TLS 的路径中断；服务管理器重启它 |
| nett-relay | 专用低权限用户 | 中继的 TLS 证书私钥；不持有组网私钥 | 公网：一个中继 UDP 端口、TLS 443 | 经它的路径切走 |
| Edge | 低权限 | 网站证书私钥；DNS 凭据（解密后才交给它） | 公网 80、443 | 该入口节点上的网站中断 |

公网端口清单见 mesh.md 第 5.5 节。

## 4. 信任链

| 信任根 | 签什么 | 谁验证 |
|---|---|---|
| 用户的 passkey 与恢复密钥 | 信任锚更新；变更批准；节点策略；组网准入材料（成员、设备凭据、宣告网段、访问规则集）；部署档位；允许降级 | 节点独立验证，不信任 Hub |
| 浏览器生成的一次性入网私钥 | 准入证明（绑定节点 ID、身份公钥、组网公钥） | Hub 与所有组网成员 |
| 项目的发布签名密钥 | 发布包 | 节点（公钥编译在 `nett` 中） |
| 用户的备份密钥 | 加密 Hub 备份 | 只有持有离线私钥的用户能解开 |

Hub 被攻破后，攻击者**能**：观测；执行低风险操作；确认中风险操作，例如在部署档位之内部署不带机密的 stack、修改路由的路径或证书；让组网连接断开；对从未收到某条撤销记录的成员隐瞒它。攻击者**不能**：提升任何节点的权限；加入组网成员或放宽访问（包括借助改标签）；新增路由的回源目标；读取机密（带机密的 stack 定义要签名）；让节点降级；伪造节点身份；用重发旧签名产物的方式恢复已撤销的权限。

**前提**：用户没有在被攻破的控制台上完成签名。控制台页面由 Hub 提供，被攻破的 Hub 可以显示一项操作、实际请求签名另一项；节点上的 `nett trust log` 可以事后核对接受过的签名（auth.md 第 2 节）。

依据：ADR 0006、0012、0014，auth.md 第 2、8、11、12 节。

## 5. 关键流程

### 5.1 入网与准入

见 auth.md 第 8 节和 ADR 0014。要点：创建 token 时，Hub 分配节点 ID 和地址，浏览器生成入网密钥对；token 携带 Hub 的完整公钥（Noise IK 需要它）和入网私钥；节点用入网私钥签署准入证明；其他成员凭"签名策略 + 准入证明"验证这个节点，不凭 Hub 的一面之词。

### 5.2 控制连接

按 protocol.md，另外两条约束：

- Hub 端点列表中至少保留一个不经组网的端点。M1 没有组网，经其他入口节点的备用端点由那个入口节点经公网 TLS 转到 Hub；这一段 Edge 配置在 ingress 模块（M3）之前需要手工维护。Hub 主机自己的初始 Edge 配置由 Hub 安装脚本生成；
- Hub 位于 Edge 之后，只信任 Edge 地址发来的 `X-Forwarded-For`（auth.md 第 13 节）。

### 5.3 组网

见 mesh.md。与原设计相比的变化：组网工作整体放进独立的组网进程，TLS 传输适配单独以低权限运行（ADR 0013）；切换到新中继时重新握手，双方都是 `dial-only` 时两端一起切（第 8.4 节）；`nett0` 固定 MTU 1280（第 4 节）；成员准入验证（mesh.md 第 4.1 节）；单端口中继，并收紧地址绑定规则（第 5.1、5.2 节）；智能入口按来源分类做源地址转换，宣告网段默认拒绝（第 10、12 节）；设备只归属一个移动网关，配置中有两个 DNS（第 11、13 节）；macOS 使用容器内成员（第 14 节）。

## 6. 入口与回源

回源的最后一跳决定了两件事：服务能否拿到访客的真实 IP，以及按来源信任的服务会不会被意外放开。

### 6.1 三种回源目标

| 服务所在位置 | 回源路径 | 服务看到的转发者 |
|---|---|---|
| 组网成员上（Linux，容器或原生进程） | Edge → 组网 → 成员的组网地址:端口。Linux 上 Docker 的端口映射对外部流量做目的地址转换，保留来源 | 入口节点的 Edge 专用地址 |
| 智能入口后面的局域网主机 | Edge → 组网 → 智能入口（按来源分类转换）→ 局域网主机 | 智能入口的入口地址 |
| macOS 上 Docker 中的容器 | Edge → 组网 → 容器内成员 → 容器网络（发布端口会丢掉来源，事实 1） | 容器内成员在该容器网络中的地址 |

**原则**（ADR 0015）：最后一跳必须来自一个只有 Edge 能使用的地址，服务只信任这个地址发来的 `X-Forwarded-For`。Edge 默认用访客的真实地址覆盖这个头（事实 6），所以访客伪造的头会被覆盖。路由的 `status.forwarder_address` 告诉用户应该在服务里把哪个地址配置为可信代理。

### 6.2 按来源信任的服务

- 转换后的地址绝不能是回环地址；转发到宿主上的服务时，使用宿主的局域网地址，绝不使用 `host.docker.internal`（事实 2）；
- 宣告的局域网段默认只对用户的设备开放；
- Edge 专用地址只能访问路由的目标，这部分访问规则由路由生成。新增或改变回源目标等于把一个内网端口暴露到公网，属于高风险变更（changes.md 第 9 节）。

### 6.3 Edge 与 nett-relay 共用 443

实测标准 Caddy 2.10.2（事实 9、10）：

| 流量 | Edge 怎么转交 | 结果 |
|---|---|---|
| 网站 | 按 Host | 正常 |
| WebSocket 传输 | 按 Host 反向代理给 nett-relay | 正常 |
| HTTP/2 CONNECT | 匹配"方法为 CONNECT 且 SNI 为 nett-relay 的域名"（`:authority` 是目标地址，不能按 Host） | 正常，隧道内再套 TLS 也正常；其他 SNI 不放行 |
| HTTP/1.1 CONNECT | 同上 | 请求能到达后端，但隧道建立不起来 |

因此入口节点上只提供 HTTP/2 CONNECT（ADR 0011）。Edge 所在主机本身是组网成员，回源直接走组网，不需要 CONNECT。

没有可用域名的节点（例如所在地区要求域名在该云厂商备案，事实 8）：nett-relay 按 IP 提供 TLS，客户端按 Hub 下发的证书指纹校验，不发送 SNI。这条传输是否可用由路径层的测量决定，被拦截时自动不选。这类节点也不能做这些域名的入口节点：路由的 `spec.edges` 要匹配节点的 `spec.ingress_domains`。

## 7. 安全要点

| 要点 | 在哪里 |
|---|---|
| 部署档位：中风险的部署不能使用特权容器、宿主网络、宿主路径挂载等，提高档位需要签名 | changes.md 第 7.1 节 |
| 发布签名属于项目；节点只自动接受更高版本，降级需要签名；升级只经 `release` 分区 | auth.md 第 12.3 节、ADR 0012 |
| 机密（stack 敏感变量、DNS 凭据）由浏览器用目标节点的公钥加密，Hub 只存密文 | auth.md 第 13 节 |
| 备份包含 Hub 身份私钥和主密钥，用备份公钥加密，由其他节点定时拉取 | auth.md 第 13 节、protocol.md 第 5 节 |
| `ai` 类型 token 的一切写入都经过变更集 | auth.md 第 6.2 节、changes.md 第 5 节 |
| 恢复密钥在浏览器本地签名，Hub 从未见过恢复私钥 | auth.md 第 4 节 |
| 节点不在云主机的"局域网地址"上提供 DNS；局域网地址上的探测应答不响应未认证的探测 | mesh.md 第 7、11 节 |
| 控制台页面由 Hub 提供：签名承诺的前提；`nett trust log` 事后核对 | auth.md 第 2 节 |
| 撤销记录：旧的签名产物不能恢复已撤销的权限；准入材料不按批准的过期时间拒绝 | auth.md 第 11.2、11.4 节 |
| 机密绑定签名的 stack 定义 | auth.md 第 13 节、changes.md 第 9 节 |
| 访问规则签名展开后的结果，改标签不能扩大访问 | mesh.md 第 12 节、api-resources.md 第 5.7 节 |
| Edge 专用地址防冒用；CONNECT 由 nett-relay 逐连接授权 | ADR 0015；mesh.md 第 5.4、12 节 |
| 过滤规则挂在目的地址转换之前，先于对端生效，失败时拒绝 | mesh.md 第 12 节 |

## 9. 主要风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 组网工作量 | M2 是全项目最大的一块，新增了准入验证、单端口中继、分类转换 | M2 第一步是 Linux 原型关卡，实测中继接管、切换时间、漫游纠正和 MTU，通过后再铺开；macOS 改用容器内成员，收窄用户态范围 |
| 用户态 WireGuard 选型 | 维护状态、性能和内存 | M2 开工前评估；在 NAS 系统上先逐项验证 TUN、IP 转发、NAT 能力 |
| 网络环境 | UDP 被限速或识别、跨境链路晚高峰质量差、域名备案限制 | TLS 传输兜底；M1 起积累线路数据；某条传输（例如按 IP、不带 SNI 的 TLS）在某个网络里是否可用，由测量决定，不预设 |
| 资源预算 | 节点上最多四个常驻进程（node、组网进程、传输适配进程、relay），各 ≤ 5 MB | 分别计量，同时记录 RSS 和 PSS（development.md 第 4 节）；分片重组落盘；每个里程碑做浸泡测试 |
| 只支持 HTTP/1.1 CONNECT 的客户端 | 入口节点上用不了 CONNECT | 使用非入口节点上的 nett-relay |
| 云安全组只能手工改 | 无法自动化 | mesh.md 第 5.5 节的端口清单，`nett doctor` 给出具体提示 |
| Hub 主机是最大的单点 | Edge、中继、移动网关集中在一台机器上 | architecture.md 第 12.3 节；加密备份由其他节点拉取 |

## 10. 分阶段要点

roadmap 已按本次复核更新。与原计划相比：

- **M1** 增加：恢复密钥与备份密钥、准入证明、信任锚、变更集最小版本与 passkey 签名（设计文档原本就放在 M1，roadmap 曾写在 M3）；项目发布签名与防降级；加密备份由其他节点拉取；Hub 安装脚本生成初始 Edge 配置；线路测量只由节点主动发起；
- **M2** 增加：原型关卡、组网进程与传输适配进程、准入验证、撤销记录、Edge 专用地址与分类转换、宣告网段默认拒绝、单端口中继、HTTP/2 CONNECT、macOS 容器内成员、`whois`。验收中的"Edge 回源全部经过组网"在 ingress 模块完成之前手工修改 Edge 配置；
- **M3** 增加：部署档位、机密加密下发并绑定签名的 stack 定义、路由的回源选项与域名约束。

## 11. 实践中得到的事实

第 1–7 条来自一次真实部署：云主机上的 Caddy 经 WireGuard 隧道，回源到家里 macOS 上 OrbStack 中的容器服务。第 9、10 条是 2026-11-04 在本机容器中对标准 Caddy 2.10.2 的实测。

| # | 事实 | 用在 |
|---|---|---|
| 1 | macOS 上的 Docker（OrbStack）：经发布端口访问容器的所有客户端，在容器内都显示为容器网络的网关地址，局域网、VPN、本机访问都一样 | 6.1；ADR 0015、0016 |
| 2 | 容器经 `host.docker.internal` 访问宿主上的原生服务，宿主看到的来源是 `127.0.0.1` | 6.2 |
| 3 | OrbStack 容器中的内核 WireGuard，在宿主开着代理类 VPN 应用（增强模式）时工作正常，UDP 直接发出，没有被代理截走 | ADR 0016 |
| 4 | 有的云厂商的安全组默认拒绝全部入方向 UDP，而且只能在网页控制台手动修改 | mesh.md 第 5.5 节 |
| 5 | 容器中的 Caddy 可以直接经宿主的 WireGuard 接口访问隧道地址，Docker 的地址伪装把来源换成宿主的隧道地址 | ADR 0015（按容器地址匹配 Edge 流量） |
| 6 | Caddy 默认用真实来源覆盖 `X-Forwarded-For`，并写入 `X-Forwarded-Proto: https`，伪造的头会被覆盖 | 6.1 |
| 7 | 把隧道端点放进服务所在的容器网络、只在隧道地址上监听，可以让服务认出代理；这个端点容器空闲内存约 1.6 MiB | ADR 0016 |

## 13. 修订记录

复核清单中的 48 条问题已全部处理，按类别：

- **安全与信任（16 条）**：成员表、部署、发布签名、数据面、IK 握手、设备凭据、AI 写入、中继绑定、网段默认值、监听地址、机密、备份、真实来源、恢复密钥签名位置、签名重发幂等、`nett leave`。按上面的决策处理；签名重发视为幂等（auth.md 第 11.2 节）；`nett leave` 定为降权，协议增加 `Leave` 消息；
- **阶段与归属（9 条）**：roadmap 的 M1、M2、M3 已调整；服务发现改归 metrics 模块；升级只经 `release` 分区，`node.upgrade` 动作移除，降级改为 `node.allow_release`；tailscale 后备标为未排期、不计入节点预算、地址池排除组网网段；死信开关的监视由其他节点的 metrics 模块承担；身份查询即 `whois`，服务注册表即 `services` 与 `hostnames`；
- **组网与入口（8 条）**：单端口中继解决了只映射一个端口的节点无法做中继的问题；设备归属网关；DNS 范围与两个 DNS；未开 mesh 的局域网主机的主机名；路由的回源选项；节点角色进入 `node-policies`；中继流量上限改为 Hub 下发（`nodes.spec.relay_limits`）。组网地址的分配粒度**按凭据**而不是按成员：复核清单原先写的是"按成员"，修订时发现同一设备的多份凭据会同时作为网关的不同对端，而 WireGuard 不允许对端的 `AllowedIPs` 重叠，因此改为每份 WireGuard 凭据一对地址（mesh.md 第 3 节）；
- **资源预算（2 条）**：分片重组落盘；已完成任务记录最多 1000 条；预算统一为"各自 ≤ 5 MB"；
- **一致性（13 条）**：恢复密钥命名；节点 ID 在创建 token 时分配；模块风险等级（metrics 为低，其余为高）；状态机补上 `applying → succeeded / failed`；签名对象以 auth.md 为准，统一为 `status.plan.hash`；补上缺失的资源和字段（`trust`、token 的 `kind` 与 `allowed_sources`、`trigger` 的 `api_token`、设备的 `disabled`、服务的 `start`）；权限范围改为 `<资源>:propose`、`heartbeat-checks:ping`，动作目录增加"所需权限范围"一列；降权规则的表述统一；`dial-only` 的写法统一；安装命令统一带 `sudo`；入网 token 有效期为默认 30 分钟、最长 24 小时；README 补上 nett-relay 和 nett-datapath；命令表补上 `nett trust reset`、`nett deny`；roadmap P0 勾选已完成的设计草案。

复核中另外做出的连带调整：新增或改变回源目标的路由变更改为高风险（它会生成放宽访问的规则，而放宽访问需要签名）；恢复密钥和备份密钥由浏览器生成。

**外部评审**（2026-11-04）：由另一个模型只读取公开文档的副本独立评审，提出 23 条意见和 3 个疑点。逐条对照原文核实后，全部成立或部分成立，按下面的方式处理（部分条目的严重程度经核实后下调）：

- **签名与信任**：控制台页面的信任边界（D13）；机密绑定 stack 定义（D14）；访问规则签名展开后的结果，改标签不能扩大访问（mesh 第 12 节）；准入材料原先按"首次接受时未过期"验证，很久以后加入的成员会拒绝老成员，改为只由被授权的节点自己检查过期（auth 第 11.2 节）；新增撤销记录，重发旧的签名产物不能恢复已撤销的权限（auth 第 11.4 节）；自动回滚与"版本只增不减"冲突，改为先放宽、后收窄（changes 第 8 节）；设备私钥只在浏览器生成，配置只在创建时导出一次（auth 第 10 节）；`whois` 由本机按准入材料回答（mesh 第 11 节）；
