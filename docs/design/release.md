# Release and Installation

- Status: draft
- Phase: M1 (the release workflow and Homebrew items of roadmap M1 "Installation")

## 1. Goals

After a version tag is pushed, CI builds `nett` for each platform, signs it with the project's release key (ADR 0020), publishes a GitHub Release, and updates the Homebrew formula and the project website. The computer that runs the signing tool is installed and upgraded with Homebrew; other machines, Linux and macOS alike, are installed with the install script on the project website (section 6). Machines connected to a Hub upgrade themselves (section 7); the enrollment command is described in hub.md.

## 2. Versions and artifacts

- Version numbers follow semantic versioning and equal `version` in the workspace `Cargo.toml`; tags are written `v<version>`, and the release workflow fails when the two differ. User-visible changes are recorded in `CHANGELOG.md`;
- Each target platform has one archive `nett-<version>-<target>.tar.gz`, containing `nett`, `LICENSE-MIT` and `LICENSE-APACHE`:

| Target | Use |
|---|---|
| `aarch64-apple-darwin`, `x86_64-apple-darwin` | macOS native member (install script) and signing tool (Homebrew) |
| `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl` | Linux servers (statically linked) and images for container members |

- Each target also has the bare program `nett-<version>-<target>`, which nodes download when they upgrade themselves (section 7);
- Every archive and bare program has a `.minisig` of the same name, with the trusted comment `nett v<version> <file name>`; `SHA256SUMS` lists the hashes of all of them and is signed the same way. Users can verify with `minisign -V -p keys/nett-release-primary.pub -m <file>`;
- The macOS `nett`, in the archives and bare, is also signed with the maintainer's Apple Developer ID (identifier `io.gotry.nett`, hardened runtime, secure timestamp) and notarized by Apple. macOS then knows it as the same program across versions: its application firewall lets signed downloaded software receive by default and keeps that through upgrades, and Gatekeeper accepts it. With the ad-hoc signature the linker gives, every build is a new program to macOS, and the firewall holds the packets other members send to the mesh process until someone answers its prompt. This signature identifies the program to macOS only; what nodes trust when they upgrade is the release signature (section 7);
- `release.json` on the project website (section 6) describes the latest version for automatic upgrades: the version and, per target, the URL, SHA-256 and signature of the bare program (section 7). It is not signed itself: what a node installs is checked against the release signature.

## 3. Release workflow

`.github/workflows/release.yml`, triggered by `v*` tags (tags are protected by a ruleset, ADR 0020). Each job is granted only the minimum permissions it needs, and third-party actions are pinned to commit hashes:

1. **Build**: native runners for each platform (macOS arm64, Linux x86_64 and arm64) build the release version, package it and keep the bare program, and check that the tag matches the workspace version;
2. **Apple signing**: runs on a macOS runner in the `apple` environment, which only `v*` tags may use. It receives only the macOS archives and programs produced by the build jobs, signs `nett` with the Developer ID certificate (`APPLE_DEVELOPER_ID_P12` and its password `APPLE_DEVELOPER_ID_PASSWORD`, imported into a temporary keychain that is deleted when the job ends), has Apple notarize both programs (`xcrun notarytool` with an App Store Connect API key: `APPLE_NOTARY_KEY`, `APPLE_NOTARY_KEY_ID`, `APPLE_NOTARY_ISSUER_ID`), and packs the signed program into the archive and the bare program again (section 2). Like the signing job, it does not check out code and uses only the tools that come with macOS;
3. **Sign**: runs in the `release` environment, receives only the archives and programs produced by the build jobs (for macOS, those of the Apple signing job), downloads a pinned version of minisign whose hash has been verified, signs with the primary key and generates `SHA256SUMS`; it does not check out code or install other dependencies;
4. **Publish**: creates the GitHub Release and uploads the archives, bare programs, signatures and `SHA256SUMS`; the release notes are the section of `CHANGELOG.md` for this version;
5. **Update the formula**: fills in the version, URLs and hashes according to `packaging/homebrew/nett.rb` (the formula template, the single source) and pushes to `Formula/nett.rb` in `gotry-io/homebrew-tap`, using the repository secret `TAP_PUSH_TOKEN` (write access to the tap repository only);
6. **Update the project website**: verifies the `SHA256SUMS` produced by the signing job, fills in the version and the hashes of the per-platform archives according to `packaging/install.sh` (the install script template, the single source), generates `release.json` (section 7), and deploys them together with this version's archives and bare programs to `nett.gotry.io` (section 6). The deployment tool `wrangler` is version-pinned, and its configuration is `packaging/site/wrangler.jsonc`; the secrets `CLOUDFLARE_API_TOKEN` (which can only edit this account's Workers and the gotry.io Worker routes) and `CLOUDFLARE_ACCOUNT_ID` live in the `site` environment, which only `v*` tags can use: a new machine trusts this website on first install, so the secrets that deploy it are protected like the signing keys.

## 4. macOS: Homebrew and the mesh service

- The computer that runs the signing tool installs the command line (`nett site` etc.) with `brew install gotry-io/tap/nett`, uses it with the user's privileges, and upgrades it with `brew upgrade`. The formula's install notes, like the output of the nett command, are English only (architecture.md section 14.3). Other Macs use the install script (section 6) to install to `/usr/local/bin/nett`, and the following steps are the same;
- The mesh service of a native member runs as root (design/userspace.md section 6.3). Homebrew directories are writable by ordinary users; if the root service ran the program there directly, a malicious program running with the user's privileges could replace it and obtain root and the mesh private key at the next start. The service therefore runs a root-only copy:
  - `sudo nett install`: one command completes the installation; all paths are fixed and the user does not need to know them:
    - In `/Library/Application Support/nett/` (directory owned by root, mode `0700`) it generates the mesh private key and the identity private key (`0600`; existing ones are reused, and private keys never leave the machine). When the machine has no desired state yet, it prints the line of public keys needed by `nett site add --keys`; when it already has one, it only reports the result;
    - It copies the running `nett` to `nett` in this directory, and writes the launchd configuration (`/Library/LaunchDaemons/io.gotry.nett.mesh.plist`); its content is defined only in code. Logs go to the system log, start-up failures included, so there are no log files (userspace.md section 6.3);
    - It imports the desired state: in `nodes/` of the site directory of the user running `sudo` (site.md section 8, default `~/.config/nett`), it finds the one for this machine (the mesh public key in this node's admission material matches this machine's mesh private key) and copies it in. When the signing tool is not on this machine, or the site is elsewhere, `--config <desired.json>` specifies it, with the same check. Only regular files are read, with a size limit. The recovery key in the site directory is protected only by this user's privileges anyway, and a program able to rewrite this directory can already sign, so importing from here does not widen the risk;
    - It starts the service when there is a desired state. When the service is already running: if the program changed (after an upgrade), it restarts the service so that it uses the new copy; if only the desired state changed, it has the service reload through the local interface (the same request as `nett reload`, status.md section 4.1) without restarting or interrupting connections, and shows whether it was accepted; if neither changed, it does nothing. When there is no desired state yet, it only installs and explains the next step;
  - First installation: `sudo nett install` → on the computer that holds the site, `nett site add <name> --keys "<the printed line>"` (site.md section 4) → run `sudo nett install` again. After the desired state is updated, run the same command;
  - Joining the Hub: `sudo nett install <token>` (hub.md sections 3.5 and 7) additionally writes `io.gotry.nett.node.plist`, which runs `nett node` from the same copy; from then on the desired state is received from the Hub by it, and `sudo nett install` no longer imports from the site directory and does not accept `--config`;
  - Upgrade: run `sudo nett install` after `brew upgrade nett` (or after running the install script again). On a machine connected to a Hub, nett-node upgrades the copy itself (section 7);
  - `sudo nett uninstall` and `sudo nett leave` remove what section 8 lists;
  - Starting and stopping the service calls `/bin/launchctl`, with arguments passed as an array and a timeout (hard rules 9, 14);
- Installation and each upgrade need one sudo each. The way without sudo is an app with a Network Extension, which needs signing with an Apple developer account (the M3 client in ADR 0018).

## 5. Linux

Servers install `nett` with the install script (section 6), or download the matching archive, verify the signature and extract it. The program lives in `/usr/local/lib/nett/nett` (the directory is owned by root, `0755`) and `/usr/local/bin/nett` is a symbolic link to it: the systemd units run it from its own directory, which is the only directory besides `/etc/nett` that nett-node may write, to replace the program when it upgrades (section 7). `sudo nett install` puts itself there (it does not copy when it already runs from there), creates the link, creates the system user `nett` the mesh service runs as (`packaging/systemd/nett.sysusers`, with systemd-sysusers), gives `/etc/nett` to its group (mode `2750`, so new files get the group; the desired state is `0640`, the keys and the Hub configuration `0600`), writes the systemd units to `/usr/local/lib/systemd/system` (the place for units of locally installed software) and starts them; a file of the same name in `/etc/systemd/system` would override a unit and keep an older setup running, so `sudo nett install` stops before changing anything and names it (hub.md section 7): each unit is a file in `packaging/systemd/`, embedded at compile time; calls to `systemctl` pass arguments as an array and have a timeout. The units of nett-relay and the transport adapter are written only while the desired state needs them, by nett-node, or by `sudo nett install` on a machine without a Hub (hub.md section 5), and deleted when it no longer does. The image for container members is built with the `aarch64` or `x86_64` static version (`packaging/container/`). The Hub runs only on Linux: `nett-hub-<version>-<target>.tar.gz` is published together with the `nett` archives and signed the same way, and the image and the Compose example are in `packaging/hub/`.

## 6. Install script and project website

The one-line command on a new machine (hub.md section 3.3) begins with `curl -fsSL https://nett.gotry.io/install.sh | sh`.

- **Website**: `nett.gotry.io` is the project home page, hosted on Cloudflare: a Worker with only static files is attached to this custom domain, and the DNS records and certificate are managed by Cloudflare. Its content is deployed only by the release workflow (section 3): the home page, `install.sh`, `release.json` and the archives and bare programs of the latest version (`dl/nett-<version>-<target>.tar.gz`, `dl/nett-<version>-<target>`). The website is neither on the user's own machines nor on the Hub;
- **The script installs only `nett`**: it detects the system (Linux, macOS) and architecture (x86_64, aarch64/arm64), downloads the matching archive, verifies it against the SHA-256 written in the script (`sha256sum` or `shasum -a 256`), extracts it to a temporary directory, and installs it owned by root with mode `0755` (using `sudo` when not root): on Linux at `/usr/local/lib/nett/nett` with the link `/usr/local/bin/nett` (section 5), on macOS at `/usr/local/bin/nett`. When `/usr/local/bin/nett` is a link that the script did not make (Homebrew), it stops and says to use `brew upgrade`. The script does not read a token, connect to the Hub or write configuration; enrollment and the service are completed by the following `sudo nett install`;
- **Trust**: the first installation trusts the project website (over HTTPS) and the code hosting and CI behind it, the same as Homebrew trusting the formula and the install scripts of other mesh products (ADR 0020). The hash in the script prevents the archive from being replaced alone, in transit or on the website; if the website itself is tampered with, newly installed machines can be taken over, while machines already installed are not affected, and upgrades still verify the release signature;
- The script is written in POSIX `sh` and uses only `uname`, `curl`, `tar`, `mktemp`, `install` and hash commands; on error it says which step failed and why, and exits non-zero.

## 7. Automatic upgrades

Machines connected to a Hub upgrade themselves to the latest release (ADR 0020, auth.md section 11.3, hub.md section 9 H3). There is one path: the `release` partition of the desired state (protocol.md section 6.1).

- **The Hub relays the manifest only**: `nett-hub serve` fetches `release.json` when it starts and every 6 hours (`--releases <URL or file>`, by default `https://nett.gotry.io/release.json`; `--releases off` turns upgrades off). It uses the system's CA certificates (the container image mounts the host's), accepts at most 64 KiB, checks its shape, and sends it to every node as the `release` partition; when it changes, the Hub sends the new partition to connected nodes. The Hub never holds or serves programs, and needs no release key: nodes do not trust it for upgrades;
- **nett-node verifies everything it installs**: for its own target it compares the version with the one it runs; an equal or lower version is acknowledged as applied with nothing to do. For a higher version it downloads the bare program over HTTPS (certificates verified, at most 16 MiB, with a timeout), checks the SHA-256, verifies the minisign signature against the release public keys built into `nett` (primary and backup, ADR 0020), and requires the trusted comment to be exactly `nett v<version> nett-<version>-<target>`: the signed comment binds the version and target, so an old signed program cannot be passed off as a newer one. Only `https://` URLs are fetched;
- **Installing**: the verified program is written next to the installed one and replaces it with a rename; the replaced program is kept as `nett.previous`, the only version a machine can roll back to. nett-node then restarts the mesh service (`systemctl restart nett-mesh.service`, `launchctl kickstart -k system/io.gotry.nett.mesh`, by absolute path with arguments as an array, hard rule 9; the mesh interface stays, connections continue) and waits up to 60 seconds for its local status interface to answer. If it does not, nett-node restores `nett.previous`, restarts the mesh service again and acknowledges the upgrade as rejected. Otherwise it records an upgrade marker and exits; the service manager starts nett-node from the new program, which clears the marker once it has connected to the Hub, and then restarts nett-relay and the transport adapter when they run (`systemctl try-restart`): they run the same program, and move to the new one only once it has settled (the relay keeps its sessions across a restart, mesh.md section 5.2). A new nett-node that exits three times before connecting restores `nett.previous` itself;
- **Units follow the program**: the units are embedded in the program, so after an upgrade the new nett-node compares each installed unit with its own copy when it starts, rewrites the ones that differ, runs `systemctl daemon-reload`, and restarts the changed services that are running (`systemctl try-restart`); when its own unit changed, it exits and systemd starts it again with the new unit. On macOS it does the same with the launchd configuration: it rewrites the mesh service's and reloads that service with it (`launchctl bootout`, then `bootstrap`; when the new one does not load, the previous one is restored), and rewrites its own, which launchd reads the next time it loads the service, at the latest when the machine starts. This happens before the upgrade check, so a start that only picks up its own new unit does not count as a failed start of the new version. This is why `/usr/local/lib/systemd/system` is the third directory nett-node may write;
- **No retry loops**: a version that failed is recorded with its reason in `/etc/nett/upgrade.json` (`/Library/Application Support/nett/upgrade.json` on macOS) and is not tried again; the next higher version is. The acknowledgement for the `release` partition carries the result, and `nett site status` shows each machine's version and the last upgrade problem;
- **Paths**: on Linux the program is `/usr/local/lib/nett/nett` (section 5), and the `nett-node` unit may write only `/etc/nett`, that directory and the unit directory; on macOS it is the root-only copy in `/Library/Application Support/nett/` (section 4), and nett-node also replaces `/usr/local/bin/nett` when the install script put it there (a regular file owned by root in a directory owned by root), so the command matches the services. The computer that runs the signing tool upgrades its command line with Homebrew;
- **Build parameter**: setting `NETT_RELEASE_PUBLIC_KEYS` when building replaces the built-in public keys with the given minisign public keys (one per line), for people who build and sign their own releases and for test builds; official builds embed the keys in `keys/`. Downgrades other than the rollback above are not installed.

## 8. What nett places on a machine

nett is one program. Everything it places on a machine is listed here; `sudo nett uninstall` removes all of it except the machine's identity, `sudo nett leave` removes the identity, and after both nothing of nett remains. A change that places anything else on a machine adds it here first.

| | macOS | Linux |
|---|---|---|
| Program | `nett` (and `nett.previous` after an upgrade, section 7) in `/Library/Application Support/nett/`, the copy the services run; the command `/usr/local/bin/nett` from the install script (section 6), or Homebrew's | `/usr/local/lib/nett/nett` (and `nett.previous`), linked from `/usr/local/bin/nett` (section 5) |
| Services | `/Library/LaunchDaemons/io.gotry.nett.mesh.plist`; with a Hub also `io.gotry.nett.node.plist` | in `/usr/local/lib/systemd/system`: `nett-mesh.service`; with a Hub also `nett-node.service`; `nett-relay.service` and `nett-transport.service` only while the desired state needs them |
| Accounts | none | the system users `nett`, `nett-relay` and `nett-transport` with their groups, declared in `/etc/sysusers.d/nett.conf` |
| Identity | in `/Library/Application Support/nett/`: the keys, the desired state, the Hub configuration, the copy of the Hub's backup (hub.md section 8.2) and the trust store (`state/`) | the keys, the desired state, the Hub configuration and the copy of the Hub's backup in `/etc/nett/`; the trust store in `/var/lib/nett/`; the relay's certificate key in `/var/lib/nett-relay/` |
| Upgrade records | `upgrade.json` next to the identity | `/etc/nett/upgrade.json` |
| While running | the utun interface and its routes, `/etc/resolver/nett.internal`, `/var/run/nett/` | the `nett0` interface and its routes, nett's nftables table, systemd-resolved's settings on `nett0`, `/run/nett/` |
| Logs | the system log | the journal |

- **`sudo nett uninstall`** stops and removes the services, tears down the mesh interface and filter rules (on macOS the utun goes away with the mesh process), and deletes the program, nett's own copy of the command (a link or another installer's file is left alone), the accounts, the upgrade records and the files of the running mesh. It keeps the identity and names where it is: `sudo nett install` brings the machine back as the same member, and deleting those directories removes it (on Linux they are given to root first, so no account created later inherits them). On macOS it also removes what earlier releases placed: the start-up failure logs in `/Library/Logs/nett` with `/etc/newsyslog.d/nett.conf`, and the transport service of 0.3.11 with its account `_nett-transport` (userspace.md section 6.3);
- **`sudo nett leave`** (hub.md section 7) tells the Hub, removes the services and the mesh interface, and deletes the identity and the upgrade records; the program stays, so the machine can join a site again;
- Machines without nett's services (`nett join`, container members, hub.md section 7) hold only the directories they were given.
