# Release and Installation

- Status: draft
- Phase: M1 (roadmap M1 "Installation")

## 1. Goals

After a version tag is pushed, CI builds `nett` for each platform, signs it with the project's release key (ADR 0020), publishes a GitHub Release, and updates the project website. Every machine, Linux (Synology DSM included) and macOS alike, the computer that runs the signing tool included, is installed with the install script on the project website (section 6). Machines connected to a Hub, containers and the Hub upgrade themselves to a release once the user approves it (section 7); the enrollment command is described in hub.md.

## 2. Versions and artifacts

- Version numbers follow semantic versioning and equal `version` in the workspace `Cargo.toml`; tags are written `v<version>`, and the release workflow fails when the two differ. User-visible changes are recorded in `CHANGELOG.md`;
- Each target has one archive `nett-<version>-<target>.tar.gz`, containing its program, `LICENSE-MIT` and `LICENSE-APACHE`:

| Target | Program | Use |
|---|---|---|
| `aarch64-apple-darwin`, `x86_64-apple-darwin` | `nett` | macOS native member and signing tool |
| `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl` | `nett` | Linux machines (statically linked) and the container image (container.md) |
| `hub-x86_64-unknown-linux-musl`, `hub-aarch64-unknown-linux-musl` | `nett-hub` | The Hub (hub.md section 8) and its image |

- Each target also has the bare program `nett-<version>-<target>`, which the Hub mirrors, and nodes, containers and the Hub fetch when they upgrade themselves (section 7);
- Every archive and bare program has a `.minisig` of the same name, with the trusted comment `nett v<version> <file name>`; `SHA256SUMS` lists the hashes of all of them and is signed the same way. Users can verify with `minisign -V -p keys/nett-release-primary.pub -m <file>`;
- The macOS `nett`, in the archives and bare, is also signed with the maintainer's Apple Developer ID (identifier `io.gotry.nett`, hardened runtime, secure timestamp) and notarized by Apple. macOS then knows it as the same program across versions: its application firewall lets signed downloaded software receive by default and keeps that through upgrades, and Gatekeeper accepts it. With the ad-hoc signature the linker gives, every build is a new program to macOS, and the firewall holds the packets other members send to the nett daemon until someone answers its prompt. This signature identifies the program to macOS only; what nodes trust when they upgrade is the release signature (section 7);
- `release.json` on the project website (section 6) describes the latest version for upgrades: the version and, per target, the URL, SHA-256 and signature of the bare program (section 7). It is not signed itself: what a node installs is checked against the release signature;
- The images `ghcr.io/gotry-io/nett` (container.md) and `ghcr.io/gotry-io/nett-hub` (hub.md section 8), for `linux/amd64` and `linux/arm64`, are tagged `<version>` and `latest`. Each holds the signed bare program of its target and the CA certificates, nothing else.

## 3. Release workflow

`.github/workflows/release.yml`, triggered by `v*` tags (tags are protected by a ruleset, ADR 0020). Each job is granted only the minimum permissions it needs, and third-party actions are pinned to commit hashes:

1. **Build**: native runners for each platform (macOS arm64, Linux x86_64 and arm64) build the release version (`nett`, and on Linux `nett-hub`), package each program and keep it bare, and check that the tag matches the workspace version;
2. **Apple signing**: runs on a macOS runner in the `apple` environment, which only `v*` tags may use. It receives only the macOS archives and programs produced by the build jobs, signs `nett` with the Developer ID certificate (`APPLE_DEVELOPER_ID_P12` and its password `APPLE_DEVELOPER_ID_PASSWORD`, imported into a temporary keychain that is deleted when the job ends), has Apple notarize both programs (`xcrun notarytool` with an App Store Connect API key: `APPLE_NOTARY_KEY`, `APPLE_NOTARY_KEY_ID`, `APPLE_NOTARY_ISSUER_ID`), and packs the signed program into the archive and the bare program again (section 2). Like the signing job, it does not check out code and uses only the tools that come with macOS;
3. **Sign**: runs in the `release` environment, receives only the archives and programs produced by the build jobs (for macOS, those of the Apple signing job), downloads a pinned version of minisign whose hash has been verified, signs with the primary key and generates `SHA256SUMS`; it does not check out code or install other dependencies;
4. **Publish**: creates the GitHub Release and uploads the archives, bare programs, signatures and `SHA256SUMS`; the release notes are the section of `CHANGELOG.md` for this version;
5. **Images**: builds the two images from the files the signing job produced, after checking them against `SHA256SUMS`, for both architectures with Podman, which comes with the runner, from `packaging/container/Dockerfile` and `packaging/hub/Dockerfile` (no step runs inside an image, so no emulation is needed), and pushes them to the GitHub Container Registry with the job's `GITHUB_TOKEN`, which alone has `packages: write`. The CA certificates are those of the build runner's `ca-certificates`;
6. **Update the project website**: verifies the `SHA256SUMS` produced by the signing job, fills in the version and the hashes of the per-platform archives according to `packaging/install.sh` (the install script template, the single source), generates `release.json` (section 7), and deploys them together with this version's archives and bare programs to `nett.gotry.io` (section 6). The deployment tool `wrangler` is version-pinned, and its configuration is `packaging/site/wrangler.jsonc`; the secrets `CLOUDFLARE_API_TOKEN` (which can only edit this account's Workers and the gotry.io Worker routes) and `CLOUDFLARE_ACCOUNT_ID` live in the `site` environment, which only `v*` tags can use: a new machine trusts this website on first install, so the secrets that deploy it are protected like the signing keys.

## 4. macOS: the command and the service

- Every Mac, the computer that runs the signing tool included, installs the command with the install script (section 6) at `/usr/local/bin/nett`, owned by root; the user runs the command line (`nett site` etc.) from there with their own privileges. On a machine connected to a Hub, nett-node replaces it with each upgrade (section 7), so the command matches the service;
- The nett service of a native member runs as root (design/userspace.md section 6.3). `sudo nett install` may run from a directory ordinary users can write, such as an archive unpacked in the home directory; if the root service ran the program there directly, a malicious program running with the user's privileges could replace it and obtain root and the mesh private key at the next start. The service therefore runs a root-only copy:
  - `sudo nett install`: one command completes the installation; all paths are fixed and the user does not need to know them:
    - In `/Library/Application Support/nett/` (directory owned by root, mode `0700`) it generates the mesh private key and the identity private key (`0600`; existing ones are reused, and private keys never leave the machine). When the machine has no desired state yet, it prints the line of public keys needed by `nett site add --keys`; when it already has one, it only reports the result;
    - It copies the running `nett` to `nett` in this directory, and writes the launchd configuration (`/Library/LaunchDaemons/io.gotry.nett.plist`), which runs `nett daemon --dir "/Library/Application Support/nett"` from that copy; its content is defined only in code. Logs go to the system log, start-up failures included, so there are no log files (userspace.md section 6.3);
    - It imports the desired state: in `nodes/` of the site directory of the user running `sudo` (site.md section 8, default `~/.config/nett`), it finds the one for this machine (the mesh public key in this node's admission material matches this machine's mesh private key) and copies it in. When the signing tool is not on this machine, or the site is elsewhere, `--config <desired.json>` specifies it, with the same check. Only regular files are read, with a size limit. The recovery key in the site directory is protected only by this user's privileges anyway, and a program able to rewrite this directory can already sign, so importing from here does not widen the risk;
    - It starts the service when there is a desired state. When the service is already running: if the program changed (after an upgrade), it restarts the service so that it uses the new copy; if only the desired state changed, it has the service reload through the local interface (the same request as `nett reload`, status.md section 4.1) without restarting or interrupting connections, and shows whether it was accepted; if neither changed, it does nothing. When there is no desired state yet, it only installs and explains the next step;
  - First installation: `sudo nett install` → on the computer that holds the site, `nett site add <name> --keys "<the printed line>"` (site.md section 4) → run `sudo nett install` again. After the desired state is updated, run the same command;
  - Joining the Hub: `sudo nett install <token>` (hub.md sections 3.5 and 7) additionally saves the Hub configuration and starts the service, or restarts it when it runs, so that it also runs nett-node, in the same process (ADR 0013); from then on nett-node receives the desired state from the Hub, and `sudo nett install` imports nothing from the site directory and refuses `--config`;
  - Upgrade: on a machine connected to a Hub, nett-node upgrades the copy and the command itself (section 7); without a Hub, run the install script again, then `sudo nett install`;
  - `sudo nett uninstall` and `sudo nett leave` remove what section 8 lists;
  - Starting and stopping the service calls `/bin/launchctl`, with arguments passed as an array and a timeout (hard rules 9, 14);
- Installation and each upgrade need one sudo each. The way without sudo is an app with a Network Extension, which needs signing with an Apple developer account (the M3 client in ADR 0018).

## 5. Linux

Servers install `nett` with the install script (section 6), or download the matching archive, verify the signature and extract it. The program lives in `/usr/local/lib/nett/nett` (the directory is owned by root, `0755`) and `/usr/local/bin/nett` is a symbolic link to it: the systemd units run it from its own directory, which the nett service may write besides `/etc/nett` and nett's unit directory, to replace the program when it upgrades (section 7). `sudo nett install` puts itself there (it does not copy when it already runs from there), creates the link, makes `/etc/nett` root's alone (`0700`; the keys, the desired state and the Hub configuration are `0600`), writes the unit `nett.service` to `/usr/local/lib/systemd/system` (the place for units of locally installed software), and enables and starts it once there is a desired state; a file of the same name in `/etc/systemd/system` would override a unit and keep an older setup running, so `sudo nett install` stops before changing anything and names it (hub.md section 7). Each unit is a file in `packaging/systemd/`, embedded at compile time; calls to `systemctl` pass arguments as an array and have a timeout. `nett.service` runs `nett daemon --dir /etc/nett` as root with only `CAP_NET_ADMIN`, `CAP_NET_RAW` and `CAP_NET_BIND_SERVICE`, on a file system that is read-only except `/etc/nett`, `/usr/local/lib/nett` and `/usr/local/lib/systemd/system` (ADR 0013), and systemd starts it again whenever it exits; its privileged start step `nett resolver` points names under `nett.internal` at the daemon's DNS responder through systemd-resolved (names-and-diagnostics.md section 3). The unit of nett-relay is written only while the desired state runs a relay, by nett-node, or by `sudo nett install` on a machine without a Hub (hub.md section 5), and deleted when it does not; nett-relay runs as a user systemd allocates and fetches its assignment from the daemon (status.md section 3.1). On Synology DSM the program and the link are the same, and the service differs (dsm.md section 6): the unit is the DSM variant in `packaging/systemd/dsm/`, runs as root with the same capabilities and a file system that is read-only except nett's directories, is not enabled, and is started by a boot task in Task Scheduler that `sudo nett install` creates. Containers run the image of container.md. The Hub runs only on Linux: its archives and bare programs are the `hub-` targets of section 2, and its image and Compose example are in `packaging/hub/`.

## 6. Install script and project website

The one-line command on a new machine (hub.md section 3.3) begins with `curl -fsSL https://nett.gotry.io/install.sh | sh`.

- **Website**: `nett.gotry.io` is the project home page, hosted on Cloudflare: a Worker with only static files is attached to this custom domain, and the DNS records and certificate are managed by Cloudflare. Its content is deployed only by the release workflow (section 3): the home page, `install.sh`, `release.json` and the archives and bare programs of the latest version (`dl/nett-<version>-<target>.tar.gz`, `dl/nett-<version>-<target>`). The website is neither on the user's own machines nor on the Hub;
- **The script installs only `nett`**: it detects the system (Linux, macOS) and architecture (x86_64, aarch64/arm64), downloads the matching archive, verifies it against the SHA-256 written in the script (`sha256sum` or `shasum -a 256`), extracts it to a temporary directory, and installs it owned by root with mode `0755` (using `sudo` when not root): on Linux at `/usr/local/lib/nett/nett` with the link `/usr/local/bin/nett` (section 5), on macOS at `/usr/local/bin/nett`. When `/usr/local/bin/nett` is a link that the script did not make, it stops: the link belongs to another installer. The script does not read a token, connect to the Hub or write configuration; enrollment and the service are completed by the following `sudo nett install`;
- **Trust**: the first installation trusts the project website (over HTTPS) and the code hosting and CI behind it, the same as the install scripts of other mesh products (ADR 0020). The hash in the script prevents the archive from being replaced alone, in transit or on the website; if the website itself is tampered with, newly installed machines can be taken over, while machines already installed are not affected, and upgrades still verify the release signature;
- The script is written in POSIX `sh` and uses only `uname`, `curl`, `tar`, `mktemp`, `install` and hash commands; on error it says which step failed and why, and exits non-zero.

## 7. Upgrades

Machines connected to a Hub, containers and the Hub upgrade themselves to a release once the user approves it (ADR 0027, ADR 0020, auth.md section 11.3, hub.md section 9 H3). There is one path: the `release` partition of the desired state (protocol.md section 6.1).

- **The user approves**: `nett site upgrade` approves the release the Hub holds for the Hub and every machine, `nett site upgrade <machine>...` for those machines, and `nett site upgrade --hub` for the Hub alone (site.md section 3). An approval is the version a machine, or the Hub, may be upgraded to; it is part of the site the signing tool pushes (hub.md section 4), not signed: it decides when a genuine release is installed, never what is. Nothing is approved by default, and `nett site status` shows the release the Hub holds as available for every machine and the Hub that runs an older version, with the command that approves it. A release higher than what was approved waits for its own approval;

- **The Hub relays the manifest and mirrors the programs** (ADR 0025): `nett-hub serve` fetches `release.json` when it starts and every 6 hours (`--releases <URL or file>`, by default `https://nett.gotry.io/release.json`; `--releases off` turns upgrades off). It uses the system's CA certificates (its image holds them), accepts at most 64 KiB and checks its shape. For each target in the manifest it first fetches the program into `releases/` in its data directory, writing it to disk as it arrives (at most 16 MiB; a download that receives nothing for 60 seconds is abandoned), verifies the SHA-256, the release signature and the signed comment as nodes do (below) with the release public keys built into `nett-hub`, keeps the program only when they hold, and deletes the programs of other versions; a program already in `releases/` is verified again instead of fetched. Then it sends the manifest as the `release` partition to each node approved for its version, so nodes find the programs at the Hub when they learn of the release, and to no other; when the manifest or an approval changes, the Hub sends the partition to the connected nodes it now concerns. A program it could not fetch, or whose bytes differ from the manifest, is fetched again after 1 minute, then after twice as long each time up to an hour; one whose signature does not hold is not fetched again for that manifest, and nodes fetch it from its URL. The Hub needs no release private key, and nodes do not trust it for upgrades: they verify again;
- **nett-node verifies everything it installs**: for its own target it compares the version with the one it runs; an equal or lower version is acknowledged as applied with nothing to do. For a higher version it fetches the bare program from the Hub over its session (`ProgramFetch`, protocol.md section 5), and from the URL in the manifest over HTTPS (certificates verified) when the Hub does not hold it or sends nothing for 10 seconds; a transfer from the Hub that breaks off is taken up from the Hub again on the next try (below), since the website may be the slow path. It writes the program to `nett.new` next to the installed one as it arrives (at most 16 MiB), computing its SHA-256 and BLAKE2b-512 on the way, so the program is never held whole in memory, and abandons a source that sends nothing for 60 seconds. It checks the SHA-256, verifies the minisign signature (the prehashed form, over the BLAKE2b-512) against the release public keys built into `nett` (primary and backup, ADR 0020), and requires the trusted comment to be exactly `nett v<version> nett-<version>-<target>`: the signed comment binds the version and target, so an old signed program cannot be passed off as a newer one. Only `https://` URLs are fetched; a program that fails verification is deleted and the next source tried;
- **Installing**: the verified program replaces the installed one with a rename; the replaced program is kept as `nett.previous`, the only version a machine can roll back to. nett-node records an upgrade marker, and the service exits; the service manager starts it from the new program (systemd's `Restart=always`, launchd's `KeepAlive`). Before its mesh comes up, the new program counts its starts in the marker: when it starts a fourth time without having settled, or when its mesh does not answer within 60 seconds, it restores `nett.previous`, records the version as failed and exits, so that the service manager starts the restored program. It has settled once nett-node has connected to the Hub, or once it has run for 5 minutes while the Hub is away; it then deletes the marker and restarts nett-relay when its unit is installed (`systemctl try-restart`, by absolute path with arguments as an array, hard rule 9): the relay runs the same program, and moves to the new one only once it has settled (the relay keeps its sessions across a restart, mesh.md section 5.2). On Linux connections continue across the restart, because the kernel keeps the WireGuard interface and its sessions; on macOS and the userspace data plane the TUN interface goes with the process, so connections through the mesh pause until the new program is up (userspace.md section 6.3);
- **The Hub upgrades itself** (ADR 0026): once it holds the programs of a release higher than its own and the user has approved that version for the Hub, and before it relays the manifest, the Hub takes the program of its own target (`hub-<target>`) from its mirror, unless that version is recorded in `upgrade.json` in its data directory. It writes it to `nett-hub.new` there with its signature in `nett-hub.new.minisig`, keeps the one it replaces as `nett-hub.previous` (with its signature), renames the new one into place and records the upgrade marker. Then it stops as on `SIGTERM` (nodes reconnect after about a second, hub.md section 8), copies its database to `hub.db.previous` and, in the same process, runs the installed program's check (below) on the new version, which relays the manifest to the approved machines once it has started. Until then the machines approved with it wait; a program it has not fetched or cannot place yet is tried again with the programs not held, and `nett site status` shows why. A release with no program for the Hub's target, one whose signature does not hold for the Hub's keys, or one recorded as failed for the Hub goes to the approved machines without waiting for the Hub. The installed `nett-hub` stays as it is, owned by root;
- **The installed program's check** (ADR 0026), which the Hub runs at every start and the container's `nett` at every command (container.md section 6): it runs the program in the state directory when its signature holds for the release keys built into the installed program and its signed comment is `nett v<version> nett-<version>-<target>` for its own target and a higher version than its own, through the file it verified, with the same arguments. Otherwise it runs itself, and deletes the programs there that are not newer than itself. While an upgrade marker is recorded it counts the starts of the new version; a new version that starts three times without settling (the Hub: a node's session, or five minutes of running) is replaced by `nett-hub.previous` (or the installed program), the Hub's database by `hub.db.previous`, and the version is recorded in `upgrade.json`. Once the new version has settled, it deletes the marker and the database copy;
- **Containers** upgrade with nett-node as on a machine, and place the program in their volume instead of replacing their own (container.md section 6);
- **Units follow the program**: the units are embedded in the program, so after an upgrade the new program's nett-node compares each installed unit with its own copy when it starts, rewrites the ones that differ, runs `systemctl daemon-reload`, and restarts nett-relay when its unit changed and it runs (`systemctl try-restart`); when the nett service's own unit changed, the service exits and systemd starts it again with the new unit, a start that counts as one of the new version's starts (above). On macOS the service rewrites its launchd configuration when it differs, and launchd reads it the next time it loads the service: when the machine starts, or at `sudo nett install`. launchd keeps the configuration from load time, so the file alone does not tell which one runs: the configuration carries a fingerprint of its own content in its environment (`NETT_SERVICE_CONFIG`), `sudo nett install` loads the service again when the loaded service does not show the current one, and the service logs a warning when it was started with an older one. Tailscale's `tailscaled install-system-daemon` unloads and loads the service at every run (v1.104.7 `cmd/tailscaled/install_darwin.go`); nett loads it again only when the configuration differs, so that importing a desired state does not interrupt connections. This is why `/usr/local/lib/systemd/system` is the third directory the nett service may write (section 5);
- **Failures**: when no source delivers the program (none reachable, none making progress, the Hub not holding it yet, or bytes that differ from the manifest's SHA-256), nothing is recorded: the node tries again after 1 minute, then after twice as long each time up to an hour, and reports the problem with how much of the program arrived. A version whose program matches the manifest's SHA-256 but fails the signature or the signed comment (every source delivers those same bytes), whose program differs from the manifest from every source, or which fails to install or to start (above), is recorded with its reason in `/etc/nett/upgrade.json` (`/Library/Application Support/nett/upgrade.json` on macOS) and is not tried again; the next higher version is. The acknowledgement for the `release` partition carries the result, and `nett site status` shows each machine's version and the last upgrade problem, and the Hub's (from its own `upgrade.json`);
- **Paths**: on Linux the program is `/usr/local/lib/nett/nett` (section 5), and the nett service may write only `/etc/nett`, the program's directory and the unit directory; on macOS it is the root-only copy in `/Library/Application Support/nett/` (section 4), and nett-node also replaces `/usr/local/bin/nett` when the install script put it there (a regular file owned by root in a directory owned by root), so the command matches the service; the Hub's are in its data directory, and a container's in its volume (container.md section 7);
- **Build parameter**: setting `NETT_RELEASE_PUBLIC_KEYS` when building replaces the built-in public keys with the given minisign public keys (one per line), for people who build and sign their own releases and for test builds; official builds embed the keys in `keys/`. Downgrades other than the rollback above are not installed.

## 8. What nett places on a machine

nett is one program. Everything it places on a machine is listed here; `sudo nett uninstall` removes all of it except the machine's identity, `sudo nett leave` removes the identity, and after both nothing of nett remains. A change that places anything else on a machine adds it here first.

| | macOS | Linux | Synology DSM |
|---|---|---|---|
| Program | `nett` (and `nett.previous` after an upgrade, section 7) in `/Library/Application Support/nett/`, the copy the service runs; the command `/usr/local/bin/nett` from the install script (section 6) | `/usr/local/lib/nett/nett` (and `nett.previous`), linked from `/usr/local/bin/nett` (section 5) | as on Linux |
| Services | `/Library/LaunchDaemons/io.gotry.nett.plist` | in `/usr/local/lib/systemd/system`: `nett.service`; `nett-relay.service` only while the machine's relay serves TLS (ADR 0032; an upgrade removes it from a machine whose relay does not) | in `/usr/local/lib/systemd/system`: the DSM variant of `nett.service`, not enabled; one boot-up task `nett` in Task Scheduler that starts it (dsm.md section 6.2) |
| Accounts | none | none: nett-relay runs as a user systemd allocates while it runs (`DynamicUser=yes`), which leaves nothing behind | none |
| Identity | in `/Library/Application Support/nett/` (root, `0700`): the keys, the desired state, the Hub configuration, the copy of the Hub's backup (hub.md section 8.2) and the trust store and the record of blocked endpoints (`state/`, obfuscation.md section 5) | in `/etc/nett/` (root, `0700`): the keys, the desired state, the Hub configuration, the copy of the Hub's backup, the trust store and the record of blocked endpoints (`state/`, obfuscation.md section 5) and the relay's certificate (`relay/`) | in `/etc/nett/` (root, `0700`): the keys, the desired state, the Hub configuration, the copy of the Hub's backup and the trust store and the record of blocked endpoints (`state/`, obfuscation.md section 5) |
| Upgrade records | `upgrade.json` next to the identity | `/etc/nett/upgrade.json` | `/etc/nett/upgrade.json` |
| While running | the utun interface and its routes, `/etc/resolver/nett.internal`, `/var/run/nett/` | the `nett0` interface and its routes, nett's nftables table, systemd-resolved's settings on `nett0`, `/run/nett/`, which also keeps the relay's bindings while the service restarts (gone with a reboot); on a mobile gateway whose system `filter FORWARD` chain drops forwarded traffic, one rule at its top accepting `nett0` to `nett0` (devices.md section 6) | the `nett0` interface and its routes, `/run/nett/`; the kernel's TUN driver, which `nett install` loads at boot when nothing else has, stays loaded until the next restart (dsm.md section 6.2) |
| Logs | the system log | the journal | the journal |

- **`sudo nett uninstall`** stops and removes the services (on DSM the boot task too), tears down the mesh interface and filter rules (on macOS and DSM the TUN interface goes away with the nett daemon), and deletes the program, nett's own copy of the command (a link or another installer's file is left alone), the upgrade records and the files of the running mesh. It keeps the identity and names where it is: `sudo nett install` brings the machine back as the same member, and deleting that directory removes it;
- **`sudo nett leave`** (hub.md section 7) tells the Hub, removes the services (on DSM the boot task too) and the mesh interface, and deletes the identity and the upgrade records; the program stays, so the machine can join a site again;
- Machines without nett's services (`nett join`, hub.md section 7) hold only the directories they were given; a container holds only its volume (container.md section 7).
