# 0021. Mesh experience is baselined against Tailscale

- Status: accepted
- Date: 2026-11-05

## Context

The user requires that the experience when a path breaks, when quality fluctuates, when falling back to a relay or TLS, and when recovering to a better path, as well as performance, match Tailscale.

How Tailscale does it (per magicsock in v1.104.5):

- For a connection with traffic, the current path is probed every 3 seconds; if no reply arrives within 6.5 seconds, the path is no longer trusted, and from then on every packet is sent over both this path and DERP at the same time, with the DERP connection always kept;
- When not on a direct path, every heartbeat probes all candidates (each candidate at most once every 5 seconds), and as soon as the first reply comes back it switches to that direct path immediately, with no waiting period; when already on a direct path with latency above 5 milliseconds, it tries for a better path once a minute and switches when latency improves by more than about 1%;
- It selects paths only by latency and whether there is a reply, ignoring packet loss;
- Each node hands every peer the addresses of its interfaces as well as those learned through STUN, and peers probe them all on the schedule above; an address that never replies is kept and probed on the same schedule. Every authenticated ping is answered whatever address it comes from, and its source becomes a candidate until no ping has come from it for 45 seconds. `tailscale ping` probes every address at once, outside the schedule, until a direct path answers (main at c4d689c);
- Hole punching probes are sent from WireGuard's own port; during hole punching traffic keeps flowing through DERP, and a failure does not interrupt the connection.

Following the practices "switch only after a better path persists for 30 seconds", "change the endpoint before the handshake when hole punching" and "switch to the next-best candidate after a failure", nett would be worse in three places: recovering from a relay or TLS to a better path would wait 30 seconds; a failed hole punch would stall for about 10 seconds; and when all UDP is blocked, it might try UDP relays one by one before falling back to TLS. In addition, a peer in kernel WireGuard has only one endpoint, so nett cannot "send over two paths at once" and can only make fault detection faster.

## Decision

- **Baseline**: for the four kinds of situations, break, fluctuation, fallback and recovery, compare with Tailscale on the same lab topology under the same faults. nett is no worse than Tailscale in interruption time, recovery time, number of switches during fluctuation, throughput and latency; in no case may an in-progress TCP connection be interrupted. Performance is accepted separately under M1 in the roadmap. Both the prototype gate and the M1 acceptance include this comparison (design/prototype.md).
- **Break**: for a connection with traffic, an in-tunnel probe is sent every 1 second. After 2 consecutive probes with no reply, the path enters "suspected failure": 3 extra probes are sent immediately on the current path (200 millisecond interval) while all candidate paths are probed at the same time; if all the extra probes are lost, the path is judged failed, and one of the candidates just measured is chosen to switch to. Failure detection takes about 3 seconds. When packets from the peer are still arriving (the bytes WireGuard has received from it are increasing) and an in-tunnel reply (including a late one) was received within 10 seconds, the path is not judged failed: it is up, just queuing. The current path is probed at suspected failure too: when it answers while the tunnel does not, the session was lost (the peer restarted, or a relay lost the link's index), and the handshake is redone once on that path, as soon as it answers, before any switch. A machine that restarted tells its peers so through the Hub, and they handshake again at once, as Tailscale's peers do when control hands them a new disco key; without the Hub the probes recover the pair.
- **Fluctuation**: packet loss above 30% for 3 seconds is also judged a failure (Tailscale looks only at whether there is a reply; this is more aggressive), except while queuing (a late reply was received within 10 seconds); between paths of the same type, switching is by score, keeping the hysteresis rule "better than the current by at least 15% and at least 10 milliseconds, persisting for 30 seconds", which switches less than Tailscale. When the current path has obvious loss (2 or more of the last 10 in-tunnel probes lost) while candidates of the same type reply consistently, it switches after 5 seconds, and candidates of the same type are probed every 3 seconds. Before a candidate's score decides a switch, a loss check measures the candidates and the current path the same way at the same time, 40 probes each 50 milliseconds apart, every 10 seconds at most while the pair loses packets and every minute otherwise: a candidate's score counts the loss it showed there, one that lost about as much as the current path while both lost compares without the loss, which is shared, the pair leaves for loss above 30% only for a candidate that lost at most 1, and takes the 5-second switch only to such a candidate; when no candidate qualifies, the pair stays (mesh.md section 8.2).
- **Fallback**: the next path is chosen only from the results just measured at suspected failure; when all UDP candidates are unreachable, it switches directly to TLS without trying UDP relays one by one. For a `dial-only` member that has a TLS candidate, the TLS transport keeps an idle connection to the TLS relay (the mesh's first probe to it establishes the connection, which is then kept alive), so a TLS connection does not have to be set up on the spot during fallback.
- **Recovery**: when the current path is not of the best type (via a relay while a direct candidate exists, via TLS while a UDP candidate exists), candidates of those better types are probed once per second; a candidate that has never replied is probed every second only in its first minute, then on Tailscale's schedule: every 5 seconds while on a relay, every minute while on a direct path, and not at all while that direct path is within 5 milliseconds, so an address that does not work costs a packet every few seconds at most, and a firewall opened in the way is found within 5 seconds while on a relay, or at once with `nett ping`, which probes every candidate before each ping; right after switching away from a better-type path because of a failure, that path is probed every 50 milliseconds for 15 seconds, and a reply is handled as soon as it arrives. After the first reply, it probes once more immediately to confirm, and after 2 consecutive replies it switches, without waiting 30 seconds. From the second failure of the same path within 10 minutes, the wait before switching back doubles with the failure count (starting at 10 seconds, at most 5 minutes), to avoid flapping on an intermittent path; recovery after the first failure does not wait, matching Tailscale's switch back on the first reply. When a path fails without ever having connected (for example the first handshake has not completed), the first time does not count as a failure; a repeat of this kind of failure is counted as usual, to avoid flapping on a path where probes get through but WireGuard does not. A path left while it was losing packets is switched back to only once its loss is measured low: at most 2 of its last 60 probes lost, about a minute at one probe a second, with no high-frequency probing.
- **A relay much faster than direct**: on long paths, for example across a congested border, a path through a well-placed relay is often much faster than the direct one. When a relay scores at most 70% of the direct path for 30 seconds and the pair carries little traffic (under 2 Mbit/s), nett moves the pair to it, and returns to direct when that gap closes or the traffic grows (mesh.md section 8.2); Tailscale keeps the direct path whenever it works. Bulk transfers stay direct, which usually has more bandwidth than a relay's uplink.
- **Hole punching without interruption: probing on the WireGuard port from M1**. On Linux kernel WireGuard, the mesh sends probes with a raw socket using the WireGuard port as the source port; for receiving, an nftables rule hands the mesh only copies of probe packets destined for this port (these packets are not WireGuard messages, and kernel WireGuard discards them); on userspace platforms the mesh already holds this port. During hole punching traffic continues on the current path, and the switch happens after the punched path is verified; a failure does not affect the connection. Probes use WireGuard's own NAT mapping, so direct candidates can also be measured accurately before switching. It is attempted as long as one end is behind a cone NAT; port guessing when both ends are behind symmetric NAT remains in M2.
- The nett daemon therefore needs `CAP_NET_RAW` in addition on Linux. On the WireGuard port only authenticated probes are answered; unauthenticated packets still get no response.

## Rationale

- The user's requirement; Tailscale is what the user is most likely to compare with;
- Failure detection takes about 3 seconds, plus one re-handshake, shorter than Tailscale's 3.5-6.5 seconds, which makes up for not being able to send over two paths at once;
- The extra probes at suspected failure keep false positives very low: with 10% random packet loss, the probability that 5 consecutive probes are all lost is about one in a hundred thousand;
- Congestion is not a break: when the connection's own traffic fills a slow link and queues are deep (a rate-limited VPS, home broadband with deep upload buffers), replies to in-tunnel probes queue for several seconds. Judging by timeout alone would switch repeatedly and re-handshake, yet all paths go through the same bottleneck, so switching does not help and throughput drops (prototype.md section 9, scenario 24). When the link is fully broken, packets from the peer cannot arrive either, so "packets from the peer are still arriving" does not affect how fast a break is detected; when only one direction works, detection is at most 10 seconds later;
- Packet loss below the failure threshold also needs to be left quickly: Tailscale's DERP runs over TCP, so loss becomes latency and no data is lost; nett's relay runs over UDP, so loss reaches the upper layer directly. Measurements show that with 5% link loss on the current relay, the 30-second hysteresis alone would keep the connection on the impaired relay for 36-105 seconds, losing about 10% of packets in that time. "2 lost out of 10" almost never occurs with 1% random loss, so a single lost packet does not trigger a switch;
- A candidate's loss needs more probes than its usual interval gives: a relay probed every 15 seconds while the pair is direct keeps one probe lost by chance in its loss for minutes, and its 50 milliseconds of score kept a relay much faster than a slowed direct path from being taken (prototype.md section 9, scenario 25); in the path layer's simulation, a relay that lost one probe before direct slowed was never taken within two minutes, and with the check it was taken after the hold in all 50 runs, while a faster relay losing 20% was taken in 34 of 50 runs without the check and in 4 with it;
- Loss is not always the path's: a receive queue overflowing at one end, or a policer on its access link, drops packets on every path alike, and so does a link every path shares. A candidate's few probes at its usual interval then look clean by chance, the pair moves to it and takes the loss along, and the better score of the path it left brings it back. Measured: under a handshake flood on a member's userspace data plane, both relays of the pair lost about 15% and it moved between them (prototype.md section 9, scenario 20(c)); in the path layer's simulation of a 15% loss on every path, 49 of 50 five-minute runs switched 1-16 times; with the check 3 of 50 switched once, none came back, and when the current relay then became 40 milliseconds slower, 49 of 50 moved to the other one once, after 35 seconds at the median. Forty probes tell a clean path from one losing 15% (it passes about one check in 80) within the 3 seconds the loss must last anyway, so leaving a path that is itself lossy is no slower;
- A restart loses the sessions of the userspace data plane, and WireGuard alone handshakes again only after 15 seconds without answers. Measured on two members reaching a machine at its obfuscated port (prototype.md section 9, scenarios 34 and 35): the probe streams stopped for 14.8-16.1 s when it restarted; with the handshake redone on the path that answers, 2.1-3.6 s; with its notice through the Hub, 0.3-0.6 s. Tailscale 1.104.5, told through its control plane, took 1.0-1.2 s for one restart (scenario 35) and 1.6-6.4 s when both ends restarted together and the machine once more 5 s later (scenario 34);
- Recovery no longer waits 30 seconds, handled separately by path type: a path of a better type switches as soon as it is verified, while paths of the same type are still subject to hysteresis;
- A lossy path is not a broken one: with 15-20% loss it still answers most probes, so two replies in a row come at once and switching back on them returns the pair to the loss within a second. Leaving on loss is where nett differs from Tailscale, which ignores loss, so the way back is judged on loss too; at one probe a second, "at most 2 of 60 lost" passes within about a minute once the loss is gone (below 2% it passes most of the time), rarely at 10% and almost never at 15% or more (prototype.md section 9, scenario 28);
- During a break Tailscale sends every packet over both the direct path and DERP, and switches back as soon as the direct path recovers (measured: 19 of 20 times within 0.26-0.29 seconds); nett cannot send over two paths at once and can only discover recovery by probing. Short failures are the most common, so within 15 seconds after switching away it probes at high frequency and then drops to once per second; high-frequency probing happens only after the first failure (when no backoff is needed);
- Hole punching without interruption is the most noticeable point of the Tailscale experience; probing on the WireGuard port is the only way to achieve it on kernel WireGuard.

## Alternatives considered

- **Keep the practices above and only record the comparison results**: recovery and hole punching would be clearly worse than Tailscale, which does not meet the user's requirement.
- **Make nett's mesh able to send over two paths at once**: only userspace WireGuard can do this, and on Linux the performance of kernel WireGuard would be given up.
- **Use nftables to redirect probe replies destined for the WireGuard port to the mesh**: redirecting alters connection tracking for that five-tuple, and later WireGuard data from the same address would also be diverted. Copying only (`log`) does not affect connection tracking, so receiving uses it.
- **Receive with a raw socket carrying a BPF filter**: the kernel first copies every incoming UDP packet to the raw socket and then filters; measurements show this lowers WireGuard throughput by about 7%.

## Consequences

- mesh.md sections 6.1, 7, 7.1, 8.2, 15 and 18 state these parameters and practices; probing on the WireGuard port belongs to M1, and M2 keeps only port guessing when both ends are behind symmetric NAT;
- The nett daemon holds `CAP_NET_RAW` on Linux (architecture.md sections 2 and 13.2, ADR 0013);
- Probe traffic increases: one in-tunnel probe per second for each pair with traffic, still within the budget of about 1 KiB/s per pair; in the 15 seconds after switching away because of a failure, the fast-recovery probe round trips use about 2.5 KB/s; a loss check sends 40 probes to each candidate and the current path over 2 seconds, while some candidate qualifies by score, at most once every 10 seconds while the pair loses packets and once a minute otherwise;
- The lab environment for the prototype gate and M1 acceptance must run Tailscale at the same time (self-hosted Headscale and DERP).
