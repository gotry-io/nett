# 0007. 自研组网：WireGuard 会话层 + nett 路径层

- 状态：已采纳
- 日期：2026-10-12

## 背景

期望的组网像导航软件一样工作：覆盖局域网、公网、国内、跨境等场景；节点之间有多种连接方式；所有能被外部连入的节点都能做中继；自动探测最优路径；路径抖动、中断或节点离线时自动切换，连接不中断；没有单点。同时，节点运行在 1 GB 级别的机器上，资源占用是硬性约束。

现有方案都不完全满足：

| 方案 | 能做到 | 做不到 |
|---|---|---|
| Tailscale | 打洞、直连、经自己节点的 UDP 中继（Peer Relays，2025 年 10 月推出）、DERP 兜底、全平台客户端 | 不比较路径质量（能直连就直连）；不支持多跳；不能按线路选中继；tailscaled 常驻 25–70 MB，跑流量时可能超过 200 MB |
| 纯内核 WireGuard | 加密，性能最好，内存约为零 | 每个对端只有一个固定地址：不探测、不切换、不中继；只支持 UDP |
| EasyTier 等 | 多传输协议，适配中国网络 | 无 iOS 客户端；不适合作为库嵌入 |

## 决定

组网由 nett 自研，分为三层：

- **会话层：WireGuard**，只负责加密。Linux 使用内核实现；无内核模块的平台使用 Rust 用户态实现。不同时维护其他加密协议。
- **传输层：可插拔**。UDP 为默认；UDP 受限时使用 TCP/TLS 443；后期加入 QUIC 和混淆包装。加密后的数据包放进这些传输里，WireGuard 本身不变。
- **路径层：组网进程**（ADR 0013；最初设计在 nett-node 的 mesh 模块中）。为每对节点维护候选路径（局域网直连、公网直连、经中继、多跳接力），持续测量，按得分选择，带防抖，路径变差时快速切换。切换只更新 WireGuard 会话的对端地址，会话和上层连接不受影响。

配套规则：

- 所有 `public` 节点都具备中继能力，由 Hub 选择实际使用的中继；中继只转发加密数据包；
- `dial-only` 节点至少连接两个 `public` 节点；
- 拓扑和密钥持久化在节点本地，Hub 离线时节点照常选路和切换；
- 一个局域网由一台运行 nett-node 的主机作为智能入口接入；
- tailscale 保留为可选后备，由 Hub 管理，对上层隐藏。后备方案未排期；只在用户显式启用的节点上运行，不受节点内存预算约束；Headscale 的地址池必须排除 nett 的组网网段。
- 路径层和用户态 WireGuard 运行在独立的组网进程中（ADR 0013）；macOS 在 M1 以原生成员加入（ADR 0018），需要访客真实 IP 的容器服务使用容器内成员（ADR 0016）。

## 理由

- WireGuard 精简、经过形式化验证、有内核实现、全平台有标准客户端，并原生支持对端地址变化，正适合作为不随路径变化的会话层；
- 它的不足（只支持 UDP、特征明显、没有中继和选路）全部可以在传输层和路径层补齐；
- 自研路径层才能实现按质量选路、多跳、按线路选中继，这正是产品的核心价值；
- 加密由内核完成，中继只转发密文，资源占用和安全性都优于在用户态处理全部流量。

## 放弃的方案

- **以 tailscale 为主后端，逐步替换**：能快速起步，但核心能力（按质量选路、多跳）始终受限，而替换成本会随时间增加。
- **自研加密协议，或在会话层使用 QUIC、OpenVPN、IPsec**：自研需要额外的安全审计，手机上也没有标准客户端；QUIC 更适合作为传输层；OpenVPN 性能和资源占用差；IPsec 在 NAT 环境和漫游场景下表现差。
- **全部走中继（不直连）**：抗干扰最好，但大流量（如远程观看视频）会受限于中继带宽。

## 影响

- 组网是项目中工作量最大的部分，M1 需要实现会话管理、路径层、nett-relay 和 TCP/TLS 传输；
- 需要评估并选定一个 Rust 用户态 WireGuard 实现；
- 两端都在 NAT 后的链路：都是锥形 NAT 或都有全局 IPv6 地址时打洞直连（M1），否则经中继连通，对称型 NAT 的打洞在 M2。内核 WireGuard 的端口归内核所有，M1 的打洞要先把 endpoint 改过去再试，失败时连接停顿几秒（design/mesh.md 第 6.1 节）。
