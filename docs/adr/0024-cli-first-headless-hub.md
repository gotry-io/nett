# 0024. The command line is the operating interface, and the Hub starts without a console

- Status: accepted
- Date: 2026-11-10

## Context

In local signing (ADR 0022), the user defines and signs the whole network on their own computer with `nett site`, then copies each machine's desired state over by hand. As machines multiply, the manual steps (copying public keys, copying files, `sudo` every time, upgrading machine by machine) become the main burden, and the root of these steps is that there is no channel between the user's computer and the machines, and no resident agent on each machine to receive anything; it has nothing to do with whether there is a graphical interface.

When M1 completes the Hub, nett-node, the Web console, passkey login and signing, and the change set together (ADR 0005, 0006, changes.md), the console, passkeys and change sets are the largest part of the work. Also, signing in the console has a known weak point: the signed payload is computed by a page provided by the Hub, and a compromised Hub can make the page show one operation while requesting a signature on another (auth.md section 2).

## Decision

- **The command line is the operating interface**: defining the network, signing, viewing the status of all machines and inviting new machines are all done with `nett`. Signing still happens on the user's own computer, with the signing tool computing and displaying what is to be signed locally;
- **The site is maintained with commands** (modeled on ufw): machines, the Edge and advertised routes, and access rules are all added and removed by `nett site` commands; each command lists what is to be signed, and after confirmation signs and delivers it; which machines connect with each other is derived from the access rules; the site state is kept by the tool, with no hand-edited file. Whether a Hub is connected or not, the same commands are used (design/site.md);
- **The Hub is a resident server with no interface**: it stores signed artifacts and the site model, composes the desired state for each machine and delivers it through the node gateway, aggregates the status of the machines, and later also handles upgrades and runtime coordination. The Hub holds no key that can sign;
- **nett-node on each machine** connects to the Hub, receives the desired state and hands it to the mesh process, and reports status;
- **The enrollment command is generated by the signing tool**, states the hash of the release package (the signing tool first verifies the release signature), and the node downloads the release package, checks the hash and then runs it; installation does not run a script provided by the Hub;
- **The Web console, passkey login and signing, and change sets are deferred**: when needed they are added as another front end on the same API, without changing the protocol between the Hub and nodes or the signature format;
- A site that does not connect to a Hub keeps using local signing as usual (local-signing.md).

For the design see design/hub.md and design/site.md.

## Rationale

- What removes the manual steps is the channel formed by "a resident server + an agent on each machine". Building the channel first yields automatic distribution, one-command enrollment and centralized status viewing;
- With signing on the user's own computer, with content computed and displayed by a tool that does not depend on the Hub, a compromised Hub cannot trick the user into signing something else, which is safer than signing in a page provided by the Hub. The enrollment command is also generated by this tool and carries the hash of the release package, so a compromised Hub cannot issue an installer with a backdoor, and "a compromised Hub cannot exceed its privileges" therefore has no additional premise. The "independent approval tool separate from the Hub" listed under "may have" in vision thereby becomes the main path;
- At the scale of a single user and a few to a dozen machines, the command line is sufficient for all operations;
- The site is kept by the tool and rules are recorded by machine ID: when a machine is removed, the rules that reference it are cleaned up together, and a new machine with the same name does not inherit them; a later console and multiple signing devices modify the same data. Access rules in the site are only allow rules, without order, so adding and removing them one at a time cannot go wrong through position: that is the difference between iptables, which manages a whole file, and ufw, which can be managed with commands;
- The deferred parts are not a separate thing apart from transitional code: the console is later built on the same API, with the node protocol and signature format unchanged.

## Alternatives considered

- **Build the console first**: the largest part of the work comes first, and replacing the manual steps comes much later; the content to be signed depends on the Hub's page;
- **The command line connects directly to each machine through the mesh** (no server): the user's computer must be online to distribute, upgrade and coordinate; the management channel runs over the mesh, so when the mesh configuration goes wrong it may break too (violating hard rule 8); the state of multiple signing devices would fork;
- **No Hub**: with few machines manual distribution is acceptable, but enrollment, upgrades, address changes, relay scheduling and centralized viewing cannot be done automatically;
- **A hand-edited site description file** (TOML): adding a machine means editing the file first; rules reference machines by name, so after a machine is removed the rules remain in the file and a new machine with the same name would inherit them; a later console cannot change a file on the user's computer;
- **Specify connections pair by pair**: with many machines, many pairs must be written; access is default deny, so a pair that no rule allows cannot transfer data even if it connects.

## Consequences

- In vision.md the Web console and passkeys belong to "may have", and in the roadmap the Web console is not scheduled; architecture.md sections 4, 5 and 13.3 describe the Hub, authentication and installation according to design/hub.md, section 11 has the library `nett-site` for the site model, and for the whole-network commands in section 13.4 see design/site.md; the site in local-signing.md is maintained by commands;
- auth.md: initialization is done through `nett site link` (section 4.1), the enrollment token is generated by the signing tool (section 8), and the site holds the `owner` token (section 6); login, sessions and passkeys are added with the Web console (section 13);
- The status of ADR 0005, 0006, 0008 and 0012 notes the deferred or modified parts (0012: the install script is not provided by the Hub); the console and change set parts of changes.md and api-resources.md are added with the Web console;
- At this stage the only signing key is the recovery key, kept on the user's computer (the risk of ADR 0022 is unchanged); later improvements are hardware keys or separate keys on multiple devices (design/hub.md section 9);
- Phone configuration (ADR 0008) is generated by the command line as a configuration file and a QR code.
