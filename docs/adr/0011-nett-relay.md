# 0011. nett-relay: independent low-privilege relay and transport entry point

- Status: accepted
- Date: 2026-10-12

## Context

The self-built mesh (ADR 0007) needs relay forwarding, transport entry points such as TCP/TLS, and path probe responses, all of which require listening on public ports. Under ADR 0001, the high-privilege nett-node must not listen on public ports.

Another need is "the application itself initiates the TCP connection": clients on networks where UDP is restricted access internal services. Such clients are not convenient to run the mesh on, but commonly support HTTPS proxies. (The host where Edge runs is itself a mesh member, and origin traffic goes directly over the mesh, so CONNECT is not needed.)

## Decision

Add an independent process, **nett-relay**, running with low privileges on `public` nodes:

| Function | Description |
|---|---|
| Packet relay | Forwards WireGuard-encrypted packets without seeing their contents. **Each relay uses only one UDP port** and determines the destination from the WireGuard messages themselves (see below) |
| Transport entry point | Accepts TCP/TLS 443 transport (QUIC later) and hands packets to the local WireGuard |
| Probe responses | Answers path-layer measurement probes; does not respond to unauthenticated probes |
| **HTTPS CONNECT proxy** | HTTP/2 over TLS; forwards per connection; multiple relays can be chained; credentials are a kind of device credentials (see auth.md) |

**Single-port relay**: `mac1` in a handshake initiation and a handshake response is computed with the receiver's public key as the key, so the relay can determine the receiver by trying the known public keys one by one. When forwarding a handshake initiation, it first records the initiator's session index and source (a pending entry), so a cookie reply can be sent back accordingly; after receiving the handshake response, it records both session indexes; subsequent data messages are forwarded by receiver index. The relay needs no private key.

**Address binding**: `mac1` only proves that the sender knows the receiver's public key. When the relay receives a handshake initiation from a new address, it does not change the binding at first; only **after the peer sends a response to that handshake** does it move the binding to the new address; a handshake response is accepted only from the peer's currently bound address. The relay has no keys and cannot verify whether a response is genuine: an attacker who can forge the source address may still forge a response and change the binding. The consequence is that this connection's ciphertext is sent to the wrong address, that is, a disconnection, and contents are not disclosed. Two further measures are therefore added: binding changes are rate limited; if no data arrives from the new address within a period after a new binding, the old binding is restored. The path layer switches as usual when it detects the interruption.

**Sharing 443 with a reverse proxy** (measured with standard Caddy 2.10.2): on an entry node, 443 is occupied by the reverse proxy, which hands nett-relay traffic over. On the Hub host this configuration section is generated by the Hub install script (ADR 0009); on other entry nodes the user configures it in their own reverse proxy.

| Traffic | How the reverse proxy hands it over | Result |
|---|---|---|
| Websites | By Host | Works |
| WebSocket transport | Reverse proxy to nett-relay by Host | Works |
| HTTP/2 CONNECT | The request's `:authority` is the CONNECT target and cannot be routed by Host; match "method is CONNECT and the TLS SNI is nett-relay's domain" | The tunnel works, and TLS inside the tunnel works too; other SNIs are not let through |
| HTTP/1.1 CONNECT | Same as above | The request reaches nett-relay, but Caddy treats the response as an ordinary response, and the tunnel cannot be established |

Therefore, when handing over through Caddy only HTTP/2 CONNECT is offered; for other reverse proxies, go by measurement. Clients that support only HTTP/1.1 CONNECT use a nett-relay that listens on 443 directly on a non-entry node.

**TLS certificates**: on an entry node the reverse proxy terminates TLS; on other nodes nett-relay serves TLS itself, the certificate can be self-signed, the fingerprint is distributed by the Hub with the relay list, and clients verify by fingerprint. When a node has no usable domain (for example, the region requires domains to be registered with the cloud provider), clients connect directly by IP without sending SNI.

**Every hop between relays uses TLS**; which relays are actually used and which path CONNECT takes is decided by the Hub based on line quality.

## Rationale

- It preserves "what has privileges is not exposed, what is exposed has no privileges": even if nett-relay is compromised, the attacker cannot obtain the mesh private key and cannot manage nodes;
- A single port means each relay needs only one UDP port opened in the security group, so a node with only one port mapped (such as the smart gateway at home) can also act as a relay;
- HTTPS CONNECT is a universal standard, so any client that supports an HTTPS proxy can use it directly, without a dedicated client;
- Packet relay and CONNECT share the TLS, authentication, and path selection infrastructure, and implementing them in one process costs the least.

## Alternatives considered

- **Implement the relay in nett-node**: one process fewer, but violates ADR 0001.
- **Allocate two ports per relayed connection (like TURN)**: simple to implement, but a large range of ports must be opened in the security group, and a node with only one port mapped cannot act as a relay.
- **A separate port for CONNECT**: not limited by the capabilities of the reverse proxy, but restricted networks often allow only 443. Measurement shows HTTP/2 CONNECT can share 443 with websites, so a separate port is not needed.
- **Packet relay only**: clients that support only an HTTPS proxy cannot use it directly.
- **CONNECT only**: supports TCP only and cannot carry mesh traffic of arbitrary protocols.

## Consequences

- CONNECT supports only TCP; UDP support (such as CONNECT-UDP) is left for later;
- A CONNECT relay can see the destination address, and the contents of unencrypted traffic are visible too. Relays all run on the user's own machines, which is acceptable;
- The CONNECT egress uses a dedicated mesh address (the CONNECT egress address) shared by all devices; the target node cannot tell devices apart from it, so nett-relay checks signed access rules per connection by credential; targets can only be mesh addresses, and it does not connect directly to the host where the relay runs or to its LAN (mesh.md section 5.4). A compromised nett-relay can reach all targets that CONNECT permits using this address;
- A single-port relay has to handle session index collisions and entry aging, and the cost of trying `mac1` must have an upper bound; when switching to a relay that has not yet handled a given connection, a new handshake is needed to establish the index (mesh.md section 8.4);
- At startup nett-relay obtains the relay assignment and the verified material needed by CONNECT from the mesh process, and does not depend on nett-node when restarting (ADR 0013);
- A nett-relay on a non-entry node binds 443 and needs `CAP_NET_BIND_SERVICE`;
- One more process on `public` nodes, and its idle memory counts toward the resource budget.
