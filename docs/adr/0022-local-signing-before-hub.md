# 0022. 接入 Hub 之前，用本地签名部署替换已有的隧道

- 状态：已采纳
- 日期：2026-11-09

## 背景

原型关卡通过之后，roadmap 原本的顺序是先接入 Hub（nett-node、入网、passkey 签名、控制台），再铺开平台和功能；替换用户手工配置的 WireGuard 隧道排在更后面。用户的近期目标是尽快用 nett 替换正在使用的隧道。

信任模型中，Hub 只是签名产物的转发者，节点用用户的信任锚独立验证每一份产物（auth.md 第 2 节）。原型的组网进程已经从本地文件读取签名的准入材料，这些材料由实验工具集中生成，节点的私钥也由它生成，因此只能用于实验。

## 决定

- 原型关卡之后、接入 Hub 之前，增加一步**本地签名部署**（design/local-signing.md）：
  - 用户自己的电脑上运行签名工具 `nett site`。它持有恢复密钥，这是唯一的信任锚；
  - 节点用 `nett mesh keys` 在本机生成私钥；
  - 正式构建的 `nett mesh --config` 读本地的期望状态文件，由用户拷到节点上；
- 签名格式、验证链条和期望状态的格式都与接入 Hub 之后相同，组网进程不区分期望状态来自哪里；
- 这一步同时实现访问控制、Edge 专用地址和以边车运行的容器内成员（mesh.md 第 12 节，ADR 0015、0016），足以替换"VPS 上的 Edge 经隧道回源到 Mac 上的容器服务"这类隧道。

## 理由

- 用户签名、节点验证的边界不变：没有 Hub 时，被攻破的 VPS 照样不能加入成员或放宽访问，因为它没有恢复密钥；
- 签名格式、准入验证和组网都复用 M1 本来就要实现的部分，没有只为过渡而写的代码；
- 原型已经在真实机器上验证了组网（prototype.md 第 9 节）。早一点替换手工隧道，就能在日常使用中尽早发现问题。

## 放弃的方案

- **按原顺序等 Hub**：替换要等 Hub、nett-node、入网流程和控制台全部完成。
- **在生产中直接使用实验构建**：实验工具集中生成节点的私钥，违反"私钥不离开节点"；实验构建也不应出现在生产机器上。
- **一个简化版的 Hub**：多一套最终要丢弃的控制面。

## 影响

- 恢复密钥以文件形式保存在用户的电脑上，只在签名时读取，比只离线保存的风险高；local-signing.md 第 3 节写明了保护建议；
- 期望状态由用户手工分发：没有自动更新、自动升级和集中的状态查看；
- 正式构建增加 `nett site`、`nett mesh keys` 和 `nett mesh --config`。接入 Hub 之后，nett-node 用同一种格式把期望状态交给组网进程；
- roadmap M1 的顺序变为：原型关卡 → 本地签名部署 → 接入 Hub → 铺开平台和功能。
