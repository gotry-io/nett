# 0022. Replace existing tunnels with local signing before joining the Hub

- Status: accepted
- Date: 2026-11-09

## Context

After the prototype gate passes, the roadmap's original order was to join the Hub first (nett-node, enrollment, passkey signing, the console), then roll out platforms and features; replacing the user's hand-configured WireGuard tunnels came much later. The user's near-term goal is to replace the tunnels in use with nett as soon as possible.

In the trust model, the Hub is only a forwarder of signed artifacts, and nodes independently verify every artifact against the user's trust anchor (auth.md section 2). The prototype's mesh process already reads signed admission material from local files, but that material is generated centrally by the lab tool, and the nodes' private keys are generated by it as well, so it can be used only for experiments.

## Decision

- After the prototype gate and before joining the Hub, add a step, **local signing** (design/local-signing.md):
  - The signing tool `nett site` runs on the user's own computer. It holds the recovery key, which is the only trust anchor;
  - Nodes generate their private keys locally with `nett mesh keys`;
  - The production build of `nett mesh --config` reads a local desired state file, which the user copies to the node;
- The signature format, the verification chain and the desired state format are the same as after joining the Hub, and the mesh process does not distinguish where the desired state came from;
- This step also implements access control, the Edge address and the container member (as the smart gateway of the container network it lives in; mesh.md sections 10 and 12, ADR 0015, 0016), enough to replace tunnels such as "the Edge on a VPS sending origin traffic through a tunnel to container services on a Mac".

## Rationale

- The boundary that the user signs and nodes verify does not change: without a Hub, a compromised VPS still cannot add members or widen access, because it does not have the recovery key;
- The signature format, admission verification and the mesh all reuse parts that M1 has to implement anyway, so no code is written only for the transition;
- The prototype has already verified the mesh on real machines (prototype.md section 9). Replacing hand-made tunnels earlier surfaces problems earlier in daily use.

## Alternatives considered

- **Wait for the Hub in the original order**: replacement would wait until the Hub, nett-node, the enrollment flow and the console are all finished.
- **Use the lab build directly in production**: the lab tool generates node private keys centrally, which violates "private keys do not leave the node"; a lab build should not appear on production machines either.
- **A simplified Hub**: one more control plane that would eventually be thrown away.

## Consequences

- The recovery key is stored as a file on the user's computer and read only when signing, which is riskier than keeping it only offline; local-signing.md section 3 states the protection recommendations;
- The desired state is distributed by the user by hand: there is no automatic update, automatic upgrade or centralized status view;
- The production build gains `nett site`, `nett mesh keys` and `nett mesh --config`. After joining the Hub, nett-node hands the desired state to the mesh process in the same format;
- The order of roadmap M1 becomes: prototype gate → local signing → joining the Hub → rolling out platforms and features.
