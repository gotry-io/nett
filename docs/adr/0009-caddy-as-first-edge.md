# 0009. 首期 Edge 使用 Caddy，路由模型与实现解耦

- 状态：已采纳
- 日期：2026-10-12

## 背景

Edge 负责 TLS 终止和反向代理。候选方案在资源和功能上差异明显。HTTPS 终止 + 反代、限制 1 CPU / 256 MB、50 并发压测 20 秒的实测：

| | Caddy 2.11 | Nginx 1.31 | Traefik 3.7 |
|---|---|---|---|
| 空闲内存 | 38–56 MB | 4.4 MB | 13.3 MB |
| 压测峰值内存 | 67.6 MB | 7.3 MB | 132.4 MB |
| 请求/秒 | 18,025 | 66,989 | 21,777 |
| p99 延迟 | 10.3 ms | 2.3 ms | 41.2 ms |

## 决定

- 首期使用 Caddy；
- Hub 只保存与实现无关的路由模型（域名 → 服务 → 节点:端口），由 ingress 模块翻译成具体反向代理的配置。

## 理由

- 目标规模下，三者的吞吐都远超需求，**性能差异没有实际意义**；
- Caddy 内置证书自动申请和续期（包括需要 DNS 验证的通配符证书），并提供无需重载的配置 API；
- 路由模型解耦后，资源更紧张的场景可以切换到 Nginx（每台节省约 25–50 MB），只需新增一个翻译后端。

## 放弃的方案

- **Nginx**：资源最省，但证书管理需要额外组件，修改配置需要重载。以后可作为第二个后端。
- **Traefik**：优势在于同机容器的标签发现，而本项目中代理和服务通常不在同一台机器；压测峰值内存最高。
- **自研**：见 ADR 0001。

## 影响

- 入口节点上 Caddy 的内存可以通过 `GOMEMLIMIT` 约束峰值。
